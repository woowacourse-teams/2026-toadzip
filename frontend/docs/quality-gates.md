# 프론트엔드 품질 게이트

## 기본 검증 루프

1. 사용자에게 달라지는 결과와 실패 조건을 먼저 정한다.
2. 변경 전에 가까운 코드, 테스트와 설정 원본을 확인한다.
3. 버그는 증상을 재현하는 테스트로 시작하고 기능은 가장 가까운 행동 테스트를 함께 둔다.
4. 개발 중에는 관련 테스트를 빠르게 반복한다.
5. 완료 직전 최종 작업 트리에서 `frontend/`의 `npm run check`를 새로 실행한다.
6. UI나 브라우저 경계가 바뀌었다면 해당 시나리오를 실제 브라우저에서 확인한다.

`npm run check`의 실제 구성은 [`package.json`](../package.json)을 원본으로 삼는다.
CI 성공만 인용하지 말고 로컬 변경을 포함한 최종 결과를 확인한다.

## 테스트 기준

- 구현 내부보다 사용자가 보는 내용과 수행하는 동작을 검증한다.
- 컴포넌트는 가능한 경우 role과 accessible name으로 찾는다.
- 정상 경로와 이번 변경으로 영향을 받는 실패·경계 상태를 검증한다.
- 네트워크와 SDK는 경계에서 제어하고 외부 서비스가 없어도 자동 테스트가 결정적으로 동작하게 한다.
- 스냅샷, 과도한 mock과 커버리지 숫자를 테스트 품질의 대리물로 삼지 않는다.
- jsdom은 DOM 행동의 증거이며 레이아웃, 실제 브라우저 API와 SDK 렌더링의 증거가 아니다.

## 수동 확인이 필요한 변경

| 변경 | 최소 확인 |
|---|---|
| 표시·상호작용 | 관련 경로의 실제 클릭·입력·포커스와 화면 |
| 라우팅·URL 상태 | 직접 접근, 새로고침, 뒤로가기와 잘못된 경로 |
| 비동기 화면 | 가능한 로딩, 빈 결과, 오류와 재시도 |
| 외부 SDK | 실제 브라우저의 로딩, 초기화, 상호작용과 정리 |
| 반응형·스타일 | 영향을 받는 대표 화면 크기 |

문서, 테스트 또는 브라우저 동작을 바꾸지 않는 내부 변경에는 수동 확인을 강제하지 않는다.

## 새 차단 검사 도입 조건

다음을 모두 만족할 때만 CI나 `npm run check`에 새 차단 검사를 추가한다.

1. 반복되었거나 실패 비용이 큰 구체적 문제를 막는다.
2. 외부 비밀과 불안정한 네트워크 없이 결정적으로 실행된다.
3. 개발자가 로컬에서 같은 명령으로 재현하고 해결할 수 있다.
4. 실행 시간과 오탐 비용이 현재 위험보다 작다.

근거 없는 버전 재검사, 커버리지 수치, E2E와 번들 크기 제한을 선제적으로 추가하지 않는다.

## 완료 보고

```text
Changed: 사용자 관점 결과와 핵심 파일
Verified: 실행한 명령과 결과
Browser: 확인한 시나리오 또는 해당 없음
Not run: 실행하지 못한 검사와 이유
Risks: 잔여 위험 또는 없음
```

검증하지 않은 항목을 통과로 표현하지 않고 검사 실패를 설정 완화로 해결하지 않는다.
