# PDF 근거로 데이터 보완

## 관리자 흐름

1. 단지·공고 목록에서 대상을 열고 `PDF로 보완`을 선택한다. 상세 화면은 전체 너비를 사용하며, `목록과 검색 펼치기`로 기존 목록과 필터를 다시 볼 수 있다.
2. 공식 출처 URL과 PDF를 선택하고 필요한 쪽수(예: `1-3, 7`)만 추출한다.
3. 자료 선택 영역이 접히면 추출 근거를 확인한다. `PDF 원문 보기`로 원문을 대조하고, 자료를 바꾸려면 `자료 다시 선택`을 펼친다.
4. 기본 방식인 `직접 입력`에서 수정 항목·값·근거 쪽수·원문 인용·변경 이유를 입력한다. 에이전트를 사용한다면 `에이전트 자료 다운로드` 파일을 전달한 뒤 `에이전트 결과 가져오기`에서 응답 JSON을 불러온다. 방식 전환 시 수기 입력은 유지된다.
5. 현재값·수정안·단위·적용 범위·인용을 확인한 항목만 선택하고 확인 메모를 작성한다.
6. 반영 후 `출처·수정 이력`에서 바뀐 항목과 PDF 근거를 먼저 확인한다. 변경 전후 전체 데이터는 `전체 기록 보기`를 펼쳐 확인한다.

수기 수정값은 항목에 맞는 입력을 사용한다. 기관·유형·설치 여부는 한국어 선택지로, 날짜는 날짜 선택기로 입력하며 금액은 정밀도를 보존하는 숫자 문자열로 처리한다.

주소는 PNU·행정구역·좌표를 함께 확인해 기존 주소 편집으로 수정한다.
이미 검토된 접수 기간은 기존 접수 일정 편집에서 수정한다.
이 화면의 수정은 단지 전체를 검증 완료로 표시하지 않는다. 실제 확인한 범위는 기존 검증 화면에 기록한다.
임대조건은 조회 당시 값과 현재 값을 함께 비교한다. 수집 중 값이 바뀌면 저장을 중단하고 수정안을 유지한다.
검토 결과를 내려받아 보관한 뒤 `현재 데이터 다시 조회`로 최신 값을 확인하고 다시 검토한다.

## 에이전트 응답

자료의 `responseTemplate`과 `allowedFields`를 기준으로 다음 응답을 반환한다.

```json
{
  "schemaVersion": "document-review/v1",
  "targetKey": "complexes:7:basic",
  "version": 2,
  "sha256": "다운로드 자료의 64자리 해시",
  "proposals": [{
    "field": "totalHouseholdCount", "value": 120, "page": 2,
    "quote": "단지 전체 세대수 120세대", "unit": "세대",
    "scope": "단지 전체", "reason": "전체 세대수 보완"
  }],
  "unresolved": [{"field": "completionDate", "reason": "선택한 페이지에 없음"}]
}
```

금액은 원 단위의 18자리 이하 정수 **문자열**이다. 예: `"12000000"`.
기관·유형은 자료에 나열된 enum, 날짜는 실제 존재하는 `YYYY-MM-DD`로 반환한다.
미확인 값을 0으로 채우거나 세대수를 임의로 합산하지 않는다. 같은 항목의 중복·미확정 제안은 거부한다.

## 처리 한계와 비용

- 유료 AI API와 자동 외부 전송을 사용하지 않는다. 운영자가 다운로드한 자료를 직접 전달한다.
- PDF.js는 선택 페이지의 텍스트와 위치를 추출한다. 표의 병합 셀·행/열 구조를 확정하지 않는다.
- 25MB·10,000쪽 이하 파일, 한 번에 50쪽·500,000자 이하를 처리한다. 같은 세션의 페이지는 재사용한다.
- 텍스트 없는 페이지는 `OCR 필요`다. OCR 처리된 PDF로 다시 작업하거나 기존 수기 편집을 사용한다.
- 해시·대상·버전·항목 형식·단위·범위·인용을 브라우저에서 검사한다. 값이 인용의 의미와 맞는지는 사람이 확인한다.
- 서버는 관리자 권한·CSRF·버전·근거 형식을 검증한다. PDF 원문을 내려받아 재검증하거나 원본 파일을 보관하지 않는다.
- 페이지 캐시는 메모리에만 있다. 새로고침 전에 필요한 자료·결과를 다운로드한다.

## 단지 누락 대조

관리자 메뉴 `단지 누락 대조`에서 공식 출처 URL·기준일·기관을 입력한 뒤 단지명·도로명주소를 한 줄씩 추가한다(최대 50개).
수집 도구나 에이전트가 준비한 목록은 `JSON 가져오기`에서 파일 또는 텍스트로 입력한다.
서비스와 같은 원천 식별자만 선택적으로 `sourceIdentifier`에 넣는다.
기관별 이름·주소 검색과 휴지통 검색을 수행하고 등록 확인·미등록 후보·동일성 검토·휴지통 후보·조회 실패로 나눈다.
검색 상한이나 실패는 미등록으로 판단하지 않는다. 결과 분류 버튼으로 확인할 후보만 표시하고, 결과를 내려받아 수집 실패·다른 명칭·공개 노출 조건을 직접 확인한다.
후보의 자동 등록·연결·복구는 수행하지 않는다.

## 검증 (2026-10-13)

- 백엔드: 기능 구현 단계의 전용 PostgreSQL에서 `./gradlew --rerun-tasks check` 2,627개 통과(실패·오류·건너뜀 0). 추가 UI 개선은 백엔드 코드를 변경하지 않았다.
- 최종 프론트엔드: Linux Docker의 Node 24.19.0에서 `VITE_API_BASE_URL=http://localhost:8080 VITEST_MAX_WORKERS=2 npm run check` 실행. lint·2,383개 테스트·TypeScript·프로덕션 빌드 통과.
  검사 이미지에 저장소 원본 `.gitignore`와 테스트가 참조하는 백엔드 `representative-points.csv`를 포함했다. 테스트 내용·제한시간·검사 설정 파일은 완화하지 않았다.
- Windows의 순차 전체 검사는 기존 검색·필터·수집 화면 테스트 7개가 시간 제한으로 실패했다. 같은 Node 버전의 Linux 전체 검사에서는 모두 통과했다.
- 실제 로컬 PostgreSQL 연동: 관리자 로그인, PDF.js 추출·선택 반영, 수정값·파일 식별값·쪽수·인용 이력 저장과 오래된 버전 요청의 409 거부를 확인했다.
- 실제 브라우저: 상세 전체 너비·목록 펼치기, 직접 입력·에이전트 방식 전환, 공식 단지 대조·결과 필터와 데스크톱(1440px)·모바일(390px) 배치를 확인했다. 임대조건 충돌 화면은 별도 API 검증 자료로 저장 중단·수정안 유지를 확인했다.
- 실제 기관 문서 전체 유형·운영 재수집·배포는 검증하지 않았다.
