# 프론트엔드 개발 기준

## 설정 원본과 기술 역할

정확한 버전과 명령은 아래 파일만 원본으로 삼고 이 문서에 복제하지 않는다.

| 판단 대상 | 원본 또는 역할 |
|---|---|
| Node.js | [`.nvmrc`](../.nvmrc)와 [`package.json`](../package.json)의 `engines.node` |
| npm | `package.json`의 `packageManager`와 `engines.npm` |
| 명령·직접 의존성 | `package.json` |
| 재현할 전체 의존성 그래프 | [`package-lock.json`](../package-lock.json) |
| TypeScript 검사 | [`tsconfig.json`](../tsconfig.json)과 참조 설정 |
| 정적 검사 | [`.oxlintrc.json`](../.oxlintrc.json) |
| 개발·테스트·프로덕션 빌드 | [`vite.config.ts`](../vite.config.ts) |
| 설치·실행 방법 | [`README.md`](../README.md) |

Node.js나 npm 계약을 변경할 때는 같은 행의 중복 정의를 함께 갱신한다.

- React는 화면과 상호작용을, React Router는 URL과 탐색을 소유한다.
- TypeScript는 정적 계약이며 외부 데이터의 런타임 안전을 대신하지 않는다.
- Vitest와 React Testing Library는 jsdom에서 사용자 행동을 검증한다.
- Vite 빌드 결과는 정적 `dist/`이며 AWS·Nginx 배포 구성은 별도 인프라 결정이다.
- 지도는 NAVER Maps JavaScript SDK 직접 연동을 기준으로 하며 React 래퍼를 미리 도입하지 않는다.
- 전역 상태, 서버 캐시, UI·CSS와 E2E 도구는 실제 문제가 생기기 전에 선정하지 않는다.

## 코드와 상태

- 기능 변경은 사용자에게 관찰 가능한 동작 하나를 완성한다.
- `main.tsx` 같은 진입점에는 부트스트랩만 두고 제품 규칙을 넣지 않는다.
- 컴포넌트는 PascalCase, 함수·변수는 camelCase, 훅은 `use`로 시작하고 테스트는 `*.test.ts(x)`로 둔다.
- 상태는 사용하는 가장 가까운 곳에 두고 계산 가능한 값이나 외부 데이터의 복사본을 중복 저장하지 않는다.
- 공유 가능한 비민감 검색·탐색 상태는 URL에 두고 일시적이거나 민감한 상태는 로컬에 둔다.
- 재사용을 예상한다는 이유만으로 공통화하지 않고 두 번째 실제 사용처에서 추출을 검토한다.
- 비동기 화면은 실제 가능한 로딩, 빈 결과, 오류와 성공을 구분하며 실패를 빈 성공으로 위장하지 않는다.
- 버튼과 입력은 의미 있는 HTML 요소와 접근 가능한 이름을 사용하고 키보드 동작을 보존한다.

## TypeScript와 외부 경계

- `strict`와 기존 lint·build 검사를 유지한다.
- URL, storage, 네트워크 응답과 SDK 값은 신뢰하지 않고 `unknown`에서 검증해 좁힌다.
- 오류를 숨기기 위한 `any`, `@ts-ignore`, 무근거 non-null assertion을 사용하지 않는다.
- 외부 타입 보완이 불가피하면 API·SDK 경계 한 곳에 격리하고 이유와 검증을 남긴다.
- 브라우저·네트워크·SDK 부수효과는 렌더링과 분리하고 등록한 이벤트와 리소스를 정리한다.
- SDK 로딩, 초기화, 실패 처리와 해제의 소유자를 하나로 두어 컴포넌트에 흩뜨리지 않는다.
- 브라우저에 전달되는 `VITE_*` 값은 모두 공개 정보로 취급한다.
- Client Secret, 서버 토큰과 비공개 키가 필요한 호출은 프론트엔드에서 직접 수행하지 않는다.
- 필수 설정이 없으면 명시적으로 실패하고 실제 Client ID를 저장소나 fixture에 기록하지 않는다.
- 환경 변수를 추가하면 `frontend/.env.example`에 실제 값 없이 이름, 용도, 필수 여부와 누락 동작을 남긴다.
- 외부 문자열을 `dangerouslySetInnerHTML`로 직접 렌더링하지 않고 불가피하면 경계에서 검증·정제한다.
- 외부 입력으로 URL을 만들 때 허용할 프로토콜과 호스트를 검증한다.

## 의존성 변경 기준

새 의존성은 다음을 모두 확인한 뒤 최소 범위로 추가한다.

1. 현재 브라우저 API와 설치된 의존성으로 해결할 수 없는 구체적 문제인가.
2. 유지보수 상태, 보안·라이선스와 번들 영향이 수용 가능한가.
3. 테스트 방법과 제거 가능한 경계가 있는가.
4. 도입 근거와 대안을 이슈 또는 PR에 남겼는가.

lock 파일을 직접 편집하거나 현재 작업과 무관한 버전 갱신을 함께 넣지 않는다.
