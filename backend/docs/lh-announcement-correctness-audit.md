검증일: 2026-09-25. 같은 결과를 더 빨리 저장하는 검증과 원천 의미의 정확성을 별도로 확인했다.

외부 응답의 `dsSbdNm`·`dsSplScdlNm`에 들어 있는 한글 필드 설명과 실제 값을 대조했다.

이 fixture의 세 가지 테스트가 수정 전에 실제 실패했고 수정 후 통과했다.

일정 원천에 세 컬럼을 추가하는 `V20260925_02__lh_announcement_schedule_dates.sql`을 추가했다.
수집 버전은 6이다. 버전 4·5의 성공 기록은 새 수집을 건너뛰는 근거로 재사용하지 않는다.
재수집 성공 후 같은 조회 조건의 과거 실패 기록을 해결한다. 재정제에서 기존의 잘못된 LH 당첨일을
올바른 날짜로 바꾸고 서류대상자 발표를 별도 일정으로 저장하는 PostgreSQL 통합 테스트를 포함했다.

## 실제 응답 → DB → 값 변환 검증

실제 인증키와 실제 서비스로 마이홈·LH 목록·공급·상세를 읽어 격리 PostgreSQL에 저장했다.
HTTP 응답 본문과 저장 행을 수집하고 Java 파서와 별도의 Python 비교 코드로 검사했다.
인증키·인증 URL은 결과에 기록하지 않았다. 운영 DB는 사용하지 않았다.

| 항목 | 결과 |
|---|---:|
| 마이홈 원천 / LH 목록 | 211행 / 581건 |
| LH 고유 요청 | 83개 조건 × 공급·상세 = 166회 |
| 유형별 요청 조건 | 060: 3, 061: 4, 062: 71, 063: 5 |

| 원천→DB 필드 대조 | 12,571개 값, 불일치 0 |
| DB→금액·세대수·일정 변환 대조 | 3,848개 값·일정 식별자 집합, 불일치 0 |

요청 해시·PAN_ID별 행 수와 순서, 응답의 조회 조건, 유형별 필드, 숫자 변환, 일정 종류·날짜를 확인했다.
독립 비교의 날짜 변환은 Java의 정규식을 호출하지 않고 별도 날짜 파서를 사용했다.
이 증거는 현재 구현한 원천 필드와 값 변환 범위에 해당하며 API의 모든 필드를 저장한다는 뜻은 아니다.

## 남은 데이터 제약

- **금액:** 402행 중 348행은 LH가 `공고문 참조`를 반환했다. 실제 숫자 보증금·월세 쌍은 54행이다.
  숫자가 없는 값은 임의로 만들지 않는다. 마이홈 금액의 활용 가능성·기존 금액의 유효성은 별도 판단한다.
- **날짜 의미:** 2개 공고의 6개 일정 행에서 `ACP_DTTM`과 구조화된 접수 날짜 범위가 다르다.
  PAN_ID는 `2015122300020741`, `2015122300020623`이다. 현재는 시각을 포함한 신청일시를 우선한다.
  세부 신청과 전체 접수 범위의 차이인지 정정 누락인지 공고문과 대조해야 한다. 차이만으로 오류나 동일 의미라고 단정하지 않는다.
- **미확정 날짜:** 당첨일 183개 중 3개는 `9999.12.31`, 13개 행은 당첨일 미제공이었다.
  변환 결과의 당첨 일정은 180개다. 날짜만 있는 값의 00:00은 저장 표현이며 실제 접수 시각을 검증한 값은 아니다.
- **수집 범위:** 현재 상세·공급 대상은 마이홈에서 연결한 공고다. LH 목록에만 있는 공고의 제품 등록은 미구현이다.
  같은 제목의 다른 PAN_ID를 자동으로 합치지 않는다.
- **완전성:** 이번 표본의 공급 최대 26행, 상세의 개별 dataset 최대 32행이다.
  실제 100·101행 경계와 모든 LH 유형의 완전성을 증명하지 못했다. 최초 응답의 상류 누락도 검출했다고 주장하지 않는다.
- **제품 전체:** 실제 원천을 기존 모든 제품 단지·주택형과 연결해 화면까지 검증한 실행은 아니다.
  매칭·트랜잭션·실패 보존은 관련 통합 테스트로 확인했다. 운영 데이터의 연결 충족률은 별도 측정해야 한다.

임시 실호출 테스트는 일반 검사에서 외부 API를 호출하지 않도록 제거했다.
재현 fixture·일정 복구 테스트·기존 실패 보존 테스트는 저장소에 남겼다.

## 성능과 정책에서 다음에 고려할 것

| 우선순위 | 지금의 근거 | 다음 조치와 적용 기준 |
|---|---|---|
| 1. 품질 완료 기준 | 실패 0건이어도 금액 348행은 숫자로 확보되지 않음 | 호출 성공률과 별도로 금액·일정 충족률, 연결 성공률, 보류 사유를 집계. 제품 준비 완료로 오인하지 않게 표시 |
| 2. 동시성과 호출 속도 | 8개 제한은 진행 중 요청의 상한이며 초당 제한이 아님 | 공식 허용량 또는 23/429 계측으로 필요를 확인하면 인증키·API 단위 호출 속도 제한을 추가. 현재는 8을 유지하고 제한 증가 시 4/2로 조정 |
| 3. 실패 범위 | 목록·공급·상세가 회로를 공유하고 회로 상태는 JVM별 | 한 API의 장애/일일 한도가 다른 API를 막는 비용을 측정. 필요하면 API별 회로와 공통 실행 상한을 조합. 다중 앱이 같은 키를 쓰면 키 전체의 예산 관리 필요 |
| 4. 재수집 우선순위 | 목록 불변은 상세 불변을 보장하지 않음 | 신규·변경·마감 임박 우선, 안정된 연결은 24시간 재확인, 미연결/마감 근접은 6시간. 실패 복구 대상은 성공 캐시에 묻히지 않게 유지 |
| 5. 삭제·철회 판정 | 공급행 감소를 부분 응답으로 거절해 기존 값을 보호 | 실제 철회·주택형 정정도 거절될 수 있으므로 공식 변경 근거 확인 후 승인된 정정 경로 마련. 단순 미조회로 삭제하지 않음 |
| 6. 남은 DB 비용 | 외부 대기는 줄었지만 전량 재정제·저장 비용이 남음 | 단계별 SQL 수·DB 대기부터 측정하고 변경된 원천/복구 대상만 정제. 공고 단위 조회 재사용과 내용 동일 시 저장 생략을 검증 |

예를 들어 요청 평균이 2초면 동시성 8의 처리량은 대략 초당 4건이지만, 0.2초면 초당 40건 가까이 된다.
응답이 빨라져도 초당 제한에 닿을 수 있으므로 두 제한은 목적이 다르다. 실제 처리량에는 DB 저장 시간도 포함된다.

타임아웃 3초/10초는 이번 표본에서 실패가 없었던 설정이다. 더 줄이기 전에 p95/p99와 타임아웃률을 본다.
읽기 타임아웃은 전체 작업 마감 시간이 아니다. 재시도·이미 시작한 worker의 종료 대기가 더해진다.
원천 데이터 오류를 네트워크 장애처럼 재시도하지 않고, 장애 차단 후 성공 데이터와 실행 잠금을 정리한 뒤 반환한다.

동시성 16 이상, 공급·상세 무제한 동시 실행, 날짜 검색 조건만을 믿는 증분 수집,
공고문 금액의 검증 없는 자동 추출은 이번에 적용하지 않았다. 각각 제한·데이터 품질의 근거가 먼저 필요하다.

## 검증과 배포

- 실측 비교는 [성능 문서](announcement-collection-performance.md)의 같은 166회 요청 비교를 따른다.
- `./gradlew test --tests 'com.toadzip.backend.ingest.*'` 629개 통과.
- 격리 PostgreSQL의 `./gradlew --rerun-tasks check` **1,447개 통과**(실패·오류·건너뜀 0).
  신규/기존 DB의 Flyway 적용·Hibernate 스키마 검증을 포함한다. 하네스·`git diff --check`도 통과했다.
- 배포 시 새 migration을 먼저 적용하고 수집 버전 6으로 재수집한 뒤 재정제한다.
  구버전 수집을 종료한 뒤 교체해야 공통 실행 잠금이 일관되게 적용된다.
- 이번 작업은 로컬 수정·격리 DB 검증이다. 운영 재수집·배포·원격 push는 수행하지 않았다.
