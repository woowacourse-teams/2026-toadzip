# Ingest 브랜치 통합 검토 (2026-09-30)

## 결과와 비교 기준

`codex/143-ingest-simplification`을 최종 작업 브랜치로 정했다. 두 브랜치는 별도 분기가 아니라 **143의 7개 커밋 위에 scheduler-removal의 3개 커밋이 이어진 관계**였다. 미커밋 통합 실행·실응답 대응은 `d82f2d0`으로 보존한 뒤 143을 fast-forward하고 최신 `origin/develop`을 병합했다. 원격 push·배포는 하지 않았다. scheduler-removal은 `d82f2d0`의 보관용 참조다.

|---|---|

목표는 한 브랜치에서 수집·정제의 흐름과 보호 정책을 함께 읽고 실행할 수 있게 하는 것이다. 기존 사용자 변경과 적용된 마이그레이션을 보존하고, 운영 DB·비밀·원격 Git 쓰기는 이번 검토 대상으로 삼지 않았다.

| 정책 | 유지한 이유·근거 |

| 공고별 원자성·금액 보호 | 기존 LH 공고의 주택형 변경과 보강이 함께 성공해야 저장한다. 검증 실패는 함께 롤백한다. 신규 금액 누락·매칭 실패는 기존 숫자와 보존 사유를 남긴다. |

## 읽을 흐름과 병합 지점

단계 순서는 `DataPipelineType.steps()`, 실제 호출은 `DataPipelineRunner.execute()`에서 시작한다. 단일 호출만 넘기는 서비스·Fetcher와 중복 로컬 잠금을 되살리지 않았다. 수집 Store와 공고·단지별 Writer의 트랜잭션 경계는 남겼다. 최신 develop 대비 ingest 운영 Java는 2,292줄 감소했다. 줄 수는 가독성의 증명이 아니며 아래 호출·저장 경계로 검토했다.

```text
통합 실행 → Runner → 수집 Service → 응답 완전성 검증 → 원천 Store
                       ↓ 수집 성공·정상 TTL 생략 때만
               정제 Service → SourceMapper → Resolver → MappingWriter
                                                     → EnrichmentWriter
공급 정정 승인 → 승인 Service → 기존 공급 refresh → 원천 Store에서 1회 소비
공고 보강 → 현재 요청의 승인된 빈 공급 확인 → LH 금액만 삭제 또는 기존 금액 보호
```

12개 병합 충돌에서 승인 재조회를 통합 수집 Service로 연결하고, 짧아진 Writer에 빈 공급·금액 보존 사유·일정 단지명을 반영했다. 신규 품질 테스트의 제거된 클래스 의존도 정리했다. 기존 마이그레이션을 수정하지 않고 develop의 3개와 통합 유형 1개를 함께 적용해 **21개**를 검증했다.

## 이번 통합의 새 검증

- LH 품질 화면 회귀는 최신 통합 결과를 무시하는 Red 1건을 확인한 뒤 Green으로 수정했다. 통합·단독이 각각 최신인 경우를 검사했다.
- 격리 PostgreSQL 55442/55443의 관련 백엔드 224개, 전체 `TEST_POSTGRES_PORT=55442 TEST_SHARED_POSTGRES_PORT=55443 ./gradlew --rerun-tasks check` 1,775개가 실패·오류·생략 없이 통과했다. 새 DB Flyway와 기존 DB baseline·Hibernate validate도 통과했다.
- 지정 Node 24.19.0·npm 11.17.0의 `npm run check`: lint, 프론트 테스트 1,089개, TypeScript·프로덕션 빌드가 통과했다. 브라우저 응답 대역에서 최신 통합 성공률 `2/3 (67%)`와 재조회 유지도 확인했다.
- 추가 스키마 테스트 4개도 통과했다. 기존 작업 DB의 `20260930.01` 뒤에 develop의 세 버전이 들어오면 기본 검증에서 시작이 막히는 Red를 확인했다. [1회 업그레이드](ingest-branch-db-upgrade.md) 후 기본 설정 재기동·재적용 0건·기존 실행 이력 보존을 검증했고 전역 설정은 바꾸지 않았다.
- 실행 소유권·계층·공고별 저장 경계와 승인 소비 정책을 읽기 전용 독립 리뷰로 확인했다. 하네스 검사·`git diff --check`도 통과했다.
- [실제 API 검증](ingest-live-verification.md)은 `d82f2d0` 이전 작업 트리의 증거다. 이번 develop 통합 뒤 외부 API를 다시 호출하거나 운영 DB·다중 인스턴스·저장소 밖 제거 API 호출을 검증하지 않았다. 당시 좌표·매칭·원천 값 경고가 남아 있다는 판단도 유지한다.

배포 시 통합 enum 이력을 읽을 수 없는 구버전 ingest를 종료하고 서버·관리자 화면을 함께 교체해야 한다. 자세한 스키마·복구 조건은 [실행 문서](data-pipeline-execution.md), 공급 정정 절차는 [LH 품질 운영](lh-announcement-quality-operations.md)을 따른다.
