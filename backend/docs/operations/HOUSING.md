# 단지 데이터

마이홈 원천을 제품 단지에 연결하고, 관리자가 같은 단지임을 확인한 경우 통합한다.

## 단지 통합

### 조건

- 원천 식별자(`hsmpSn:공급유형`)는 `myhome_complex_links`를 통해 제품 단지에 연결한다.
- 기존 단지는 마이그레이션에서 현재 ID로 1:1 연결한다. 마이그레이션은 실제 단지를 통합하지 않는다.
- 최초 통합은 단일 원천을 가진 LH 단지 2~20개를 대상으로 한다. 이미 통합한 그룹의 재통합은 보류한다.
- 같은 이름·주소·PNU·기관·공급유형은 후보 조건이다. 실제 건물과 공급 범위의 동일성은 관리자가 확인한다.
- LH의 이름·지역·공급유형이 일치하고 전체 세대수가 원천별 세대수 합계와 일치해야 미리볼 수 있다.
- 이 합계는 통합의 자동 승인 조건이 아니다. 주택형 행마다 반복된 원천 전체 세대수는 한 번만 센다.
- 채택 세대수는 확인된 단지의 해당 공급유형 범위다. 건물 전체 세대수나 주택형별 세대수로 해석하지 않는다.

### 통합 후 처리

#### 제품과 이력 보존

- 가장 작은 기존 제품 ID를 대표로 유지한다. 다른 제품 ID는 별칭으로 남겨 상세 조회를 대표로 연결한다.
- 주택형 ID와 공고 공급행·관심 단지·검증된 신청 일정의 행 ID를 유지하고 소속 단지만 이전한다.
- 단지 이미지·최근 퇴거자 수는 한쪽에만 있으면 대표에 보존하고 서로 다르면 통합을 보류한다.
- 주택형의 세대수·평면도·복층·관리비를 유지한다. 공용·공급면적이 다른 행도 각각 유지한다.
- 전용면적별 세대수의 중복 배분은 하지 않는다. 여러 주택형에 대응하는 LH 집계는 기존처럼 보류한다.
- 통합 당시의 전체 제품 행·참조·연결, 원천 값·수집 시각, 확인자·근거·실행 시각을 이력으로 보존한다.
- 현재 원천이 이후 교체되거나 삭제되어도 이력의 근거는 바뀌지 않는다.

#### 재정제

- 통합된 그룹은 연결 원천 전체를 검증한 뒤 주택형을 동기화한다.
- 연결 원천 누락, 공통 정보·세대수 변경은 실패 이력으로 남기고 기존 제품을 보존한다.
- 원천 행이 없는 누락은 승인된 연결마다 `linked-complex:` 키로 1건 기록하고 실패 집계에 포함한다.
- 승인된 원천의 공급유형 정정도 보류한다. 기존 유형이 남아 있는 별도 공급유형 추가는 유지한다.
- 주택형의 이름 기반 보정은 같은 hsmpSn 안에서만 한다. 사라진 행의 수동·보강값도 보존한다.

### 통합 실행

#### API

기준 경로: `/api/admin/ingest/myhome/complex-merges`. 관리자 로그인과 쓰기 요청의 CSRF 토큰이 필요하다.

| 메서드·경로 | 입력과 결과 |
|---|---|
| GET `/candidates` | `afterId=0&size=20`, 후보별 제품·원천 ID, 세대수, 선택 가능한 LH 원천 ID·시각 |
| POST `/preview` | `complexIds`, `lhSourceId` → 대표 ID, 채택 세대수, 원천별 시각·세대수, `previewHash` |
| POST 기준 경로 | 미리보기 입력 + `operationId`(UUID), `expectedHash`, `confirmedSameComplex:true`, `reason`(10~2000자) |
| GET `/{operationId}` | 통합 및 복구 상태, 확인자, 채택 근거의 JSON 문자열 |
| POST `/{operationId}/revert` | 통합 전 제품과 참조 복구 |

#### 확인과 실행

1. 후보의 공식 근거로 동일 건물과 공급 범위를 확인한다. 후보의 세대수 합계만으로 결정하지 않는다.
2. 미리보기 결과와 이전할 참조·수동 값의 충돌 여부를 확인한다.
3. 새 UUID와 미리보기 hash로 통합한다. 재시도는 같은 UUID와 같은 요청을 사용한다.
4. 대표 ID·이전 ID 상세, 목록·지도, 공고·주택형 참조를 확인한 뒤 재정제한다.

미리보기 뒤 원천·제품·참조가 달라지면 409로 거절한다. 새 미리보기를 확인한 뒤 새 작업으로 요청한다.
통합과 복구는 하나의 트랜잭션이며, 정제 실행 잠금과 단지·참조 잠금으로 부분 반영을 막는다.
HTTP 진입점은 기존 수집·정제 전역 잠금도 사용한다. 통합 중 원천 테이블 쓰기도 차단한다.

### 배포와 복구

#### 배포

1. DB 백업과 대상별 제품 ID·원천 ID·수집 시각을 확인하고 수집·정제 실행을 중지한다.
2. `V20260927_01`과 애플리케이션을 배포한다. 모든 실행 인스턴스가 연결 테이블을 사용함을 확인한다.
3. 위 API로 대상별 미리보기와 통합을 실행한다. 이슈의 로컬 ID를 다른 DB에 그대로 적용하지 않는다.
4. 검증 후 필요한 수집·정제를 수동으로 실행한다.

통합 후에는 연결 테이블을 모르는 이전 애플리케이션을 함께 실행하거나 그대로 롤백하면 안 된다.

#### 복구

복구는 현재 전체 제품·참조·연결 집합이 통합 직후와 같을 때만 수행한다. 후속 변경이 있으면 409로 보류한다.
보류된 복구는 이후 변경과 저장된 전후 스냅샷을 대조해 별도의 데이터 이전 작업으로 처리한다.
복구가 끝나면 원래 제품 ID·참조·연결이 돌아오고 별칭은 제거된다. 통합·복구 이력은 유지한다.
스냅샷 형식 버전은 1이다. 이후 관련 테이블 컬럼을 변경할 때 기존 이력의 복원 호환성도 검토한다.

## 주택형 정보

### 기본 임대조건

`housing_types`의 `basic_deposit`, `basic_monthly_rent`, `rental_condition_collected_at`에 마이홈 원천 행의 기본 임대조건을 저장한다.
보증금·월세는 원 단위이며 확인된 0원을 보존한다. 미제공·음수 금액은 null이다.
수집시각이 없는 과거 원천은 기본 임대조건을 제공하지 않는다.

공개 단지 상세의 `housingTypes[].basicRentalCondition`은 `deposit`, `monthlyRent`, `source`, `sourceUrl`, `collectedAt`을 제공한다.
공고별 `currentSupplyConditions`와 구분하며 단지의 금액 범위는 목록·지도의 요약값으로 유지한다.

#### 출처 링크

`sourceUrl`은 각 주택형 원천키의 단지 번호와 공급유형으로 만든다. 통합 단지의 대표 번호를 공유하지 않는다.
[마이홈 검색폼](https://www.myhome.go.kr/hws/portal/sch/selectRentalHouseInfoListView.do)의 웹 코드(행복주택 `09`, 통합공공임대 `11`)를 쓰고 공고 API 코드와 구분한다.
제공되지 않은 `atchFileId`는 생략한다. 원천키·공급유형을 확인할 수 없으면 URL만 null로 두고 금액·출처·수집시각은 유지한다.

#### 기존 데이터와 세대수

기존 데이터 역채움은 주택형 원천키가 정확히 일치하고 같은 키의 금액이 충돌하지 않는 경우만 허용한다.
면적·이름만으로 금액을 복사하지 않는다. 이후 마이홈 재정제가 금액과 수집시각을 갱신한다.

`housingTypes[].totalHouseholdCount`는 LH 보강에서 주택형 하나에 대응할 때만 저장한 세대수다.
단지의 `totalHouseholdCount`와 구분하며, 같은 면적의 여러 주택형에 중복 배분하지 않는다. null은 미제공이다.

새 컬럼이 없던 과거 단지 통합 이력도 복구할 수 있다.
새 컬럼을 포함한 이력은 기본 임대조건 변경도 후속 변경으로 감지하여 복구를 보류한다.

### 금액 검색

마이홈 기본 보증금·월세의 저장 기준은 `housing_types`의 `MyHomeRentalCondition`이다.
목록·지도·단지 상세의 금액 범위는 해당 단지 주택형의 MIN/MAX를 계산한 요약값이다.
가격과 면적을 함께 검색하면 **같은 주택형 하나**가 모든 조건을 만족해야 한다.
기본 금액이 없는 주택형을 공고 모집 금액으로 대신 채우지 않는다. 확인된 0원은 값으로 보존한다.

과거 merge snapshot에 기본 임대조건 필드가 없어도 주택형의 현재 기본 금액을 지우지 않는다.

## 단지 좌표

[도로명주소](https://www.juso.go.kr/)의 `위치정보요약DB_전체분.zip`에서 단지 주소와 일치하는 출입구 좌표만 저장한다.
원본 좌표는 GRS80 UTM-K다. 전국 데이터를 그대로 복제하거나 일변동 연계 API를 사용하지 않는다.

### 적재

관리자 세션·CSRF로 다음 순서대로 실행한다.

1. `POST /api/admin/ingest/myhome/complexes`로 단지 원천을 수집한다.
2. `POST /api/admin/ingest/juso/location-summaries`에 월 전체분 ZIP을 multipart `file`로 업로드한다.
3. `targetRoadAddressCount`, `matchedRoadAddressCount`, `unmatchedRoadAddressCount`를 확인한다.
4. `POST /api/admin/ingest/myhome/complex-mappings`로 단지를 정제한다.

### 검증과 교체

ZIP의 16개 지역 TXT가 모두 있고 비어 있지 않으며 예상 시도코드에 맞아야 한다.
ZIP·TXT는 CP949를 지원하고 각 행은 18개 컬럼이어야 한다.

전체 파일을 검증하고 주소 일치 행을 선별한 뒤 `road_address_locations`를 교체한다.
기존 삭제·PostgreSQL `COPY` 적재는 한 트랜잭션이다. 검증·DB 오류나 일치 행 0건이면 기존 데이터를 유지한다.
단지 정제와 좌표 적재는 같은 실행 잠금을 사용한다. 일반 단지 정제는 저장된 좌표를 매번 조회한다.

비공개·제한 건물은 원본에 좌표가 없을 수 있다. 해당 단지는 좌표 없음으로 남긴다.
새 전체분이 필요할 때만 같은 API로 교체하며 정기 실행·주소 API 인증키는 사용하지 않는다.

스키마는 [Flyway](DATABASE.md#flyway)를 따른다. 앱 롤백 시에도 참조 좌표를 보존한다. 테이블 삭제는 별도 승인을 받는다.
