# 공고 수집

마이홈 → LH 목록 → LH 공급 → LH 상세 순서로 수집한다.
실행·중지·결과 조회는 [수집 운영](INGEST.md)을 따른다.

## 수집 대상과 설정

### 원천 활성 상태

마이홈은 페이지당 500행을 요청하고 `totalCount`까지 읽는다.
모든 공급유형의 전체 페이지가 성공한 실행에서만 미조회 횟수를 늘린다.
한 번 미조회면 활성 유지, 두 번 연속이면 비활성화하며 재조회하면 활성화하고 횟수를 초기화한다.
목록에서 사라져도 원천·제품을 삭제하지 않으며 과거 공고 상세는 계속 조회할 수 있다.

### LH 조회 대상

진행 중·종료 후 30일 이내 공고와 종료일이 없거나 해석 불가한 공고는 매 실행 조회한다.
30일이 지난 공고는 일반 수집에서 제외하며 공고별 재조회는 가능하다.

마이홈의 활성 원천 중 최신 회차를 쓰고 모두 비활성이면 마지막 관찰 회차를 쓴다.
LH 목록 코드가 유일하게 일치하면 보완하며 없거나 모호하면 마이홈 해석을 유지한다.
현재 원천 요청끼리 충돌하면 실패를 남기고 기존 연결을 보존한다. URL의 `panId`만으로 원천을 고르지 않는다.

### LH 요청 설정

| 환경 변수 | 기본값 | 용도 |
|---|---|---|
| `LH_ANNOUNCEMENT_MAX_CONCURRENT_REQUESTS` | `8` | 공급·상세 동시 요청 수, 1~8 |
| `LH_ANNOUNCEMENT_CONNECT_TIMEOUT` | `PT3S` | 연결 대기 제한 |
| `LH_ANNOUNCEMENT_READ_TIMEOUT` | `PT10S` | 소켓 읽기 대기 제한 |

완료된 슬롯에 다음 요청을 넣는다. 같은 `panId`의 서로 다른 조건은 순서대로 처리한다.
동일 요청은 500행 배치를 넘어도 한 실행에서 한 번 조회하고 공고별 성공 연결을 남긴다.
읽기 타임아웃은 전체 수집을 10초 안에 끝내는 제한이 아니다.

### 호출 제한과 장애

- HTTP 429·게이트웨이 코드 22/23은 재시도 없이 새 요청과 남은 LH 단계를 중단한다. 이미 시작한 작업은 정리한다.
- 일시 장애는 최초 호출을 포함해 최대 3회 시도한다. 연결·5xx 실패가 연속 5회면 30초 차단한다.
- 차단 후 요청 1건으로 복구를 확인한다. 성공하면 재개하고 실패하면 다시 차단한다.
- 저장 실패도 새 요청 투입을 중단한다. 성공한 원천은 보존하며 실패 요청을 성공으로 기록하지 않는다.

차단은 JVM 안의 LH 목록·공급·상세가 공유한다. 다른 앱의 같은 키 사용까지 제한하지 않는다.
차단된 단독 API는 `503 LH_ANNOUNCEMENT_UNAVAILABLE`로 응답한다.
공유 요청 실패는 같은 실행에서 반복하지 않고 다음 실행에서 재조회한다.

## 저장과 정제

### 목록 갱신

`POST /api/admin/ingest/lh/announcements/catalog`는 관리자 세션·CSRF로 목록만 갱신한다. 제품 등록·정제는 하지 않는다.
전체 페이지 검증 후 목록·성공 기록을 함께 저장한다. 실패·불완전 응답은 기존 목록을 보존한다.
신규·변경·미변경 수는 `ingest.announcement.catalog.rows`의 `change` 태그로 확인한다.

### 공급·상세 보호

원천·성공 기록을 한 트랜잭션으로 저장한 뒤 공고 연결을 반영한다.
동일 응답도 검증 후 실제 성공 시각을 갱신한다. 연결만 추가할 때는 원천·성공 시각을 바꾸지 않는다.

| 응답 | 처리 |
|---|---|
| `dsSch` 조회 조건 없음·불일치 | 저장 거절 |
| 기존 상세가 있는데 새 상세가 비어 있음 | 교체 거절 |
| 기존 공급행이 있는데 빈 응답·행 누락 | 교체 보류 |
| 비교할 기존 원천이 없는 최초 빈 응답 | 허용. 성공 연결 확인 후 마이홈 정보로 정제 |

공급 비교는 단지명·주택형·전용면적·공급면적과 중복 수를 확인한다.
값이 다른 중복은 세대수·금액별 개수도 보존해야 한다. 추가·순서 변경은 허용한다.
수집 버전이 바뀌어도 같은 조건의 원천을 보호하며 최초 응답의 완전성까지 보장하지는 않는다.

실패·불완전 응답은 이전 성공 원천·시각·연결을 보존하고 실패를 기록한다.
연결 저장만 실패해도 성공 원천은 남으며 다음 수집에서 재조회·복구한다.

### 제품 반영

공급·상세의 성공 연결과 원천이 모두 현재 요청 해시·`panId`에 맞아야 정제한다.
한쪽만 새 요청으로 수집되거나 연결이 다르면 기존 제품을 유지하고 보류한다.

기존 LH 보강 공고의 매핑 변경·보강은 함께 저장한다. 매칭이 모호하거나 새 주택형 금액이 없으면 함께 롤백한다.
최초 공고는 성공 연결을 확인한 마이홈 매핑을 공개하며 보강 실패만으로 공고·공급행을 제거하지 않는다.
보강 성공 시 이전 연결의 일정·첨부·매칭된 공급행의 LH 금액을 교체하고 수동 입력은 보존한다.

## 품질 확인

`/admin/ingest`의 LH 품질 영역 또는 `GET /api/admin/ingest/quality/lh-announcements`에서 확인한다. 관리자 세션이 필요하다.

### 요청과 원천

| 지표 | 기준 |
|---|---|
| 공급·상세 요청 성공률 | 최근 수집 실행의 성공 요청 / (성공 요청 + 실제 요청 실패) |
| 원천 확보 | 현재 일반 수집 대상 중 현재 조회 조건의 성공 수집 시각이 있는 요청 수 |
| 원천 보존 | 빈 공급 응답·기존 행 감소로 교체를 막은 현재 실패 요청 수 |

요청 성공률은 재시도 호출 수나 합친 중복 요청을 세지 않는다. 원천 선택 충돌은 별도로 표시하고 분모에서 제외한다.
`failedRequestCount`는 충돌을 포함하므로 실제 요청 실패는 `failedRequestCount - selectionFailedRequestCount`다. 충돌만 있어도 실행은 실패다.

원천 확보는 활성 마이홈 원천의 현재 회차에서 충돌 없이 결정한 요청을 센다. 동일 요청은 한 번만 세고 원천 없는 요청도 분모에 포함한다.
`collectedRequests`에는 과거 성공도 포함된다. 최신성이나 이번 실행의 성공률은 아니며 `latestCollectedAt`은 확보 시각의 최댓값이다.

### 제품 정보

삭제되지 않은 LH 제품 공고·공급행을 기준으로 확인한다.

| 지표 | 기준 |
|---|---|
| 단지·주택형 연결 | 공급행의 연결 여부와 `matching_failure_reason`별 미연결 수 |
| 금액 확보 | 숫자 보증금·월세 쌍을 가진 대상이 하나 이상 있는 공급행 |
| 일정 검토 | 공고별 접수 일정 확인 여부와 실제 확인 일정 수 |
| 금액 보존 | 기존 LH 숫자 금액을 유지한 제품 공급대상 수 |

금액 보존은 미제공·매칭 실패·매핑 및 보강 보류를 구분한다. 같은 대상은 한 번만 세고 과거 원천의 정상 금액은 제외한다.
롤백된 작업은 현재 원천의 실패 이력과 공급행으로 집계한다. 정상 숫자로 갱신되고 실패가 해결되면 집계에서 빠진다.

### 공고문 확인

LH 목록과 현재 마이홈 요청·성공 연결의 불일치, 최근 변경 50건의 PAN_ID는 조사 대상이다.
과거 회차에만 연결된 공고도 포함되므로 신규 공고나 확정된 정정 건수로 해석하지 않는다.
LH 목록에만 있는 공고의 제품 등록과 제목만으로 한 정정 관계 확정은 제공하지 않는다.

API의 접수 일시는 공고문과 다를 수 있다. 금액 미제공·접수 조건·정정 여부는 공식 공고문에서 확인한다. `공고문 참조`를 숫자로 세거나 없는 금액을 추정하지 않는다.
일정·정정 정보는 [관리자 데이터 관리](ADMIN_DATA.md#수정삭제)에서 수정한다.

## 복구

### 연결·원천 실패

| 실패 사유 | 확인 |
|---|---|
| `LH_COLLECTION_REQUEST_UNSUPPORTED` | 현재 URL·공급유형 |
| `LH_COLLECTION_LINK_NOT_FOUND` / `LH_COLLECTION_LINK_MISMATCH` | 공급·상세 중 빠지거나 현재 요청과 다른 연결 |
| `LH_SUPPLY_SOURCE_NOT_FOUND` / `LH_DETAIL_SOURCE_NOT_FOUND` | 원천·성공 기록 저장 상태 |

1. 원인을 해결하고 공고 수집을 실행한다. 특정 공고·오래된 종료 공고는 아래 두 API로 재조회한다.
2. 수집 종료와 공급·상세의 현재 성공 연결을 확인한다.
3. 공고 정제를 실행하고 실패 기록·제품 결과를 확인한다.

관리자 세션·CSRF가 필요하며 `{pblancId}`는 마이홈 공고 ID다.

```text
POST /api/admin/ingest/lh/announcements/supplies/{pblancId}/refresh
POST /api/admin/ingest/lh/announcements/details/{pblancId}/refresh
```

정제만 재실행하면 외부 변경을 가져오지 않는다.

### 공급 감소 승인

#### 승인

1. 원본 공고문에서 철회·정정 범위, PAN_ID와 주택형을 확인한다.
2. 화면에서 보류 요청을 선택하고 마이홈 공고 ID, LH 공식 근거 URL과 확인 사유를 입력한다.
3. `POST /api/admin/ingest/lh/announcements/supplies/{pblancId}/verified-replacement`로 승인 후 재조회한다. 관리자 세션과 CSRF가 필요하다.

`proposedFingerprint`는 감소 응답의 식별값·면적·세대수·금액을 순서와 무관하게 해시한 값이다.
서버는 현재 연결·보류 실패·승인 지문을 확인하고, 같은 응답 지문일 때만 한 번 교체한다. 승인자·근거·사용 시각을 기록한다.
다른 감소 응답이나 재조회 실패는 기존 보호를 유지한다. 정상 응답이 오면 일반 재조회로 저장하고 미사용 승인은 폐기한다.

#### 반영 결과

승인된 빈 공급 응답은 같은 조회 조건의 빈 기준으로 유지된다. 수집 버전이 바뀌어도 적용되며, 정상 공급을 다시 확보하면 그 공급을 기준으로 삼는다.
제품 보강은 현재 마이홈 공급행의 기존 LH 금액을 제거한다. 이전 PAN에서 유지하던 금액도 제거하지만 과거 회차·관리자 입력 금액은 보존한다.

원천 반영 후 공고를 재정제하고 제품 결과를 확인한다. 실제 취소 공고는 관리자 수정·휴지통 경로에서 처리한다.

## 성능 확인

관리 포트의 `/actuator/prometheus`에서 확인한다. 단계는 `step`, 외부 조회·저장은 `source`로 구분한다.

| Micrometer 이름 | 확인할 값 |
|---|---|
| `ingest.pipeline.step` | 단계 전체 소요 시간 |
| `ingest.external.request` | 외부 조회·파싱의 시도별 시간 |
| `ingest.external.retry` | 재시도 진입 횟수 |
| `ingest.external.retry.wait` | 재시도 전 대기 시간 |
| `ingest.announcement.store` | 원천 교체 트랜잭션 시간 |
| `ingest.lh.circuit.state` | 정상 `0`, 차단 `1`, 복구 확인 중 `2` |
| `ingest.lh.circuit.rejected` | 외부 호출 전에 차단한 횟수 |

LH 저장 시간에는 성공 수집 기록의 저장도 포함된다. 연결·실패 이력 등 후처리 전체의 시간은 아니다.
호출 지연을 비교할 때 `rejected`는 제외한다. 병렬 요청의 시간 합계는 실제 단계 소요 시간과 다르다.

`event=ingest.pipeline.step.finished`의 `executionId`, `step`, `result`, `durationMs`로 실행 이력과 연결한다.
호출 제한이나 지연이 늘면 동시성을 4 또는 2로 낮추고, 같은 대상·실제 호출 수로 단계 시간을 비교한다.
