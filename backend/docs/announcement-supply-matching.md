# 공고 공급행 선택 적용 정제

## 처리 흐름

1. 자동 매칭 실패 화면에서 원천명·면적과 기존 단지·주택형을 비교한다.
2. 공급행별 선택을 화면에 모은다. 단지를 이미 찾았다면 검색은 펼치지 않는다.
3. **선택 적용·정제 실행**을 누르면 모든 공급행의 선택과 조회 토큰을 한 번에 보낸다.
4. 서버는 기존 원천으로 해당 공고만 정제한다. 외부 API를 다시 호출하지 않는다.
5. 최종 공고·공급행·LH 보강을 한 트랜잭션으로 저장한다. 실패하면 모두 롤백한다.

선택은 이번 요청에만 사용한다. 별도 매칭 규칙·일반 보완값·보완 이력 테이블은 사용하지 않는다.
최종 공급행의 단지·주택형 연결은 DB에 저장된다. 이후 자동 재정제에서 선택을 재사용하지 않으므로
다시 매칭 실패하거나 자동 매칭으로 연결이 바뀔 수 있다. 원천 이름·면적은 변경하지 않는다.

## API와 검증

- `GET /api/admin/ingest/announcement-supply-matches/{pblancId}`: 원천·자동 매칭 후보·조회 토큰.
- `POST /api/admin/ingest/announcement-supply-matches/{pblancId}/refine`: `{rows: [{rowIdentifier, token, complexId, housingTypeId}]}`.
- 모든 공급행을 빠짐없이 한 번씩 보낸다. 단지만 선택하면 그 단지 안에서 주택형을 자동 매칭한다.
- 원천 변경·공급행 추가/삭제·다른 공고의 행·중복 행·삭제 단지·다른 공급유형·타 단지 주택형은 거절한다.
- 기존 전역 실행 잠금, 관리자 인증과 CSRF 검증을 유지한다. 실행 중 입력·중복 실행은 막는다.
- 이미 존재하는 공고도 정제하지만 관리자 수정 공급행이나 삭제 공고는 임의로 덮어쓰지 않는다.
- 보존해야 하는 기존 LH 공급행이 있으면 최신 원천을 수집하도록 안내한다.
- 결과는 동기 응답으로 표시한다. 기존 실패 실행 기록은 과거 사실로 보존하며 성공으로 바꾸지 않는다.
  성공 시 해당 공고의 정제 실패 항목만 해결 처리한다.

## 배포와 제거

`V20261008_02`는 서버 적용 여부가 불명확하므로 체크섬과 파일을 유지한다.
후속 `V20261009_02__remove_ingest_corrections.sql`이 일반 보완 테이블 2개,
매칭 테이블(존재하는 경우)과 `housing_types.admin_correction`만 제거한다.
공고·단지·주택형·공급행·원천·실행 이력과 기존 관리자 변경 이력은 삭제하지 않는다.

1. 기존 앱과 진행 중 수집 작업을 중단하고 주 DB를 백업한다. 보완·매칭 규칙은 제거 후 자동 복구되지 않는다.
2. 복제본에서 새 마이그레이션·스키마 검증과 정제·기존 조회를 확인한다.
3. 새로운 백엔드와 프론트엔드를 함께 배포한다. 기존 보완 API·매칭 저장/해제 API는 더 이상 제공하지 않는다.
4. 이전 앱은 삭제된 저장소에 의존하므로 그대로 롤백하지 않는다. 필요하면 백업과 이전 앱을 함께 복구한다.
   Flyway 이력 삭제나 임의 repair로 우회하지 않는다.

이 기능을 나중에 제거할 때는 선택 UI·API와 정제 선택값 전달만 제거하면 된다. 새 테이블 정리는 필요 없다.
