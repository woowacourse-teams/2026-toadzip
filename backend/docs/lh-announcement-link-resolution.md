# LH 공고 연결 조회와 복구

## 조회 기준

- 매핑과 보강은 `LhAnnouncementLinkResolver`에서 같은 공고별 성공 연결을 조회한다.
- 공급·상세 연결이 모두 현재 수집 요청의 해시와 `panId`에 일치해야 정제를 진행한다.
- 매핑과 보강은 연결된 요청의 해시와 `panId`가 모두 일치하는 LH 원천 행만 읽는다.
  같은 `panId`를 다른 조회 조건에 사용해도 원천 행이 섞이거나 덮어써지지 않는다.
- 현재 요청은 수집의 `LhAnnouncementCollectionCandidateResolver`로 해석한다.
  같은 공고에 여러 마이홈 행이 있으면 수집은 조회 가능한 첫 행을 고르고,
  매핑·보강은 공급·상세의 성공 연결과 일치하는 행을 고른다.
  URL은 요청 일치 확인에만 쓰며, URL에서 얻은 `panId`로 원천을 직접 선택하지 않는다.
- LH 연결 확인에 실패하면 해당 공고의 매핑·보강 저장을 보류하고 기존 정제 데이터를 보존한다.
  최초 정제라면 LH 공고를 생성하지 않는다. LH 외 기관의 기본 매핑은 유지한다.
- 공급·상세 중 한쪽만 새 요청 수집을 마쳐도 두 단계 모두 보류한다.
- 수집 응답 전체의 파싱·원천 저장 후에만 해당 API의 연결을 갱신한다.
  공급·상세 응답의 `dsSch` 조회 조건이 요청 공고 ID·유형 코드와 일치해야 저장한다.
  조회 조건이 없거나 다르면 이전 원천·체크포인트·연결을 유지하고 실패로 기록한다.
  같은 조회 조건에서 이전 원천이 있었는데 상세·공급 응답이 비면 기존 원천을 보존하고 실패로 기록한다.
  이전 원천이 없는 최초 빈 응답은 허용하며, 마이홈 데이터로 제품 공고를 구성할 수 있다.
  체크포인트·공고 연결·실패 기록 해결은 함께 커밋한다. 수집 실패 시 이전 연결을 보존한다.
  성공 체크포인트를 재사용한 공고도 자신의 연결을 기록한다.

새 LH 연결의 보강이 성공하면 해당 공고의 이전 성공 연결에서 만든 일정·첨부를 정리한다.
금액은 주택형 매칭이 성공한 공급행의 이전 LH 보강 대상만 교체한다. 매칭 실패 시 이전 금액을
보존하며 복구 후 교체한다. 수동 입력·공고·이전 원천 데이터는 보존한다.
서로 다른 LH 공급행이 하나의 제품 공급행에 연결되면 마지막 행으로 금액을 덮지 않고
해당 공고의 보강을 보류한다.

## LH 목록 기반 재조회

`announcement-collection`은 **마이홈 공고 → LH 공고 목록 → LH 공급 → LH 상세** 순서다.
마이홈을 제품 공고의 기준으로 유지한다. LH 목록에 없는 마이홈 공고도 기존 URL·공급유형으로 수집한다.
LH 목록에만 있는 공고는 이 변경에서 제품 공고로 추가하지 않는다.

목록은 [LH 공고목록 API](https://www.data.go.kr/data/15058530/openapi.do)에 `PAGE`·`PG_SZ=500`으로
조회한다. 공고 유형과 날짜를 제한하지 않으며 API가 반환한 기본 검색 기간 안에서 전체 페이지를 읽는다.
2026-09-25 응답의 기본 기간은 2026-07-25~2026-09-25였다. 문서의 날짜 조건이 실응답에서
적용되지 않아 날짜 기반 증분 수집에는 의존하지 않는다. 모든 과거 공고를 조회한다는 의미는 아니다.

- 페이지 번호·전체 건수·순번·검색 기간·필수 식별자·중복을 검증한 후 목록 전체를 한 트랜잭션에 저장한다.
  빈 목록에는 `ALL_CNT` 검증 근거가 없어 실패로 처리한다. 불완전한 목록은 이전 목록을 덮어쓰지 않는다.
  현재 기간에서 빠진 과거 원천도 삭제하지 않고 현재 목록 후보에서 제외한다.
- `(PAN_ID, CCR_CNNT_SYS_DS_CD, UPP_AIS_TP_CD, AIS_TP_CD)`로 유일하게 연결되는 목록의
  `SPL_INF_TP_CD`를 사용한다. 일치하는 행이 없거나 모호하면 마이홈의 기존 해석을 유지한다.
- 이름·상태·날짜·URL·조회 코드가 바뀌면 마지막 성공 시각과 목록 변경 시각을 비교해
  TTL 만료 전에도 공급·상세를 재조회한다. 응답 시각·페이지 순번·전체 건수는 변경 판정에서 제외한다.
- 마이홈 수집 이후 6시간 이내 관찰된 목록에 연결되고 접수 종료일까지 3일 이상 남았으면
  공급·상세의 정기 재조회 주기는 24시간이다. 기본값은 `LH_ANNOUNCEMENT_UNCHANGED_REFRESH_TTL=PT24H`다.
- 목록이 없거나 오래됐거나 마감까지 이틀 이내이면 기존 6시간 주기를 유지한다.
  종료일 누락·해석 실패도 6시간, 최근 30일 내 종료 공고는 24시간, 더 오래된 종료 공고는 제외한다.
- 목록이 같아도 상세·금액의 불변을 보장할 수 없다. 24시간 만료 후 **다음 정기 실행**에 전체 확인하며,
  6시간 스케줄의 실행 시각·지연에 따라 실제 간격은 24시간을 넘을 수 있다. 마감 근접 공고는 6시간으로 복귀한다.
  원문을 확인해 즉시 갱신해야 하면 기존 공급·상세 강제 갱신 API를 사용한다.
- 건너뛴 조회는 마지막 성공 시각을 연장하지 않는다. 변경 후 실패해도 이전 원천·성공 시각을 보존해 다음 실행에서 재시도한다.

`V20260925_01`은 목록 테이블과 새 파이프라인 단계·원천 enum의 DB 허용값을 추가한다.
배포는 실행 중인 수집을 마친 뒤 신버전만 기동한다. 기존 버전은 새 단계 enum이 기록된 실행을 읽을 수 없어
단순 바이너리 롤백은 피한다. 우선 재조회 정책을 되돌릴 때는 위 TTL을 `PT6H`로 설정해 재기동한다.
현재 수집 버전 6 체크포인트도 최초 목록 관찰보다 오래됐으면 한 차례 재조회한다.

## 기존 LH 공고의 재정제

이미 LH 보강을 마친 공고는 마이홈 재매핑과 LH 보강을 공고 단위의 한 트랜잭션에서 반영한다.
보강 입력이 잘못됐거나 공급행 매칭에 실패하면 매핑 변경까지 롤백하고 매핑 실패를 기록한다.
주택형이 바뀐 공급행에 새 임대금액이 없으면 이전 주택형의 금액을 이어 붙이지 않고
공고 전체의 변경을 보류한다. 금액이 없는 같은 주택형의 기존 값 보존 정책은 유지한다.
매핑 실패가 남아 있으면 뒤따르는 독립 보강 단계도 기존 LH 공고를 수정하지 않는다.
두 단계의 실행 잠금은 같은 DB 키를 사용해 서로 다른 실행이 겹치지 않게 한다.
정상 원천으로 매핑을 다시 완료하면 실패 기록이 해결되고 새 주택형·금액을 함께 반영한다.

최초 LH 공고는 공급·상세의 현재 성공 연결을 확인한 뒤 마이홈 매핑 결과를 공개하고
LH 보강을 시도한다. 보강에 실패해도 확인된 공고·공급행은 유지한다. 처음부터 임대금액이
없으면 금액 대상은 빈 목록으로 응답하며 이전 금액을 끌어오지 않는다. 따라서 최초 공고의
보강 실패만을 이유로 공고 전체를 숨기지 않는다. 이미 LH 보강을 마친 공고의 재정제는
기존 금액과 새 주택형이 섞이지 않도록 위 트랜잭션 경계를 적용한다.

## 실패 사유

| 사유 | 의미와 조치 |
|---|---|
| `LH_COLLECTION_REQUEST_UNSUPPORTED` | 현재 URL·공급유형으로 수집 요청을 확정할 수 없음. 수집 실패·건너뜀 기록과 원천을 확인 |
| `LH_COLLECTION_LINK_NOT_FOUND` | 공급 또는 상세의 성공 연결이 없음. 공고 수집 재실행 |
| `LH_COLLECTION_LINK_MISMATCH` | 현재 요청과 이전 성공 연결이 다름. 새 요청 수집 실패 원인 해결 후 재실행 |
| `LH_SUPPLY_SOURCE_NOT_FOUND` | 성공 연결은 있지만 공급 원천이 없음. 원천 저장 상태와 성공 체크포인트 확인 |
| `LH_DETAIL_SOURCE_NOT_FOUND` | 성공 연결은 있지만 상세 원천이 없음. 원천 저장 상태와 성공 체크포인트 확인 |

상세 원천 누락은 보강에서 기록한다. 연결 실패의 상세 메시지에는 공급·상세 구분을 남긴다.
기존 공고가 없거나 공급유형이 지원되지 않으면 보강의 기존 선행 검증 사유가 기록될 수 있다.
`PAN_ID_NOT_FOUND`는 기존 실패 이력 호환을 위해 enum에 남기지만 새 연결 조회에서는 사용하지 않는다.

## 요청별 원천 식별 전환

`V20260923_01__lh_announcement_source_request_hash.sql`은 두 LH 원천 테이블에
`request_hash`를 추가하고 `pan_id` 중심 고유 제약을 요청 해시를 포함한 제약으로 교체한다.
기존 원천 행은 어떤 조회 조건에서 왔는지 확정할 수 없어 해시 없이 보존한다.
새 코드는 해시가 없는 원천 행을 읽지 않는다. 현재 수집 요청 버전 6의 재수집이 필요하다.
버전 4는 `060` 공급정보의 `dsList02` 파싱과 공급 세대수 보강 수정을 반영했다.
버전 5는 LH 공고 공급·상세 API에서 근거 없는 `PG_SZ`·`PAGE`를 제거하고 단일 응답을
100행 상한 없이 처리한다. 버전 4의 성공 체크포인트를 재사용하지 않는다.
버전 6은 구조화된 접수일·당첨일과 060 상세 필드를 추가로 보존한다. 버전 4·5의 성공 캐시는 재사용하지 않는다.
버전 6 수집이 성공하면 같은 조회 조건의 버전 4 실패 기록(페이지별 기록 포함)과 버전 5 실패 기록을 해결한다.
이전 버전의 성공 체크포인트와 연결은 새 요청으로 간주되며, 공급·상세 수집이 모두 성공하기 전에는
기존 정제 데이터를 유지한다. 정기 수집에서 제외된 공고는 아래 강제 갱신 경로로 두 원천을 다시 조회한다.
재수집 전에는 기존 정제 데이터를 보존하지만 새 원천으로 보강할 수 없다.

1. 구버전 애플리케이션과 수집 작업을 중지하고 primary DB의 백업·복구 경로를 확인한다.
   제약 교체 중 두 원천 테이블에 잠금이 걸리므로 적용 시간도 점검한다.
2. 마이그레이션을 적용하고 신버전만 기동한다. 구버전은 해시가 있는 행도 `panId`만으로
   읽으므로 두 버전을 동시에 실행하거나 신버전 수집 후 구버전으로 단순 롤백하지 않는다.
3. `announcement-collection`을 실행해 공급·상세를 다시 수집한다. 종료 후 30일이 지난
   공고는 정기 수집에서 제외되므로, 마이홈 원천의 종료일과 공급·상세 성공 연결을 대조해
   누락된 공고 ID를 구한다. 각 ID에
   `POST /api/admin/ingest/lh/announcements/details/{pblancId}/refresh`와
   `POST /api/admin/ingest/lh/announcements/supplies/{pblancId}/refresh`를 실행한다.
   두 요청의 성공 연결과 요청 해시가 있는 원천 행을 확인한 후
   `announcement-refinement`를 실행하고 실패 기록을 확인한다.

## 로컬 데이터 마이그레이션 리허설 (2026-09-23)

실행 중인 로컬 Docker DB의 마이홈·LH 원천·체크포인트·연결 테이블 다섯 개만
읽기 전용으로 덤프해 임시 PostgreSQL에 복원했다. 사용자 계정 테이블은 복제하지 않았다.

- 마이홈 원천 317행 중 LH 원천은 299행·132공고였다. 86공고는 접수 종료일이
  당일 이후, 46공고는 최근 30일 이내 종료, 30일 초과 종료 공고는 0건이었다.
- 상세 1,924행·공급 559행과 각 132개의 성공 연결이 있었다. 연결은 모두 요청 버전 2였고
  버전 3 연결은 없었다. 이 로컬 데이터는 전부 정기 재수집 대상이지만 외부 API 성공은 별도 확인이 필요하다.
- 복제본에 `V20260923_01` SQL을 적용했다. 기존 상세·공급 행 수와 해시 없는 상태가 보존됐고,
  새 고유 제약 아래 동일 `panId`·행 순서에 서로 다른 요청 해시 두 개를 삽입할 수 있었다.
  시험 삽입은 롤백했다. 원본 DB에는 스키마 변경이나 쓰기를 하지 않았다.
- 이는 로컬 데이터와 마이그레이션 SQL의 검증이다. 실제 외부 API를 통한 DB 재수집과 운영 DB 데이터
  분포는 검증하지 않았으며, 배포 대상 DB에서 위 연결·종료일 집계를 다시 확인해야 한다.

## LH 공급 API 실호출 검증 (2026-09-24)

서비스키를 사용해 LH 공급 API를 읽기 전용으로 호출했다. 응답은 최상위 배열이고 `resHeader.SS_CODE`는
두 요청 모두 `Y`였다.

- 10년임대 공고 `0000061177`, 공급유형 `060`: `dsList02`에 26행이 있었다. 첫 행에는
  `BZDT_NM`, `HTY_NM`, `RSDN_DDO_AR`, `SPL_AR`, `TOT_HSH_CNT`, `SIL_HSH_CNT`,
  `LS_GMY`, `MM_RFE`가 모두 있었다. `dsList01`은 0행이었다.
- 통합공공임대 공고 `2015122300020531`, 공급유형 `062`: `dsList01`에 2행이 있었고
  `SBD_LGO_NM`, `HTY_NNA`, `DDO_AR`, `SPL_AR`, `HSH_CNT`, `NOW_HSH_CNT`,
  `LS_GMY`, `RFE`가 모두 있었다.

두 응답의 행에는 동일한 단지·주택형·전용면적·공급면적 조합이 중복되지 않았다. 따라서 이 실호출은
유형별 dataset과 필드 매핑을 확인하지만 중복 행 교체 방어의 실제 발생 여부는 증명하지 않는다.
API 응답은 DB에 저장하지 않았다.

## LH 공고 API 페이지 조건 검증 (2026-09-24)

[LH 공급정보 공식 요청표](https://www.data.go.kr/data/15056765/openapi.do)에는 `PG_SZ`와 `PAGE`가 없다.
서비스키로 공식 마이홈 목록에서 공고 조회 조건을 얻은 뒤, LH 공급·상세 API를 읽기 전용으로
`PG_SZ=1`, `PAGE=1`과 `PAGE=2`로 호출했다. 두 페이지의 실제 데이터는 아래 표본에서 같았다.
상세 응답의 `dsSch.PAGE`처럼 요청 번호를 반영하는 메타데이터는 비교에서 제외했다.

| 공급유형 | 공고 ID | 공급행 수 | 결과 |
|---|---|---:|---|
| `060` | `0000061177` | 26 | 1·2페이지의 `dsList02` 동일 |
| `061` | `2015122300019790` | 1 | 1·2페이지의 `dsList01` 동일 |
| `062` | `2015122300020531` | 2 | 1·2페이지의 `dsList01` 동일 |
| `063` | `2015122300020806` | 8 | 1·2페이지의 `dsList01` 동일 |

네 공고의 상세 데이터셋도 페이지 번호와 관계없이 동일했다. 특히 26행·8행 응답이
`PG_SZ=1`에도 줄지 않아 이 API에서 해당 페이지 조건을 적용한다는 가정은 반증됐다.
네 유형의 공급·상세 실응답 모두 `dsSch`에 `PAN_ID`, `CCR_CNNT_SYS_DS_CD`,
`UPP_AIS_TP_CD`, `AIS_TP_CD`, `SPL_INF_TP_CD`가 있었고 요청값과 일치했다.
공식 마이홈 목록의 현재 7개 임대유형을 조회해 유효한 LH 요청 83개를 추가 확인했다.
공급 API 호출 83개 모두 성공했고 유형별 최대 행 수는 `060` 26행, `061` 2행,
`062` 20행, `063` 9행이었다. 이 표본에서도 100행 이상 응답은 없었다.
따라서 현재 지원하는 네 유형은 공식 요청표의 조건만 보내고 공급·상세 응답 전체를 한 번에
파싱한 뒤 원천과 성공 기록을 교체한다. 응답의 실제 100·101행 사례는 찾지 못했다.
API가 전체 건수를 제공하지 않아 최초 응답의 완전성은 증명할 수 없다. 기존 원천보다
행이 줄면 원천 교체를 거절하는 검사는 유지한다. 호출 응답과 서비스키는 DB나 문서에 저장하지 않았다.

## 기존 데이터 전환

1. 애플리케이션 배포 전에 연결 테이블 SQL과 아래 실패 사유 확장 SQL을 적용한다.
   연결 테이블 배포는 [원천 수명주기](announcement-source-lifecycle.md)를 따른다.
2. `POST /api/admin/ingest/pipelines/announcement-collection`을 실행한다.
   수집 대상인 공고에서 현재 버전의 성공 체크포인트가 있으면 외부 재호출 없이 누락된
   공고별 연결을 복구하고, 없으면 실제 수집한다. 오래전에 종료된 공고는 위 강제 갱신이 필요하다.
3. 공급·상세 수집 결과를 확인한 뒤 `announcement-refinement`를 실행하고 실패 기록을 확인한다.

[Flyway 도입 절차](flyway-adoption.md)의 통합 `V20260922_01`이 실패 사유 제약을 확장한다.

이 SQL은 Hibernate가 생성하는 두 실패 테이블의 `*_reason_check` 허용값을 확장한다.
기존 실패 행과 기존 enum 값은 보존한다. 사용자 지정 제약 이름을 쓰는 환경은 적용 전 확인한다.
구버전 코드로 롤백할 때는 신규 사유를 읽을 수 없으므로 신규 실패 이력의 호환 조치가 필요하다.

## 불완전한 공급 응답의 원천 보존

- 동일 `panId`와 요청 해시에 공급 원천이 있으면 전체 0행 결과로 교체하지 않는다.
  저장 트랜잭션에서 삭제 전에 거절하고 수집 실패를 기록하며, 원천·성공 체크포인트·연결을 보존한다.
- 비어 있지 않아도 기존 단지명·주택형·전용면적·공급면적 조합별 행 수가 줄면 전체 교체를 거절한다.
  중복 행도 개수로 비교하며, 순서 변경과 행 추가는 허용한다. 식별 조합이 유일한 행의
  금액·세대수 변경도 허용한다. 면적의 숫자 표기는 정규화한다.
- 같은 조합의 기존 행들이 서로 다른 세대수·금액 값을 가지면 값별 행 수도 보존해야 한다.
  모두 같은 값인 중복 행은 행 수를 유지하면서 함께 값을 갱신할 수 있다. 서로 다른 값의 행을
  구분할 추가 식별값이 없어 어느 행이 바뀌었는지 알 수 없는 변경은 자동 교체를 보류한다.
- 현재 요청 원천을 우선 비교한다. 없으면 실제 조회 조건은 같고 수집 버전만 다른 최신 성공 원천과 비교한다.
  조회 조건이 다른 원천과 요청 해시가 없는 원천은 비교에 섞지 않고 보존한다.
- 비교할 기존 원천이 없는 최초 빈 결과는 마이홈 공급행과 LH 상세를 사용하는 기존 동작을 유지한다.
- 정상 재수집은 실패를 해결한다. 실제 공급 철회, 이름·면적 정정, 구버전 식별값 누락 행의 보정은
  자동 교체를 보류한다. 원문과 보존된 원천을 확인한 별도 데이터 정정이 필요하며 수집 재시도로 우회하지 않는다.
- API 명세에는 전체 행 수가 없어 최초 수집의 완전성이나 처음부터 누락된 신규 행은 증명할 수 없다.
  이 검사는 이미 저장한 행의 누락으로 인한 삭제를 막는다. 반복되는 부분 응답도 성공으로 승격하지 않는다.

## Fallback 종료와 운영 한계

- 정제 단계의 과거 체크포인트 fallback은 #145에서 제거한다. 체크포인트 자체는 수집 중복 방지에 유지한다.
- 연결 없는 공고를 임의의 과거 체크포인트로 연결하지 않는다. 위 수집 실행으로 연결을 복구한다.
- 정기 수집 대상의 성공 체크포인트는 설정된 주기에 따라 다시 조회한다. 종료 후 30일이 지난
  공고는 정기 수집에서 제외된다. 원천 행이 없는데 성공 체크포인트만 있으면 해당 공고의
  강제 갱신으로 복구하고, 원천 누락 원인을 확인한다.
- 같은 요청의 일정·금액·첨부를 다시 가져오는 관리자 강제 갱신 경로는 위의 상세·공급 refresh API다.
  두 원천의 수집 성공을 확인한 뒤 재정제하며, 조회 결과를 근거로 한 철회·정정 승인 정책은 별도 과제다.

정확성 실응답 대조와 데이터 제약은 [정확성 검증·후속 정책](lh-announcement-correctness-audit.md)을 따른다.
