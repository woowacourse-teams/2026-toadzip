# Persistence

## 모델 경계

- Domain 객체와 JPA Entity는 같은 클래스를 기본값으로 삼는다.
- JPA 기본 생성자는 `protected`로 두고 정상 생성은 정적 팩토리만 사용한다.
- Entity 안에 상태와 불변식을 두되 Repository·HTTP·JSON 책임은 넣지 않는다.
- 지연 로딩 객체를 Web으로 전달하거나 Entity를 API 응답으로 반환하지 않는다.
- 시간대, 좌표, 금액의 저장 단위를 스키마와 코드에서 일치시킨다.

## 분리하는 시점

다음 중 하나가 실제 문제로 확인될 때 Domain과 JPA Entity 분리를 검토한다.

- 레거시 스키마나 JPA 프록시 제약이 도메인 행위를 계속 왜곡한다.
- 저장 모델과 도메인 모델의 수명·구조가 크게 달라진다.
- 한 도메인을 서로 다른 저장 방식으로 독립적으로 운영해야 한다.
- 변환 비용보다 분리로 얻는 테스트성·독립성이 크다는 근거가 있다.

분리할 때는 PR에 문제, 대안, 변환 책임과 테스트 범위를 기록한다.

## 트랜잭션

| 대상 | 원칙 |
|---|---|
| 쓰기 유스케이스 | Service 경계에서 원자성 보장 |
| 읽기 유스케이스 | 필요 범위만 읽기 전용으로 선언 |
| 외부 API | DB 트랜잭션 안에서 장시간 대기하지 않음 |
| 비동기 부수 효과 | 커밋 성공과 전달 보장을 분리해 검토 |

- 기능을 가로지르는 공유 트랜잭션은 하나의 유스케이스에서만 허용한다.
- 재시도 가능한 작업은 멱등성과 중복 처리 정책을 먼저 정의한다.
- 동시 갱신은 낙관·비관 잠금 중 실제 충돌 모델에 맞는 전략을 고른다.

## 쿼리

- 목록 조회는 정렬 기준과 동률 순서를 고정한다.
- N+1, 전체 테이블 조회, 무제한 결과를 통합 테스트로 확인한다.
- 인덱스는 실제 조회·정렬 조건과 실행 계획 근거로 추가한다.
- Domain 규칙을 SQL 조건에만 숨기지 않는다.
- 민감정보를 검색 조건이나 쿼리 로그에 노출하지 않는다.

## 마이그레이션

1. 스키마와 애플리케이션의 배포 순서를 정한다.
2. 기존 데이터의 backfill과 검증 방법을 준비한다.
3. 이전 버전과의 호환 구간을 명시한다.
4. 롤백 가능 여부와 복구 절차를 기록한다.
5. 운영 데이터 변경은 사전 승인을 받는다.

## 검증

- Repository 계약은 실제 DB에 가까운 통합 테스트로 검증한다.
- 제약조건, 변환, 쿼리 결과, 동시성 실패를 포함한다.
- 생성된 스키마 문서는 코드와 다르면 자동 생성 결과를 우선한다.
