# 개인정보 저장

## 기존 자료

개인정보 기능의 도입, 고지 기록, 선택 관리, 보유기간 배치 때문에 기존 테이블의 컬럼·제약·인덱스·
트리거·자료를 변경하지 않는다. 별도 신규 영속 테이블을 사용한다. SQL TEMP TABLE이 아니다.
기존 자료의 고지 버전·동의를 추정하거나 개인정보 보유기한을 소급 채우지 않는다.
회원 이메일 수집·저장과 관리자 조회·검색 목적은 유지한다.

신규 테이블에서 기존 테이블로 외래키를 만들지 않는다. PostgreSQL은 참조 대상에도 내부 트리거를
추가하므로 단순히 신규 테이블에 FK를 선언하는 것만으로 기존 스키마 불변이 보장되지 않는다.
회원·대상 ID는 논리 참조이고, 회원 존재 여부 확인과 잠금은 읽기 연산이다.
신규 동의 이력에서 신규 동의로 향하는 내부 FK만 허용한다.

## 테이블

| 테이블 | 소유 정보 | 수명주기 |
| --- | --- | --- |
| `privacy_analytics_consents` | 계정/브라우저의 선택·revision·현재 고지 | 비회원 만료 정책, 회원 삭제 후 고아 정리 |
| `privacy_analytics_consent_events` | 선택 증빙·중복 명령 영수증 | 효력 상실 후 파기, 고아 정리 |
| `privacy_registration_notices` | 새 회원 가입 시 안내 버전·시각 | 계정 존재 중 보존, 사라진 회원의 고아 정리 |
| `privacy_notification_states` | 회원별 설정 revision | 계정 존재 중 보존, 고아 정리 |
| `privacy_notification_notices` | 신청 시 고지·신청일·기존 업무 만료일 사본 | 취소·만료 후 파기, 고아 정리 |
| `privacy_notification_receipts` | 새 신청·취소 명령 처리 결과 | 발생 시각 기준 파기, 고아 정리 |
| `privacy_notification_events` | 유효한 분석 동의 후의 새 행동 이벤트 | 발생 시각 기준 파기 |
| `privacy_flyway_schema_history` | 이 모듈만의 스키마 적용 이력 | 사용자 자료가 아니며 임의 삭제·repair 금지 |

숫자 보유기간과 운영 책임은 [운영 정책](../../../docs/privacy-policy.md)을 따른다.
동의·알림·가입 고지 배치는 신규 자료만 정리한다. 고아 자료는 회원 부재를 다시 확인한
다음 성공한 배치에서 파기한다. 시스템 중단·잠금·오류 시 지연되므로 완료 시각과 미처리 건수를
감시한다. 회원의 거부·철회·revision은 계정이 존재하는 동안 유지해 이전 허용이 부활하지 않게 한다.
기존 회원·알림·이메일·비회원 요청·과거 행동 기록은 이 배치의 대상이 아니다.

## 가입·알림 연동

- `SocialUserService`: 기존 회원 생성과 이메일 갱신을 유지한다. 새 회원이며 전달된 정책 버전의 보관 원문이 확인될 때만
  `UserRegistrationNoticeRepository.record`로 링크 버전 메타를 별도 저장한다. 버전 누락은 로그인을 막지 않는다.
  `User`에는 이번 기능용 추가 필드나 동의 모델 참조가 없다. 기록을 시도한 경우 저장 실패는 가입과 함께 롤백한다.
- `NotificationSettingsService`: `NotificationSubscriptionRepository`의 기존 업무 신청·취소 연산과
  `PrivacyNotificationRepository`의 메타 저장을 하나의 트랜잭션으로 처리한다. 메타 저장 실패 시
  해당 사용자 명령 전체를 롤백한다. 기존 구독의 상태·만료일이 업무 원본이고 메타는 사본이다.
- `NotificationInterestService`: 유효 동의를 확인하고 `PrivacyNotificationEventRepository`에 새
  행동 기록을 저장한다. 알림 업무 영수증과 행동 식별자를 연결하지 않는다.
- `AnnouncementViewService`: 유효 동의 확인 후 기존 공고 조회수 집계 기능을 호출한다. 기존 집계
  테이블은 개인정보 메타 테이블이 아니며 새 파기 배치가 변경·삭제하지 않는다.
- `AnalyticsConsentService`, `PrivacyController`, 프론트 `ConsentStore`: 기존 API 계약으로
  미동의·거부·철회·만료에는 차단하고 현재 범위의 유효 동의 후 SDK와 자체 수집을 허용한다.

직접적인 사용자 신청·취소·가입·이메일 갱신과 동의 후 조회수 집계는 기존 기능의 정상 업무 연산이다.
이 연산에 수반되는 원래 컬럼 변경을 개인정보 메타 기록·마이그레이션·배치로 수행하지 않는다.
기존 알림에 신규 고지 메타가 없으면 `null`로 응답하며 과거에 새 고지를 읽었다고 표시하지 않는다.
개인정보 모듈은 기존 회원·알림을 삭제하는 관리자 API를 제공하지 않는다.

## 변경과 기능 제거

1. 제거 중인 서버·화면이 신규 자료를 쓰지 않도록 버전을 함께 전환한다. 동의 기능을 제거하면서
   GA·PostHog 수집을 무조건 활성화하지 않는다. 분석 기능도 종료하거나 별도로 승인된 동의 수단으로 교체한다.
2. `privacy`의 API·동의 저장소·고지 카탈로그·배치·엔티티·마이그레이션 설정과 프론트 개인정보 화면·
   `ConsentStore`·SDK 연동을 정리한다. OAuth 안내 버전 기록 호출과 관련 DTO, 신규 알림 설정 API의
   개인정보 어댑터도 제거하거나 기존 업무 API에 연결한다. revision·고지 입력을 제거하기 전에
   기존 클라이언트와의 호환성을 확인한다.
3. 회원 생성·이메일 저장, 원래 알림 구독 저장소·스키마, 기존 공고 조회수 저장소는 유지한다.
   고지·revision은 신규 테이블에만 있으므로 기존 엔티티의 컬럼 제거 작업이 필요 없다.
4. 종료 후 필요한 증빙 보존·파기를 확인하고 별도 승인된 절차로 신규 테이블만 정리한다.
   신규 테이블 제거는 사용자 자료 삭제이므로 자동 실행하거나 `DROP ... CASCADE`로 처리하지 않는다.
   기존 테이블과 기존 Flyway 이력에는 제거 DDL이나 수정이 필요 없다.
5. 이미 폐기된 설계가 적용된 DB는 이 제거 절차의 대상이 아니다. 원본 DB·이력을 보존하고
   [배포 문서](../operations/PRIVACY.md)의 별도 복구 절차를 먼저 확정한다.

제거 작업에서 확인할 코드 범위는 다음과 같다. 기존 업무 저장소와 메타 어댑터를 구분한다.

| 범위 | 정리 대상 |
| --- | --- |
| 공통 동의·안내 | `privacy` API·엔티티·저장소·고지 카탈로그·배치·지표·관련 테스트 |
| 가입 고지 | `SocialUserService`의 기록 호출·저장소 의존, OAuth의 선택적 버전 메타, `UserRegistrationNotice`·저장소·배치 |
| 알림 메타 | `PrivacyNotificationRepository`, `PrivacyNotificationEventRepository`, `PrivacyNotificationRetentionRepository/Service`, `PrivacyNotificationState/Notice/Receipt/Event`, 전용 응답 메타·호출부·테스트 |
| 프론트 | 개인정보 화면·`ConsentStore`·분석 게이트·SDK 연결, 알림 고지·revision UI 계약 |
| 시작·배포 | `PrivacyMigrationConfiguration`, 전용 SQL·스키마 점검 연결. 신규 자료 정리 완료 후 전용 이력도 승인된 범위에서 처리 |

## 검증

마이그레이션 전후 모든 기존 테이블의 컬럼·제약·인덱스·트리거 정의와 전체 행 값을 비교한다.
배치·고지 기록·동의 변경은 기존 자료를 그대로 유지해야 한다. 사용자 업무 요청 테스트는 해당
명령으로 의도한 기존 상태 변경만 허용하며 중복 요청·경합·만료·실패 롤백을 검증한다.
신규 테이블의 삭제/고아 정리와 모듈 제거 후에도 기존 자료의 조회·구조가 보존되는지 검증한다.
