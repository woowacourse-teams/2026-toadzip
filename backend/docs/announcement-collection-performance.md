# 공고 수집 성능과 계측

## 적용 범위

- 관리자 공고 파이프라인의 마이홈 페이지 크기는 500행이다. `totalCount`까지 계속 조회한다.
- LH 상세·공급은 각 API 수집 실행에서 서로 다른 공고를 기본 최대 8개씩 처리한다. 한 요청이 끝나면 빈 슬롯에 다음 요청을 투입한다.
- 같은 `panId`의 다른 조회 조건은 요청 해시별로 원천을 저장한다. 수집 묶음에서는 기존 순서를 유지해 이전 요청의 저장·체크포인트까지 기다린다.
- 동일 요청을 공유하는 마이홈 공고는 외부 호출을 합치고 각 공고의 연결을 기록한다.
- 호출 제한이나 저장 예외를 관찰하면 새 요청을 시작하지 않는다. 이미 시작한 공고는 완료·실패 처리하고 저장 예외는 원래 예외로 전파한다.
- 실행 잠금은 작업 종료까지 유지한다. 호출 제한 응답은 재시도하지 않는다.
- 공급과 상세 단계의 실행 순서는 유지한다. 목록·공급·상세의 실행 잠금을 공유해 단독 API·다른 인스턴스도 동시에 실행하지 않는다.
- 2026-09-17 성능 변경에서는 단지 수집 동작, 공개 응답, DB 스키마, 성공 체크포인트의 재수집 정책을 변경하지 않았다. 2026-09-23 LH 원천 식별 변경에서는 DB 스키마와 수집 버전이 변경됐다.
- 성공 캐시의 만료·변경 반영은 [#92](https://github.com/woowacourse-teams/2026-toadzip/issues/92)와 연결된다.
  2026-09-25에는 LH 목록 변경 감지와 24시간 재확인을 추가했다. 아래 실측과 제약을 따른다.

## 실측 표본 — 2026-09-17, 로컬에서 외부 API만 조회

마이홈 7개 공급유형을 10행·500행으로 각각 끝까지 읽었다. `(pblancId, houseSn)`의
중복 횟수와 전체 행 내용을 비교했으며 모두 일치했다. DB에는 저장하지 않았다.

| 공급유형 | 행 수 | 10행 호출 수 | 500행 호출 수 |
|---|---:|---:|---:|
| 영구임대 | 12 | 2 | 1 |
| 국민임대 | 194 | 20 | 1 |
| 50년임대 | 5 | 1 | 1 |
| 10년임대 | 17 | 2 | 1 |
| 5년임대 | 0 | 1 | 1 |
| 행복주택 | 13 | 2 | 1 |
| 통합공공임대 | 3 | 1 | 1 |
| 합계 | 244 | 29 | 7 |

조회 시간 합계는 17.821초 → 3.998초였다. 500은 공식 최대 허용값을 뜻하지 않는다.

LH는 마이홈에서 얻은 서로 다른 국민임대 공고 2건의 첫 페이지를 각 조건에서 한 번씩 조회했다.

| API | 순차 2건 | 동시 2건 | 비교 |
|---|---:|---:|---|
| 공급정보 | 4.924초 | 2.529초 | 응답 동일, 제한 오류 0건 |
| 상세정보 | 8.822초 | 2.452초 | 응답 동일, 제한 오류 0건 |

LH 응답 비교에서는 응답 생성 시각 `RS_DTTM`만 제외했다. 이번 검증은 마이홈 37회,
LH 8회 호출을 사용했다. 단회 표본이며 워밍업·시간대 차이가 있어 전체 실행 성능이나
공식 허용 동시성을 보장하지 않는다. 실제 파이프라인의 DB 저장 포함 전후 시간은 미측정이다.

## 2026-09-25 로컬 확인과 개선

실제 인증키로 마이홈 국민임대 목록 1페이지와 그 안의 LH 공고 1건에 상세·공급을
각 1회 읽기 전용 조회했다. 마이홈 161행은 0.75초, LH 상세는 2.35초, 공급은
2.27초였다. LH 응답은 상세 약 5KB, 공급 약 1KB였다. 단회 표본이며 DB 작업과
전체 파이프라인 실행 시간은 포함하지 않는다. 인증키와 요청 URL은 기록하지 않았다.

두 건씩 완료를 기다리던 LH 수집은 완료된 슬롯을 즉시 재사용한다. 같은 `panId`의
서로 다른 조건은 저장·체크포인트 순서를 유지한다. 공고 보강은 공급행별 대상 조회를
공고당 한 번의 묶음 조회로 바꿨다. LH 세대수 보강은 단지 목록을 공급유형과
총세대수로 한 번 색인한다. 이 변경들의 운영 시간 단축량과 전체 SQL 수는 아직 미측정이다.

같은 날 현재 마이홈 7개 유형을 다시 읽은 결과는 총 211행, 그중 LH 210행이었다.
기존 재수집 기준에 맞는 원천 공고는 87건이고, 중복 조회 조건을 합치면 LH API별
83건이다. 모두 6시간 갱신 그룹이었다. 따라서 체크포인트가 만료된 실행에는
공급·상세 합계 약 166회 호출이 예상된다. 실제 완료 호출 수는 성공·실패 및
체크포인트 상태에 따라 달라진다. 요청 버전 4→5 변경 시에는 이전 버전의 성공
체크포인트가 새 요청의 `isFresh` 판정에 포함되지 않아 첫 실행에서 재조회한다.

실제 LH 상세 8건을 같은 조회 조건으로 두 방식에서 각각 두 번 실행했다.
묶음 완료 대기는 9.87초·9.21초, 빈 슬롯 재사용은 9.20초·9.17초였다.
32건 모두 성공했고 요청별 시간은 2.16~2.76초였다. 순서·서버 상태가 달라지는
단회 교차 표본이므로 안정적인 개선율로 해석하지 않는다. 지연 편차가 작은 표본에서
슬롯 재사용 효과는 작았고 전체 실행에서는 요청 건수가 지배적일 가능성이 높다.

격리 PostgreSQL에서 동일 LH 공급 원천 100행을 교체할 때 기존 삭제는 SQL 202회
(100행 개별 삭제·100행 개별 삽입 포함), 173ms였다. 조건별 묶음 삭제로 바꾼 뒤
SQL 102회(묶음 삭제 1회·개별 삽입 100회 포함), 112ms였다. 각각 한 번 측정한
값이며 전체 파이프라인 DB 비용을 뜻하지 않는다.

## LH 목록을 추가한 전체 수집 실측 — 2026-09-25

실제 인증키·실제 수집 서비스·격리 PostgreSQL로 **마이홈 → LH 목록 → LH 공급 → LH 상세**를
실행했다. 초기 DB는 비어 있었다. 이어 애플리케이션의 시계만 6시간 1초 진행시킨 뒤 같은 네 단계를
다시 실행했다. 두 번째에도 마이홈·LH 목록·재조회 대상의 공급·상세를 실제 API에서 읽고 DB에 저장했다.
정제 단계·서비스 기동 시간은 제외했다. 운영 DB에는 쓰지 않았다.

| 단계 | 최초 수집 호출 / 시간 | 6시간 뒤 재수집 호출 / 시간 |
|---|---:|---:|
| 마이홈 전체 공고 211행 | 7회 / 3.684초 | 7회 / 3.469초 |
| LH 목록 581건 | 2회 / 2.791초 | 2회 / 2.507초 |
| LH 공급 | 83회 / 81.631초 | 11회 / 11.592초 |
| LH 상세 | 83회 / 78.477초 | 11회 / 10.743초 |
| 합계 | 175회 / **166.587초** | 31회 / **28.314초** |

두 실행 모두 외부 호출 실패·호출 제한 0건이었다. 초기 공급 원천 402행·상세 원천 1,264행을 저장했다.
각 LH 단계의 건너뜀 1건은 LH가 아닌 마이홈 공고다. 두 번째 실행의 원천 저장 수는 재조회한
공급 39행·상세 146행이며, 건너뛴 공고의 기존 원천은 보존했다.

마이홈의 서로 다른 LH 요청 83건 중 **72건은 목록과 연결되고 11건은 목록에 없었다**.
연결된 72건은 이 표본에서 모두 접수 종료까지 3일 이상 남아 24시간 주기를 적용했다.
따라서 6시간 뒤 상세·공급 호출은 **166회 → 22회(86.7% 감소)**, 수집 시간은
**166.6초 → 28.3초(83.0% 감소)**였다. 공급도 공고별 요청이 필요해 최초 수집의 약 절반을 차지했다.

이는 구버전·신버전의 동일 조건 속도 비교가 아니라 **최초 전체 수집과 변경 없는 정기 재수집의 비교**다.
구버전 정책에서는 해당 83건이 모두 6시간 만료 그룹이었다. 정기 수집의 조회 건수를 줄인 효과이며,
최초 도입·24시간 만료·목록 변경이 많은 실행은 전체 조회에 가까운 시간이 든다. 외부 API 상태에 따라
시간은 달라지며 이 수치를 운영 성능 보장으로 사용하지 않는다.

LH 목록은 유형 필터 없이 500행씩 두 페이지를 조회했다. 응답 기본 기간은 최근 두 달이었고,
마이홈에만 있는 11건을 제거하지 않는다. 목록 불변은 상세 불변을 보장하지 않아 24시간 만료 후
다음 정기 실행에서 전체 확인한다. 마감 이틀 이내·목록 미연결·오래된 목록은 기존 6시간 주기다.
자세한 정책, 실패 시 보존, 배포·복구는 [LH 공고 연결 조회](lh-announcement-link-resolution.md#lh-목록-기반-재조회)를 따른다.

측정은 `LhCatalogLiveBenchmarkTest`라는 임시 Spring 통합 테스트에서 수행했다. 외부 클라이언트·저장소는
실제 구현을 쓰고 `Clock`만 고정했다. 측정용 테스트는 일반 검사에서 실제 API가 호출되지 않도록 제거했다.
실응답에서 발췌한 목록 fixture, 목록 검증·변경 감지·24시간 갱신·실패 보존 통합 테스트는 저장소에 남겼다.

목록 추가 시점 검증: 격리 PostgreSQL의 `./gradlew --rerun-tasks check`에서 **1,426개 테스트 통과**.
신규 DB 생성·기존 DB baseline 경로의 Flyway 적용, Hibernate 스키마 검증,
목록 변경 후 실패·복구, 6시간/24시간 경계, 마감 근접 공고, 마이홈 단독 공고 보존을 포함한다.
하네스 검사와 `git diff --check`도 통과했다.

## 직접 전체 조회의 동시성 검증 — 2026-09-25

재조회 생략 없이 같은 12공고의 공급·상세 24회를 매번 호출했다. 순서는 동시성 2 → 4 → 4 → 2였고,
합계 시간은 각각 **19.873초 → 9.305초 → 9.099초 → 17.118초**였다. 96회 모두 성공했으며
응답의 조회 조건과 요청이 일치했다. 응답 생성 시각 `RS_DTTM`을 제외한 데이터는 요청별로 동일했다.

이번 수치는 Python HTTP 조회·JSON 검증까지이며 Java 서비스·DB 저장은 제외한다. 각 조건 두 번의 평균은
18.50초와 9.20초였다. 이어 24공고의 공급·상세 48회를 동시성 4/6/8로 각각 조회했다.
합계는 **20.261초 / 15.152초 / 11.833초**, 144회 모두 성공했고 생성 시각을 제외한 응답도 같았다.
이 표본을 근거로 동시성 8을 실제 서비스에서 아래와 같이 확인했다.

## 같은 166회 요청의 서비스·DB 포함 비교 — 2026-09-25

실제 인증키·Java 수집 서비스·격리 PostgreSQL을 사용했다. 마이홈 211행과 LH 목록 581건을 한 번
수집한 후 동일한 입력을 두 실행에 사용했다. 실행마다 상세·공급 원천, 성공 체크포인트와 출처 연결을
비워 **83공고의 공급 83회·상세 83회**를 모두 호출했다. 시계는 고정했고 외부 클라이언트는 실제 구현이다.
동시 요청 수만 2 → 8로 바꿨다. 두 실행의 연결/읽기 타임아웃은 모두 3초/10초다.

| 단계 | 동시성 2 | 동시성 8 | 외부 요청 / 저장 행 |
|---|---:|---:|---:|
| LH 공급 | 79.705초 | 21.024초 | 각각 83회 / 402행 |
| LH 상세 | 80.975초 | 20.091초 | 각각 83회 / 1,264행 |
| LH 두 단계 합계 | **160.682초** | **41.116초** | 각각 166회 / 1,666행 |

**74.4% 단축, 약 3.9배 처리 속도**다. TTL에 따른 생략 없이 같은 일을 수행한 결과다.
각 실행의 체크포인트 166개, 공고 출처 연결 174개도 같았다. 원천을 요청 조건·행 순서로 정렬해
생성 ID·수집 시각을 제외한 모든 DB 필드의 해시를 비교했고 공급·상세 모두 일치했다.
외부 요청 332회에서 실패·제한·재시도는 0건이었다. 건너뜀 1건/단계는 LH 외 기관 공고다.

목록 준비는 마이홈 7회/4.213초, LH 목록 2회/2.701초였다. 위 표는 이 공통 준비와 제품 정제,
애플리케이션 기동을 제외한 **LH 원천 수집·DB 저장** 시간이다. 전체 제품 파이프라인 시간으로 해석하지 않는다.
DB 풀은 테스트 기본값 4를 유지했다. 전체 SQL 수·DB 대기·운영 트래픽 동시 부하는 이번에 측정하지 않았다.
2 → 8 순서로 한 번씩 비교했으므로 JVM 워밍업·시간대 영향이 포함될 수 있다. 운영 성능·공식 허용량을 보장하지 않는다.

측정용 `LhConcurrencyLiveBenchmarkTest`는 일반 검사에서 실제 API가 호출되지 않도록 제거했다.
실행별 보고서와 원천 내용의 동일성 검증을 마친 뒤 아래 장애·동시성 회귀 테스트를 실행했다.

## 동시성·타임아웃·장애 차단

정상 상황의 속도 개선은 동시성 확대에서 나온다. 타임아웃·벌크헤드·서킷 브레이커는 장애가
전체 수집의 긴 대기로 번지는 것을 줄인다. [회복력 참고 자료](https://javacan.tistory.com/597)의
세 장치를 기존 실행기·HTTP 클라이언트·메트릭에 적용했으며 새 라이브러리는 추가하지 않았다.

| 장치 | 적용 값과 동작 |
|---|---|
| 동시성 제한(벌크헤드) | 상세·공급 최대 8개. 완료된 슬롯에 다음 요청을 투입하고 같은 PAN_ID는 순서를 유지 |
| 공통 실행 잠금 | LH 목록·상세·공급이 PostgreSQL advisory lock을 공유. 단독 API·파이프라인·같은 DB의 다른 인스턴스 중 한 작업만 실행 |
| LH 전용 타임아웃 | 연결 3초, 읽기 10초. 다른 외부 클라이언트의 10초/30초는 유지 |
| 서킷 브레이커 | 연결·5xx 실패가 연속 5회면 30초 차단. 이후 실제 재실행 요청 중 1건만 복구 확인. 성공 시 재개, 실패 시 다시 차단 |
| 호출 제한 | HTTP 429 또는 JSON 응답의 게이트웨이 22/23은 즉시 차단. 해당 요청은 재시도하지 않음 |
| 실패 처리 | 새 공고 투입 중단, 진행 중인 작업 정리. 성공 원천·체크포인트 보존, 차단된 요청은 성공 처리하지 않음 |

서킷 상태는 JVM 단위이며 목록·상세·공급이 공유한다. 공통 DB 실행 잠금이 인스턴스 간 동시성을 막지만,
다른 애플리케이션에서 같은 인증키를 쓰는 호출과 구버전 인스턴스까지 제한하지는 않는다.
구버전 수집이 끝난 뒤 교체해야 공통 잠금이 일관되게 적용된다.
읽기 타임아웃은 소켓 대기 제한이며 전체 작업의 10초 마감 시간이 아니다. 개별 일시 장애는 기존 최대 3회
재시도 정책을 유지하지만, 회로가 열리면 추가 네트워크 호출을 차단한다.

호출 제한 보고를 받은 파이프라인은 남은 LH 수집 단계를 건너뛴다. 병렬 처리 중 회로 차단 예외가
발생한 실행은 FAILED로 기록하고 LH 장애/제한과 재실행 안내를 보존한다. 단독 API 차단 응답은
HTTP 503, `LH_ANNOUNCEMENT_UNAVAILABLE`이다. 이미 진행 중인 응답은 끝까지 정리하므로 즉시 종료를 보장하지 않는다.

설정은 `LH_ANNOUNCEMENT_MAX_CONCURRENT_REQUESTS`(기본 8, 허용 1~8),
`LH_ANNOUNCEMENT_CONNECT_TIMEOUT`(기본 `PT3S`), `LH_ANNOUNCEMENT_READ_TIMEOUT`(기본 `PT10S`)이다.
운영에서 제한·지연이 증가하면 동시성을 4 또는 2로 낮추고 기존 단계별 메트릭으로 확인한다.
자동 속도 조절·배포·운영 부하 측정은 이번 범위에 포함하지 않았다.

검증 범위: 8개 상한과 다음 슬롯 투입, 실제 HTTP 읽기 타임아웃, 실제 PostgreSQL의 다른 잠금 인스턴스 간
상세/공급/목록 중복 거절, 연속 장애 차단·단일 복구 확인·늦은 성공의 잘못된 복구 방지,
진행 중인 성공 저장 보존, 차단 시 후속 공고·단계 중단과 관리자 실패 표시.
현재 작업 트리 검증: 격리 PostgreSQL에서 `./gradlew test --tests 'com.toadzip.backend.ingest.*'`의
625개, `./gradlew --rerun-tasks check`의 **1,443개 테스트 통과**(실패·오류·건너뜀 0).
초기 실패 테스트는 상세 실행 중 공급이 함께 시작되는 기존 동작을 재현했고 공통 잠금 적용 후 통과했다.
전체 검사에는 신규/기존 DB Flyway 적용·Hibernate 스키마 검증이 포함된다.
하네스 검사·`git diff --check` 통과, 계층 의존 방향은 변경 경로를 수동 검토했다.
[LH 독립 수집의 후속 계획](lh-announcement-collection-plan.md)은 별도로 유지한다.

## 운영에서 볼 값

기존 관리 포트의 `/actuator/prometheus`로 노출한다. 새 의존성은 필요 없다.
공통 RetryExecutor의 호출 계측은 기존 다른 수집에도 적용되며 `source`로 구분한다.

| Micrometer 이름 | 의미 / 라벨 |
|---|---|
| `ingest.pipeline.step` | 단계 전체 시간 / `step`, `result` |
| `ingest.external.request` | 시도별 외부 조회·파싱 시간 / `source`, `result` |
| `ingest.external.retry` | 재시도 진입 횟수(회로 거절 포함) / `source` |
| `ingest.external.retry.wait` | 재시도 전 대기 시간 / `source` |
| `ingest.announcement.store` | 공고 원천 교체 트랜잭션 시간 / `source` |
| `ingest.lh.circuit.state` | 0: 정상, 1: 차단, 2: 복구 확인 중 |
| `ingest.lh.circuit.opened` | 장애·제한으로 차단한 횟수 |
| `ingest.lh.circuit.rejected` | 외부 호출 전에 차단한 횟수 |

Timer는 Prometheus에서 `*_seconds_count`, `*_seconds_sum`, `*_seconds_max`로 나타난다.
재시도 Counter는 `ingest_external_retry_total`이다. 결과는 `completed`, `failed`,
`rate_limited`, `rejected`로 구분한다. `rejected`는 네트워크에 보내지 않은 시도다. 저장 Timer에는 성공과 실패한 저장 시도가 모두 포함된다.
저장 Timer는 원천 교체만 측정하며 체크포인트·실패 이력 저장과 전체 DB 쿼리를 포함하지 않는다.
평균 호출 지연은 `rejected`를 제외한 request의 sum 증가량 / count 증가량으로 계산한다. 병렬 요청의 시간 합계는
실제 실행 시간과 다르므로 단계 시간에서 단순 차감하지 않는다.

단계 종료 로그 `event=ingest.pipeline.step.finished`의 `executionId`, `step`, `result`,
`durationMs`로 DB 실행 이력과 연결한다. 실행 ID는 MDC의 `executionId`로 파이프라인과 병렬 작업에
전달하고, 파이프라인을 시작한 HTTP 요청의 `traceId`와 구분한다. 메트릭 라벨에는 넣지 않는다.

이전 변경 검증: Java 25와 격리 PostgreSQL에서 `./gradlew --rerun-tasks check`의 1,174개 테스트 통과.
페이지 경계·빈 유형, 최대 동시성·같은 공고 순서, 실패 복구·실제 DB 저장, 메트릭 집계를 검증했다.
하네스·커밋 메시지·PR 검증기 테스트, 하네스 검사와 `git diff --check`도 통과했다.

속도 비교 이후 실시한 [원천·DB·값 변환 대조와 남은 정책](lh-announcement-correctness-audit.md)을 함께 확인한다.
