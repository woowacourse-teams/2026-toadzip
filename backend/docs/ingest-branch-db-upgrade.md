# 수집 저장 구조 전환

기존 원천을 새 저장 구조로 이관하고 제품·승인·실행·실패 이력을 보존한다.
현재 원천 Reader는 새 구조만 읽으므로 이관에서 보류된 행은 자동 재사용되지 않는다.

## 이관과 보존

### 이관 기준

`20261004.07`은 단지 충돌 지역·공고 무효 식별자·LH 요청 충돌을 먼저 집계한다.
식별 불명·지역 충돌·복원 불가능한 LH 요청은 구형 테이블에 남긴다.
임시 테이블과 대량 삽입된 저장 테이블의 통계를 갱신하여 후속 조인을 지원한다.

### 보존 대상

구형 원천, 이관 보고서, 제품·관리자 승인·실행·실패 감사 이력을 보존한다.
`20261005.01`도 원천을 폐기하지 않는 보존용 버전이다.
미소비 관리자 승인을 취소하거나 기존 수집 실패를 `SKIPPED`로 바꾸지 않는다.
구형 원천을 사전 삭제하는 절차는 실행하지 않는다.

## 적용 조건

수정된 `07`과 `20261005.01`은 기존 SQL이 성공한 영구 환경이 없는 경우에만 사용한다.
이미 적용한 SQL·버전·체크섬을 덮거나 이력을 삭제하지 않는다.

중단한 리허설도 적용 이력을 확인한다. sequence 변경은 중단 후 남을 수 있으므로
원천 행 ID와 sequence 값이 같다는 가정을 하지 않는다.

## 전환 순서

1. 대상 DB와 Flyway 이력을 확인하고 전체 DB를 백업한다.
   구버전 서버·worker를 중지하고 관리자 쓰기·수집·정제를 차단한다.
   제품·계정·원천·감사 이력의 건수와 감사 행 내용을 기록한다.
2. 개발·운영 DB 복사본에서 새 아티팩트를 적용한다.
   소요 시간과 이관 보고서의 전체·이관·보류 행수 합계를 확인한다.
   원천 필드·행 순서·실제 수집 시각·업무 키·LH 요청 조건을 원본과 대조한다.
3. 실제 Flyway 이력과 아티팩트를 비교해 누락 버전을 찾는다.
   낮은 버전이 누락된 경우 이번 적용에만 `--spring.flyway.out-of-order=true`를 사용한다.
4. 최신 migration의 성공과 Hibernate `validate`를 확인한다.
   제품·계정·관리자 승인·감사 이력이 그대로인지 대조한다.
5. 일회성 `out-of-order`를 제거하고 기본 설정으로 재기동한다.
   새 원천 조회를 확인한 뒤 수집·정제를 재개한다.

## 검증과 복구

### 검증 범위

| 테스트 | 확인할 내용 |
|---|---|
| `LegacySourceImportMigrationTest` | 여섯 원천 이관, 업무 키·LH 요청 조건 보존, 충돌·NULL 지역·중복 원천·공고 식별자 선별 |
| `DiscardCollectedSourcesMigrationTest` | 구형·신규 원천, 관리자 승인과 실패 감사 이력 보존 |

운영 규모의 소요 시간은 복사본 리허설에서 확인한다.
후속 정제의 실패 해결 정책은 유지되므로, 이관 보류된 원천의 실패가 해결로 분류되는지도 확인한다.

### 검증 실패

쓰기를 차단한 상태에서 수정 버전을 적용하거나 백업 DB와 호환 아티팩트로 복구한다.
