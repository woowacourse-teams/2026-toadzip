# 기존 DB의 수집 저장 구조 전환

기존 수집 원천을 새 저장 구조로 이관하여 재사용한다.
구형 원천, 이관 보고서, 제품·관리자 승인·실행 및 실패 감사 이력은 보존한다.

`20261004.07`은 단지 충돌 지역·공고 무효 식별자·LH 요청 충돌을 먼저 집계한다.
임시 테이블과 대량 삽입된 저장 테이블의 통계를 갱신하여 후속 조인을 지원한다.
식별 불명·지역 충돌·복원 불가능한 LH 요청은 구형 테이블에 남긴다.
현재 원천 Reader는 새 구조만 조회하므로 이관 제외된 행은 자동 재사용되지 않는다.

`20261005.01`은 수집 원천을 폐기하지 않는 보존용 버전이다.
미소비 관리자 승인을 취소하거나 기존 수집 실패를 SKIPPED로 변경하지 않는다.
구형 원천을 사전 삭제하는 절차는 실행하지 않는다.

## 적용 조건

수정된 `07`과 `20261005.01`은 기존 SQL이 성공한 영구 환경이 없는 경우에만 사용한다.
이미 적용한 SQL·버전·체크섬을 덮거나 이력을 삭제하지 않는다.
중단한 리허설도 적용 이력을 확인한다. sequence 변경은 중단 후 남을 수 있으므로
원천 행 ID와 sequence 값이 같다는 가정을 하지 않는다.

## 대상과 적용 순서

1. 대상 DB와 Flyway 이력을 확인하고 전체 DB를 백업한다.
   구버전 서버·worker를 중지하고 관리자 쓰기·수집·정제를 차단한다.
   제품·계정·원천·감사 이력의 건수와 감사 행 내용을 기록한다.
2. dev·운영 복사본의 리허설 DB에서 새 아티팩트를 적용한다.
   소요 시간을 기록하고, 이관 보고서의 전체·이관·보류 행수 합계,
   원천 필드·행 순서·실제 수집 시각·업무 키·LH 요청 조건 보존을 확인한다.
3. 낮은 버전이 누락된 DB는 이번 적용에서만
   `--spring.flyway.out-of-order=true`를 사용한다.
   dev의 `20260930.09` 상태에는 `20260930.01`이 누락됐다.
   운영의 누락 목록은 실제 이력과 아티팩트를 비교한다.
4. 최신 migration의 성공과 Hibernate `validate`를 확인한다.
   제품·계정·관리자 승인·감사 이력이 그대로인지 대조한다.
5. 일회성 `out-of-order`를 제거하고 기본 설정으로 재기동한다.
   새 원천 조회를 확인한 뒤 수집·정제를 재개한다.

## 검증과 복구

`LegacySourceImportMigrationTest`는 여섯 원천 이관, 업무 키·LH 요청 조건 보존,
충돌 지역·NULL 지역·중복 원천·공고 식별자의 선별 규칙을 검증한다.
`DiscardCollectedSourcesMigrationTest`는 보존용 최신 버전까지의
구형·신규 원천, 관리자 승인과 실패 감사 이력 보존을 검증한다.
이 테스트는 운영 규모의 시간 측정을 대신하지 않는다.

후속 정제의 기존 실패 해결 정책은 변경하지 않는다.
이관 보류된 원천의 실패가 후속 정제에서 해결로 분류되는지 별도 확인한다.
검증 실패 시 쓰기를 차단하고 백업 DB와 호환 아티팩트로 복구하거나 전방 수정한다.
