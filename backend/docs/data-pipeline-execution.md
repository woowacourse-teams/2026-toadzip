# Data Pipeline Execution

진행 표시·중지 API·실패 조회와 배포 조건은 [관리자 실행 제어](pipeline-operator-controls.md)를 따른다.

## 실행 상태

- 기본 통합 실행은 `단지 수집·정제`(4단계), `공고 수집·정제`(6단계)다. 수집·정제 단독 실행 네 유형도 유지한다.
- 단지 수집·정제와 공고 수집·정제는 각자의 최신 실행 상태를 독립적으로 보존한다.
- 관리자 파이프라인은 PostgreSQL advisory lock을 획득한 실행만 시작한다.
- 시작 직후 `RUNNING` 실행을 저장하고 단계 시작·완료마다 현재 상태를 갱신한다.
- 전체 단계가 끝나면 `COMPLETED`, 정제·보강에서 처리되지 않은 원천 행이 있으면
  `COMPLETED_WARNINGS`, API 호출 제한으로 건너뛴 단계가 있으면 `COMPLETED_WITH_SKIPS`로
  저장한다. 누락과 건너뜀이 함께 있으면 `COMPLETED_WARNINGS`이며 두 단계 보고서를 모두 보존한다.
- 원천 행 누락은 단계 보고서에 남긴다. 현재 단지·공고 매칭 실패는 개별 실패 이력에도 남지만,
  LH 주택형 누락은 보고서의 건수로만 남는다. 운영 장애로 분류된 부분 실패는
  후속 단계를 한 번씩 계속 실행한 뒤 최초 실패를 대표 실패로 저장하고 실행을 `FAILED`로 끝낸다.
- 예상하지 못한 서버 오류가 발생하면 이후 단계를 실행하지 않고 즉시 `FAILED`로 기록한다.
- 한 단계의 실패가 모두 외부 API 호출 제한이면 해당 단계와 응답을 건너뜀으로 보존하고 다음 단계를 실행한다.
- 호출 제한은 재시도하지 않으며, 전국 병렬 수집 중이면 대기 중인 지역 요청도 취소한다.
- 호출 제한과 다른 운영 실패가 섞인 결과는 부분 실패로 처리하되, 동일 실행에서 실패한 단계 전체를 다시 실행하지 않는다.
- 단지 정제의 지오코딩 외부 API·좌표 변환·저장 오류는 운영 실패로 분류한다. 주소 불명·모호함과 정제·보강의 매칭 불가·원천값 오류, 매칭된 LH 단지 안의 주택형 누락은 행별 누락으로 분류한다.
- 상태 조회는 애플리케이션 메모리가 아니라 DB의 유형별 최신 실행을 사용한다.
- 완료 단계와 실패 응답을 보존하므로 다른 인스턴스나 클라이언트 재접속에서도 같은 결과를 조회한다.
- 실행 중에는 30초마다 실행 행의 heartbeat를 갱신한다. 새 실행이 advisory lock을 획득하면
  시작 전에 2분 넘게 갱신되지 않은 과거 RUNNING 실행을 실패로 복구하고 마지막 단계를 남긴다.
  실행 ID 또는 유형별 최신 상태 조회에서도 잠금이 없고 heartbeat가 만료된 실행을 복구한다.
  복구 직전 상태와 heartbeat를 다시 확인한다.
- 실행 범위 안의 쓰기 트랜잭션은 잠금 세션과 실행 소유자·세대값을 확인하고 소유권 행의 공유 잠금을
  커밋까지 유지한다. 커밋 직전에도 잠금 세션을 확인해 소유권을 잃은 실행의 쓰기를 롤백한다.
  후속 실행의 소유권 이전은 기존 쓰기 트랜잭션이 끝날 때까지 기다린다. 현행 판단은 [전체 흐름 재검토](ingest-flow-review.md)를 따른다.

## 실행 방법

- 수집·정제는 관리자 요청으로만 시작한다. 서버 부팅·예약·장애 복구는 새 ingest 실행을 만들지 않는다.
- 알림 보관 기간 정리는 공통 스케줄링으로 실행하는 별도 작업이다.
- 관리자가 `POST /api/admin/ingest/pipelines/{type}`으로 직접 시작한다. `complex-sync`, `announcement-sync`는 하나의 실행 ID·잠금으로 수집 후 정제를 수행한다.
- 통합 실행에서 수집 부분 실패가 있으면 수집 구간 뒤 `FAILED`로 끝내고 정제를 시작하지 않는다. 호출 제한만 있으면 정제 단계를 사유와 함께 건너뛰어 `COMPLETED_WITH_SKIPS`로 끝낸다.
- 정제 전에 멈춘 통합 실행 결과의 `저장된 원천으로 정제 실행`은 기존 정제 단독 API로 새 실행을 만든다. 이전 원천이 포함될 수 있고, 원래 실패 이력은 보존한다.
- `complex-collection`, `complex-refinement`, `announcement-collection`, `announcement-refinement`의 기존 단계·동작을 보존한다.
- `sh-announcement-collection`은 SH 주택임대 게시판의 원천만 수집하는 별도 1단계 실행이다.
  관리자 화면의 `SH 공고 수집` 또는 본문 없는 `POST /api/admin/ingest/pipelines/sh-announcement-collection`로
  시작한다. 관리자 세션과 CSRF는 필요하고 공공데이터포털 키는 사용하지 않는다.
  목록은 전체 페이지를 확인하고 등록일 기준 최근 90일 게시글의 상세 HTML·본문·첨부 메타데이터를
  `sh_announcement_source`에 저장한다. 기간 검색과 정렬을 추정해 페이지 탐색을 조기 종료하지 않는다.
  `ingest.sh.lookback-days` 기본값은 `90`이며 `0`이면 전체 이력의 상세를 수집한다.
  `ingest.sh.request-interval` 기본값은 `1s`이고 요청은 순차 실행한다. 페이지당 10건을 검증하고 최대 1,000페이지,
  응답당 2 MiB, 연결 10초·읽기 30초로 제한한다. 5xx·연결 오류는 기존 정책으로 최대 3회 시도하고 429는 즉시 중단한다.
  목록 건수 변화·중복 ID·파싱 오류는 실패 이력에 남긴다. 이미 저장한 글은 보존하며 재실행으로 실패를 복구한다.
  `SH:m_247:{seq}`를 저장 키로 쓰고 내용 변경 감지 시각과 수집 시각을 분리한다. 조회수·메뉴 변경은 내용 변경으로
  취급하지 않는다. 수집 범위에 없는 글을 삭제하지 않는다. 원천 조회의 `sourceUpdatedAt`은 게시자가 제공한
  수정 시각이 아닌 최초 저장/내용 변경 감지 시각이다.
  첨부는 `fileSeq`, 파일명·크기·공식 미리보기 URL을 보존한다. 파일 바이트 다운로드, PDF/HWP 추출,
  모집/결과/민간 공고 분류와 제품 `Announcement` 정제는 후속 단계다. 이 실행은 제품 테이블을 변경하지 않는다.
- 새 실행은 `MANUAL`로 기록한다. 과거 자동 실행의 `SCHEDULED`·`RECOVERY` 트리거와
  예정 시각·상위 실행 ID는 기존 실행 이력 조회를 위해 읽을 수 있다.

## 스키마 배포

`V20261010_01__sh_announcement_collection.sql`은 SH 원천 테이블과 조회 인덱스를 만들고 실행 유형·단계·외부 수집
실패 출처 CHECK에 SH 값을 추가한다. 기존 값과 이력은 보존한다. SH 이력을 읽을 수 있도록 서버와 관리자 화면을
함께 교체한다. SH 수집을 종료한 뒤 배포하고 구버전으로 되돌릴 때는 새 enum 이력 호환을 먼저 확인한다.
단건 등록의 `ANNOUNCEMENT_REGISTRATION` 유형과 대상 ID 제약도 유지한다.
이 버전은 develop의 `20261009.01` 이후에 적용하므로 SH 추가를 위한 out-of-order 설정은 필요하지 않다.
병합 전 develop을 다시 확인하고 새 migration과 버전이 겹치면 아직 배포하지 않은 SH 추가분만 조정한다.
이미 적용된 develop migration의 파일명·내용·이력은 변경하지 않는다.
구 작업 브랜치의 `20261005.02`를 적용한 실험 DB는 이 배포의 업그레이드 대상이 아니다.
그 DB를 계속 사용해야 한다면 백업과 이력을 먼저 대조해 별도 이관하며 자동 repair·이력 삭제는 하지 않는다.

`V20260930_01__allow_combined_ingest_pipelines.sql`은 실행 유형 CHECK에 `COMPLEX_SYNC`, `ANNOUNCEMENT_SYNC`를 추가한다. 기존 네 유형과 이력을 보존한다. 새 enum 이력이 생기면 구버전 서버가 전체 이력을 읽지 못하므로 ingest를 종료한 뒤 서버·관리자 화면을 함께 교체한다. 서버 다운그레이드는 새 이력 호환 처리가 필요하다.

초기 스키마는 [Flyway 도입 절차](flyway-adoption.md)의 통합 `V20260922_01`로 배포한다.
`ddl-auto=validate`는 변경을 적용하지 않으므로 첫 도입 전에 기존 DB baseline이 필요하다.
`V20260926_01__ingest_execution_ownership.sql`은 실행 소유자와 세대값을 보존하는 테이블을 추가한다.
이 검증이 없는 이전 서버와 혼합 실행하지 않도록 기존 ingest를 종료한 뒤 교체한다.

SQL은 신규 테이블을 생성하고 기존 실행·실패 테이블을 추가 컬럼으로 확장하므로 이전
애플리케이션이 기존 실패 행을 저장할 수 있다. 다만 이전 버전의 ingest는 실패 테이블을
삭제·재생성하므로 신규 버전이 쓰기를 시작하기 전에 모든 이전 인스턴스를 drain하고, 혼합
버전에서는 ingest를 실행하지 않는다. 배포 후 실행·단계 테이블, 실패 테이블의 상태·발생 횟수·
실행 ID 컬럼, `lh_household_enrichment_failures` 테이블과 관련 인덱스를 확인한다.
기존 정기 실행 메타데이터 컬럼과 스케줄 지연 테이블은 이미 적용된 마이그레이션을 변경하지 않아
스키마에 남는다. 애플리케이션은 새 스케줄 지연을 기록하지 않는다.
통합 `V20260922_01`은 Flyway의 단일 트랜잭션으로 실행되며, 오류가 나면 해당 마이그레이션의
스키마 변경과 백필을 함께 롤백한다.

실패 이력은 현재 장애와 재발 추적의 근거이므로 자동 삭제하지 않는다. 보존 기간과 삭제 기준은
운영 데이터 증가량과 감사 요구를 확인한 뒤 별도 승인된 마이그레이션으로 정한다.
신규 현재 실패와 이력 API는 `page`(0부터 시작), `size`(기본 100, 최대 200)로 나누어 조회한다.
기존 현재 실패 API는 호환을 유지하고 `/failures/page`에서 같은 페이징 계약을 제공한다.

롤백 전에 실패 테이블을 백업한다. 이전 애플리케이션에서 ingest를 실행하면 신규 실패 이력이
삭제되므로 이력 보존이 필요하면 ingest를 중지한 채 신규 버전을 복구한다. 테이블 삭제는 실행
이력 손실을 수반하므로 별도 백업과 승인 없이 수행하지 않는다.

일정 단지명 컬럼 배포와 기존 일정 재정제는 [공고 일정 대상](announcement-schedule-targets.md)을 따른다.
`20260930.01`을 먼저 적용한 작업 DB는 [develop 통합 업그레이드](ingest-branch-db-upgrade.md)의 1회 적용 절차를 따른다.
