# 관리자 수집 실행 제어

## 진행 확인

- 진행 바는 현재 수집 범위의 실제 완료 대상 수 / 전체 대상 수다. 단계 수는 별도 텍스트로 표시한다.
- `workProgress`는 범위 이름·단위·완료/전체 수·범위 시작/최근 완료 시각을 저장한 스냅샷이다.
  마이홈 단지는 전체 지역, 마이홈 공고는 현재 공급유형의 페이지, LH 목록은 페이지,
  LH 공급/상세는 현재 최대 500개 원천 행 묶음에서 이번 실행에서 아직 처리하지 않은 고유 요청을 센다. 대상 요청은 매 실행 실제 조회한다.
  실패가 확정된 대상도 처리 완료로 세며, 재시도는 같은 대상을 중복 완료하지 않는다.
- 예상 남은 시간은 `범위 경과 시간 / 완료 대상 수 × 남은 대상 수`로 계산한다.
  병렬 처리·재시도·저장 시간도 실제 경과 시간에 포함된다. 전체 파이프라인 종료 시각은 아니며,
  화면에 표시한 범위 이후의 작업량은 포함하지 않는다.
- 2개 미만 처리했으면 속도 계산 중, 전체 수가 -1이면 전체 대상 확인 중으로 표시한다.
  최근 완료 이후 60초 또는 평균 대상 처리 시간의 3배를 넘기면 지연으로 보고 추정을 보류한다.
  중지 요청·종료 시에는 예상 시간을 표시하지 않는다.
- `externalRequestCount`는 실행 전체의 외부 요청 처리 횟수이며 실패·재시도를 포함한다.
  `lastRequestDescription`, `lastProgressAt`으로 최근 요청과 활동을 확인한다.
- 전체 수집 건수를 모르는 구간에 예상 퍼센트나 남은 시간을 표시하지 않는다.
- 진행 상태와 중지 요청은 DB에 저장하므로 새로고침하거나 다른 서버에서 조회해도 유지된다.

## 관리자 탐색

- `/admin`은 `/admin/ingest`로 이동한다. 수집·정제, 단지 입력, 공고 입력, 주소 데이터는 별도 경로다.
- 공고 입력은 JSON 가져오기와 직접 입력 중 한 폼만 연다. 선택한 방식과 단지 ID는 URL에 유지한다.
- 단지 저장 후 연결 링크로 직접 공고 입력에 진입한다. 단지 정보는 기존 상세 API에서 확인하므로
  새로고침·직접 접근도 가능하며 조회 실패나 확인 전에는 공고 저장을 막는다.

## 수집 실패 뒤 정제 복구

- 통합 실행은 수집 부분 실패·호출 제한에서 자동 정제를 시작하지 않는다.
- 결과의 `저장된 원천으로 단지/공고 정제 실행`으로 해당 정제만 새로 실행한다. 현재 저장된 원천 전체를 사용하므로 이전 수집 원천이 포함될 수 있다.
- 정제 중에는 통합·독립 실행과 다른 복구 버튼을 잠근다. 수집 실패 결과는 그대로 남기고 정제 결과는 독립 정제 카드에서 확인한다.
- 단지 좌표가 부족하면 단지 수집 → `/admin/locations`의 위치정보 ZIP 업로드 → 단지 정제를 실행한다.
- 통합 실행 결과에서 수집 요청·정제 행·LH 보강 실패 목록을 각각 열 수 있다. 정제가 이미 시작된 실행에는 정제 미실행 안내를 표시하지 않는다.

## 실행 중지

`POST /api/admin/ingest/pipelines/executions/{executionId}/stop`은 관리자 세션과 CSRF 토큰이 필요하다.

- 요청은 `202`와 실행 상태를 반환한다. `RUNNING + stopRequested=true`는 중지를 기다리는 상태다.
- 수집은 다음 외부 요청·재시도 또는 다음 작업 시작 전에 중지 여부를 확인한다.
- 진행 중인 외부 응답과 저장은 강제로 끊지 않는다. 병렬 작업을 모두 마친 뒤 `STOPPED`로 저장하고
  실행 잠금을 해제한다. 그 전까지 다른 수집·정제는 시작할 수 없다.
- 정제는 현재 단계가 끝난 뒤 다음 단계 진입을 막는다. 단계 내부 중간에 중지하지 않으므로
  메모리에 모은 행별 실패 보고서의 저장을 마칠 수 있다.
- 이미 저장된 원천과 완료 단계 보고서는 보존한다. 아직 저장되지 않은 수집 버퍼는 버린다.
- 중복 요청은 같은 중지 상태를 반환한다. 이미 종료된 실행의 결과는 변경하지 않는다.
- 실제 오류가 발생한 실행은 `FAILED`로 남을 수 있다. 서버 소실 복구는 기존 heartbeat 정책을 따른다.
- `STOPPED` 수집은 정제를 시작하지 않는다. 재실행은 새 실행이다.

## 실패 확인

- 외부 API 수집 실패는 요청 단위이며, 정제·보강 실패는 원천 행 단위다.
- 화면은 기존 페이징 API로 미해결 목록 또는 해결된 항목을 포함한 이력을 20개씩 조회한다.
- 목록은 선택한 분류 전체다. 선택한 실행에서 최근 발생한 항목에는 별도 표시가 붙는다.
  실행 ID가 같지 않은 항목을 해당 실행의 실패라고 표시하지 않는다.
- 대상 식별자·공급행 번호·사유·상세 설명·최근 발생 시각을 먼저 보여주고 원본 JSON은 접어서 제공한다.
- API 실패를 빈 목록으로 바꾸지 않고 재시도 안내를 표시한다.

## 배포

- `V20260926_03__pipeline_stop_and_progress.sql`은 실행 테이블에 컬럼 4개를 추가하고
  상태 제약에 `STOPPED`를 추가한다. 기존 실행의 중지 요청은 false, 요청 횟수는 0으로 초기화한다.
- `V20260926_04__pipeline_work_progress.sql`은 nullable text 컬럼 `work_progress`를 추가한다.
  기존 실행은 진행량 스냅샷이 없으며, 새로운 수집부터 측정한다.
- 이전 서버는 `STOPPED` enum을 읽지 못하므로 실행을 모두 종료한 뒤 서버 버전을 함께 교체한다.
- 이전 버전으로 되돌릴 때 `STOPPED` 실행의 호환 처리가 필요하므로 무조건적인 다운그레이드는 피한다.
