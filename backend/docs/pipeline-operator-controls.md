# 관리자 수집 실행

`/admin/ingest`에서 실행 진행량·실패를 확인하고 중지·복구한다.
유형과 상태는 [수집·정제 실행](data-pipeline-execution.md)을 따른다.

## 진행 확인

진행률은 **현재 수집 범위**의 완료 대상 / 전체 대상이다. 실패가 확정된 대상도 완료로 세고 재시도는 중복 집계하지 않는다.
LH 공급·상세는 최대 500개 원천 행 묶음의 고유 요청을 센다. 전체 파이프라인의 진행률·종료 예상은 아니다.

총건수를 모르거나 처리 표본이 적거나 지연·중지 상태이면 남은 시간을 표시하지 않는다.
`externalRequestCount`에는 실패·재시도가 포함된다. 최근 활동은 `lastRequestDescription`·`lastProgressAt`으로 확인한다.

## 실패 확인과 복구

### 실패 목록

수집 실패는 요청 단위, 정제·보강 실패는 원천 행 단위다.
목록은 선택 분류 전체의 미해결 항목 또는 이력이며 특정 실행의 실패만 모은 결과는 아니다.

실패 조회 API는 `page=0`, `size=100`이 기본이고 최대 200이다.
단지·공고 매핑과 LH 공고 보강은 `/failures/page`, `/failures/history`를 사용한다.

### 저장 원천으로 정제

수집 부분 실패·호출 제한에서 통합 실행은 자동 정제를 시작하지 않는다.
결과의 **저장된 원천으로 단지/공고 정제 실행**을 선택하면 해당 정제의 새 실행을 만든다.
이전 원천이 포함될 수 있으므로 수집 결과를 먼저 확인한다. 원래 실패 결과는 보존된다.

단지 좌표가 부족하면 단지 수집 → `/admin/locations`의 위치정보 ZIP 업로드 → 단지 정제 순서로 실행한다.
공고별 연결·금액 실패는 [LH 복구](lh-announcement-link-resolution.md#복구)를 따른다.

## 실행 중지

`POST /api/admin/ingest/pipelines/executions/{executionId}/stop`은 관리자 세션·CSRF가 필요하며 `202`와 상태를 반환한다.
`RUNNING + stopRequested=true`는 중지 대기 상태다.

- 수집은 다음 요청·재시도 전에 중지를 확인한다. 진행 중 응답·저장을 강제로 끊지 않고 병렬 작업이 끝나야 잠금을 해제한다.
- 정제는 현재 단계를 마친 뒤 다음 단계를 막는다. 저장된 원천·완료 보고서는 남기고 미저장 수집 버퍼는 버린다.
- 중복 요청은 같은 상태를 반환하고 이미 종료된 결과는 바꾸지 않는다. 실제 오류가 발생하면 `FAILED`로 남을 수 있다.

`STOPPED` 수집은 정제를 시작하지 않는다. 재실행은 새 실행이며 기존 실행이 끝날 때까지 다른 수집·정제를 시작할 수 없다.

## 실행 이력

`GET /api/admin/ingest/pipelines/history?page=0&size=20`으로 조회한다.
관리자 세션이 필요하며 `page`는 0부터, `size`는 기본 20·최대 100이다.
