# Ingest 순차 리팩터링 계획 — 2026-09-30

사용자와 합의한 범위는 내부 흐름 정리 → 관리자 실행 방식 개선 → 수집 정책 검증이다. 근거는 [전체 흐름 재검토](ingest-flow-review.md)와 [수집 성능 기록](announcement-collection-performance.md)을 따른다.

## 작업 계약

- **Goal:** 수집부터 정제까지 한 번에 실행하고, 불완전한 수집 뒤에는 관리자가 결과를 확인해 저장된 원천으로 정제를 직접 재실행할 수 있다. 실행 제어는 명시적인 결과 분기로 읽을 수 있다.
- **Constraints:** 기존 네 실행과 이력·원천·관리자 수정값·공고별 트랜잭션을 보존한다. 새 의존성과 스케줄러를 추가하지 않는다. 운영 DB·외부 API 호출 없이 확인 가능한 근거를 먼저 사용한다.
- **Done:** 정상 통합 실행, 부분 실패·호출 제한에서 정제 차단, 수동 정제 복구, TTL 생략 후 정제, 중단·실행 잠금·기존 API 호환이 검증된다. 목록 정책 결론은 실측과 회귀 근거 및 미확인 범위를 함께 기록한다.

## 1. 내부 흐름 정리

이미 관리자 결과 요약과 로컬 `ReentrantLock` 제거를 구현했다. PostgreSQL 작업 잠금과 실행 소유권 검증은 유지한다.

[Runner](../src/main/java/com/toadzip/backend/ingest/pipeline/service/DataPipelineRunner.java)는 단계의 예상된 부분 실패를 결과로 반환하고 기록한다. 예외는 전체 실행의 최종 실패와 예상하지 못한 오류에 사용한다. 최초 실패 보고, 후속 수집 계속 실행, LH 호출 제한 전파, 중지 확인을 기존 테스트로 검증한다.

## 2. 통합 실행과 수동 정제 복구

| 실행 | 단계 | 기존 복구 실행 |
|---|---|---|
| `COMPLEX_SYNC` / `complex-sync` | 단지 수집 2단계 → 정제·보강 2단계 | `COMPLEX_COLLECTION`, `COMPLEX_REFINEMENT` |
| `ANNOUNCEMENT_SYNC` / `announcement-sync` | 공고 수집 4단계 → 정제·보강 2단계 | `ANNOUNCEMENT_COLLECTION`, `ANNOUNCEMENT_REFINEMENT` |

하나의 실행 ID·잠금·heartbeat·중지 경로를 재사용한다. 단계 소속과 순서는 실행 유형이 소유한다. 새 Flyway는 기존 유형을 보존하며 실행 유형 제약만 확장한다.

**사용자 확정 정책:** 수집에서 부분 실패 또는 API 호출 제한이 발생하면 수집 구간의 기존 후속 처리까지만 수행하고 자동 정제는 실행하지 않는다. 부분 실패는 `FAILED`, 호출 제한만 있으면 정제 건너뜀 사유를 남겨 `COMPLETED_WITH_SKIPS`로 종료한다. TTL에 따른 정상 요청 생략은 정제로 이어진다. 예상하지 못한 예외와 중지는 기존 즉시 종료 규칙을 따른다.

관리자 화면은 통합 실행을 기본 동작으로 제공하고 수집·정제 단독 실행을 함께 유지한다. 정제 전에 멈춘 통합 실행 결과에서 `저장된 원천으로 정제 실행` 버튼을 제공한다. 이전 원천이 포함될 수 있음을 표시하고 다른 실행 중에는 비활성화한다. 정제는 전체 저장 원천에 대한 기존 독립 실행이며 실패 행만 재시도하는 새 기능을 만들지 않는다.

새 단지의 주소 좌표가 없으면 기존 행 경고를 보존한다. 수집 → 위치정보 ZIP 업로드 → 단지 정제 경로를 안내한다. 최신 수집 표시는 통합·독립 수집을 모두 고려하고 수집·정제·보강 실패 목록에 접근할 수 있어야 한다.

**변경 책임:** 메인 에이전트가 Type·Step·Execution·Runner·응답 매퍼·마이그레이션, 관리자 API 타입·실행 화면·이력, 관련 테스트와 문서를 수정한다. 조사·리뷰 에이전트는 읽기 전용이다.

## 3. 수집 정책 검증

마이홈 수집의 공급유형별 성공 저장과 전체 성공 시 미조회 판정, 부분 실패 뒤 LH 수집 계속 실행을 유지한다. 성공한 공급유형까지 LH 수집을 막는 일괄 skip은 적용하지 않는다.

LH 목록은 유일 연결에서 조회 코드를 보정하고, 목록 변경 때 TTL 전에 재조회하며, 연결된 후보에 더 긴 TTL을 적용한다. 기존 실측과 격리 테스트를 대조해 유지 여부를 결정한다. `AIS_TP_CD` 누락 보완과 보정 요청이 실제 호출·체크포인트·연결에 동일하게 사용되는지 검증한다.

현재 snapshot은 후보 연결·코드 차이·현재 체크포인트·변경 후 재조회 필요 여부를 보여준다. 보정 덕분의 성공률과 과거 조기 재조회 누적 횟수는 덮어쓴 체크포인트만으로 복원하지 않는다. 운영 성과로 주장하지 않는다. 필요한 후속 감사는 원천·목록·체크포인트·연결을 격리 복제해 기존 resolver/policy로 계산한다.

## 검증과 배포

기존 회귀 → 새 행동 Red → 구현 Green → ingest 통합 테스트 → 격리 PostgreSQL 전체 `check` → 프론트엔드 `npm run check`·브라우저 → 하네스·diff 리뷰 순서로 확인한다.

마이그레이션은 기존 이력 보존·새 유형 허용·알 수 없는 유형 거부를 검증한다. 새 enum 이력이 생성되면 구버전 앱은 해당 이력을 읽지 못하므로 ingest 종료 후 서버와 관리자 화면을 함께 배포한다. 운영 배포와 원격 Git 변경은 이 로컬 구현 작업에 포함하지 않는다.

## 진행 상태

- 기존 관리자 결과 표시와 로컬 잠금 제거: 구현·검증 완료.
- Runner 부분 실패 결과 분기: 구현·회귀 검증 완료.
- 통합 실행과 수동 정제 복구: 구현 완료. 실제 DB에서 정제 차단·독립 복구·이력 보존·단계 순서·마이그레이션을 검증했다.
- 수집 정책 근거 보완: 완료. LH 목록은 유지하며 누락 코드 보완과 보정 요청·체크포인트·연결의 일치 회귀를 추가했다.
- 사용자 승인 실제 API·격리 DB 검증: 수집 부분 실패 차단, 수동 복구·중지, TTL 후 정제, 두 통합 실행 완료를 확인했다. 실응답 파서 오류와 저장 내용이 같은 단지 반복 행 처리를 보완했다. 상세 근거는 [운영 검증 기록](ingest-live-verification.md)에 있다.
