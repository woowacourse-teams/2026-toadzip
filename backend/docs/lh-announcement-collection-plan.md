# 직접 수집 속도 개선과 LH 독립 수집 계획

작성: 2026-09-25. 직접 수집 속도 개선은 구현·실측했고 **LH 단독 공고 등록은 후속 계획**이다.
LH 목록의 단독 수집·변경 관찰은 구현했다. 제품 공고 등록·정제와는 별개다.
현재 코드에는 목록 기반 재조회, 동시성 8, LH 전용 타임아웃·장애 차단을 적용했다.
같은 83공고·166회 호출의 서비스+DB 시간은 **160.7초 → 41.1초**였다.
[측정 조건과 결과](announcement-collection-performance.md#같은-166회-요청의-서비스db-포함-비교--2026-09-25)를 따른다.

## 목표와 완료 기준

- 수동 전체 재조회에서 같은 공고를 모두 조회하면서 완료 시간을 줄인다.
- 마이홈의 공고 범위를 유지하고 LH의 누락·정정·추가 공고를 별도 원천으로 확보한다.
- 중복 제품 공고, 잘못된 정정 연결, 임의로 채운 날짜·금액을 만들지 않는다.
- 완료 기준: 실제 서비스+격리 DB의 동일 대상 전후 비교, 오류·제한·저장 실패 복구 검증,
  LH 단독 원천의 검증·연결·공개 또는 보류 사유 확인, 기존 마이홈 API·제품 ID 호환.

## 1. 직접 조회도 빨라질 수 있다

기존 전체 수집 실측은 166.6초였다. 마이홈·LH 목록에 약 6.5초, LH 공급에 81.6초,
상세에 78.5초가 들었다. 당시 공급·상세를 순서대로 실행하며 각 단계의 동시성은 2였다.
관리자 수동 수집에도 현재 재조회 정책이 적용되며, TTL을 무시하는 경로는 공고별 강제 갱신이다.

이번에는 같은 12공고의 공급 12회·상세 12회를 매번 모두 호출했다.
외부 HTTP만 측정했으며 DB·Java 서비스 실행 시간은 포함하지 않았다.

| 실행 순서 | 동시 요청 | 공급 | 상세 | 합계 |
|---|---:|---:|---:|---:|
| 1 | 2 | 10.130초 | 9.743초 | 19.873초 |
| 2 | 4 | 4.471초 | 4.834초 | 9.305초 |
| 3 | 4 | 4.713초 | 4.385초 | 9.099초 |
| 4 | 2 | 8.528초 | 8.590초 | 17.118초 |

96회 모두 성공했다. 요청 조건이 응답의 `dsSch`와 일치했고 `RS_DTTM`을 제외한 응답은
각 요청의 첫 결과와 모두 같았다. 각 조건 2회 평균은 18.50초 → 9.20초로 약 50% 감소했다.
호출을 생략한 효과가 아니다. 소수 표본이며 공식 허용 동시성이나 운영 처리량을 보장하지 않는다.
[공식 공급 API](https://www.data.go.kr/data/15056765/openapi.do)는 초당 제한 오류 23을 설명하지만
공개 페이지에서 구체적인 초당 한도·동시 요청 상한을 확인하지 못했다.

### 구현 완료: 동시성 8과 장애 대기 축소

- 24공고로 넓힌 HTTP 표본에서 동시성 4/6/8은 20.3/15.2/11.8초였고 144회 모두 성공했다.
  이후 실제 서비스·격리 DB에서 같은 83공고·166회 요청을 동시성 2/8로 비교해 160.7/41.1초를 확인했다.
- 공급→상세 순서, 같은 PAN_ID의 저장 순서, 완료된 슬롯 재사용을 유지한다.
- 동시성 기본값 8, 허용 범위 1~8. 목록·공급·상세가 같은 PostgreSQL 실행 잠금을 사용해
  단독 API·파이프라인·다른 인스턴스의 중첩 실행을 거절한다.
- 연결 3초/읽기 10초, 연속 연결·5xx 실패 5회면 30초 차단. 복구 확인은 한 요청만 허용한다.
  호출 제한은 즉시 차단하며 진행 중인 성공 결과는 보존한다.
- 운영의 공식 초당 한도는 확인되지 않았다. 제한·지연이 늘면 설정을 4 또는 2로 낮춘다.
  같은 키를 사용하는 다른 애플리케이션과 구버전 인스턴스는 공통 상한 밖이다.
- 전체 강제 재조회 옵션은 추가하지 않았다. 일반 수동 실행은 기존 재조회 정책을 유지하고,
  기존 공고별 강제 갱신도 같은 제한을 적용한다. 전체 비교 실험은 격리 DB의 체크포인트를 초기화했다.
  운영 강제 옵션은 공개 요청·실행 이력 계약을 확정하는 별도 변경으로 남긴다.

공급과 상세를 공고별로 묶으면 단건 완료·재시도가 편해진다. 총 동시성이 같다면 실행 순서만 바꿔
처리량이 다시 두 배가 되지는 않는다. 이 재구성은 아래 제품 반영 경계에 맞춰 진행한다.

## 2. LH는 별도 수집원이 필요하다

09-25에 저장한 같은 시점의 두 목록을 비교했다. LH 목록 기본 조회 기간은 07-25~09-25다.
이는 마이홈과 LH 전체 보유 데이터의 포함 관계가 아니라 **해당 조회 범위의 비교**다.

| 분류 | 건수 | 해석 |
|---|---:|---|
| LH 모든 유형 목록 | 581 | 토지·분양·상가 등도 포함 |
| 그중 임대주택 `UPP_AIS_TP_CD=06` | 212 | 현재 지원 유형의 우선 비교 범위 |
| 마이홈 LH 요청과 정확히 연결 | 72 | 기존 원천 보강·변경 감지 |
| LH 임대 목록에 미연결 | 140 | 공고중 5, 접수마감 135 |
| 마이홈에 있으나 LH 목록에 미연결 | 11 | 기존 수집 유지 |

**미연결 140건을 신규 제품 공고 140건으로 해석하지 않는다.** 공고중 5건을 따로 조회한 결과:

| LH 후보 | 마이홈과의 관계 | 처리 방향 |
|---|---|---|
| 군산나운4 `2015122300020822` | 같은 제목의 마이홈 공고는 다른 PAN_ID. 접수일도 09-29와 10-06으로 다름 | 원문·일정·개정 관계 대조 후 연결 또는 별도 등록 |
| 천안쌍용5-2 `2015122300020756` | 같은 제목인데 마이홈 URL은 과거 PAN_ID `2015122300019790` | 링크 오류/새 모집 여부 확인 |
| 춘천·홍천 `2015122300020779` | 기존 마이홈 공고와 제목이 유사한 정정공고. 상세에 정정 사유 있음 | 원공고 관계 확인 후 정정으로 반영 |
| 칠곡왜관4 `2015122300020810` | 기존 마이홈 공고와 제목이 유사한 정정공고. 임대조건 수정 사유 있음 | 새 공고 중복 등록을 보류하고 개정 연결 확인 |
| 인천논현 LH16 `2015122300020780` | 수집한 마이홈 목록에 대응 공고를 찾지 못함 | LH 단독 후보. 상세가 발표일 미확정임을 명시하므로 확정 날짜로 공개하지 않음 |

5건의 상세·공급 총 10회는 모두 성공했다. 공급 주택형 행 수는 각각 2·1·11·1·3이었다.
제목 유사도는 조사 후보를 찾는 데만 사용했다. 동일 제목만으로 같은 모집·정정 관계를 확정하지 않았다.
마감일이 미래지만 `접수마감`인 취소 관련 후보도 있어 마감일만으로 활성 공고를 고르지 않는다.

## 3. 수집 범위와 원천별 역할

### 목록만 수집하고 변경을 관찰하는 경로

관리자는 `POST /api/admin/ingest/lh/announcements/catalog`로 LH 공고 목록 원천만 갱신할 수 있다.
이 경로는 목록의 전체 페이지를 검증한 뒤 한 번에 저장하며, 공고별 상세·공급 API를 호출하지 않는다.
기존 전체 공고 수집 파이프라인은 목록 다음에 상세·공급 단계를 계속 실행한다.

목록 행의 `sourceKey`를 기준으로 신규·기존을 구분한다. 기존 행은 공고 ID, 조회 코드,
공고명, 상태, 공고·게시·마감일, URL의 지문이 바뀔 때만 `changedAt`을 갱신한다.
`RNUM`·`ALL_CNT` 등 페이지 메타데이터만 달라지면 변경으로 보지 않는다. 실행 종료 로그와
`ingest.announcement.catalog.rows{change="new|changed|unchanged"}`에 각 건수를 기록한다.
조회 범위 밖의 기존 행은 삭제하지 않고, 페이지 조회·검증이 실패하면 기존 원천도 유지한다.
목록에 상세의 최종 수정 시각이 없으므로 목록이 동일해도 상세·공급의 불변성을 보장하지 않는다.

- 단독 목록 실행은 제품 공고를 생성하거나 정제하지 않는다.
- 단독 목록 실행의 완료 응답은 전체 저장 행 수를 반환한다. 신규·변경 건수는 로그·메트릭에서 확인한다.
- 기존 마이홈 공고는 LH 목록에 없더라도 계속 수집한다.

- 마이홈: LH 외 기관 포함 기존 범위, 마이홈 공고/단지 식별자, 공고 개정 연결을 계속 수집한다.
- LH 목록: 공식 조회 코드, 공고 발견, 상태·이름·날짜 변경 및 정정·취소 후보를 감지한다.
- LH 상세: 단지 주소, 세부 일정, 첨부·정정 사유를 수집한다.
- LH 공급: 단지별 주택형·면적·금액·세대수 원천을 수집한다.
- 제품 반영: 원천 조합을 검증한 한 경로가 공고·주택형·금액·일정을 함께 반영한다.
  같은 필드를 두 Writer가 서로 다른 우선순위로 덮어쓰지 않는다. LH가 최신이라는 이유만으로 자동 우선하지 않는다.

첫 범위는 기존 7개 임대유형과 검증된 공급코드 `060/061/062/063`이다. 전체 목록 저장은 유지하되
토지·상가·분양·매입임대·신혼희망타운의 별도 상위유형을 제품에 자동 추가하지 않는다.
추가 유형은 수요·필드·자격·주택형 연결을 검증한 별도 변경으로 다룬다.

우선순위는 기존 마이홈 대상 → LH 공고중/접수중의 미연결 후보 → 기존 공고 관련 정정·취소 → 종료 공고 보충이다.
현재 표본에서 기존 83조회+미연결 공고중 5후보는 최대 88조회 조건이다. 정정 관계를 확정하기 전의 상한이며
제품 공고 88개를 뜻하지 않는다. 종료 135건의 이력 수집을 매 수동 실행의 필수 경로에 넣지 않는다.

## 4. 필요한 모델·파서 변경

1. **원천 연결을 제품 ID와 분리한다.** 기존 `Announcement.id`와 마이홈 식별자를 보존한다.
   LH 전용 입력·출처 연결을 추가하고 LH 데이터로 가짜 `MyHomeAnnouncementSource`를 만들지 않는다.
   한 LH 요청이 여러 마이홈 공고의 지역별 범위나 개정본을 보강하는 실제 사례가 있으므로
   `PAN_ID` 하나를 제품 공고 하나로 강제하는 unique 제약을 만들지 않는다.
2. **공유 요청과 공유 공고를 구분한다.** 외부 호출은 조회 조건+수집 버전의 요청 해시로 합친다.
   제품 공고 연결은 원천 ID, 주택 범위, 개정 관계를 함께 확인한다. 유일한 연결만 자동 적용하고 모호하면 보류한다.
   LH로 먼저 생성한 뒤 마이홈이 나타나도 같은 범위·개정본이면 기존 제품 ID에 출처를 추가한다.
3. **일정 필드 보존은 반영했다.** 실제 응답의 `SBSC_ACP_ST_DT`, `SBSC_ACP_CLSG_DT`, `PZWR_ANC_DT`를
   원천·파서·일정 변환에 반영했다. `ACP_DTTM="~"`이면 구조화된 날짜를 사용한다.
   서류제출 대상자 발표일을 당첨일로 해석하던 오류도 수정했다. 두 접수 필드의 범위가 다른 원천은 공고문 대조가 남아 있다.
4. **표시 상태와 개정 유형을 구분한다.** LH `PAN_SS=공고중/접수마감`은 현재 제품의
   `AnnouncementPublicationType=원공고/정정/취소`와 다른 개념이다. 직접 enum 변환하지 않는다.
5. **검증 후 공고 단위로 반영한다.** 외부 조회는 트랜잭션 밖에서 하고, 상세·공급 파싱 및 주택 연결을
   완료한 뒤 공고·공급행·금액·일정·원천 연결을 한 트랜잭션으로 반영한다. 실패하면 기존 제품 상태를 유지한다.
   두 API의 성공은 같은 시점의 외부 스냅샷이라는 보장이 아니므로 충돌하는 값은 보류 사유로 남긴다.
6. **누락·미확정을 임의 값으로 채우지 않는다.** 현재 제품은 접수 시작·종료·당첨자 발표일을 필수로 요구한다.
   초기 LH 단독 도입은 필수값과 개정 관계가 검증된 공고만 공개하고 나머지는 원천과 보류 사유를 보존한다.
   미확정 날짜도 공개하려면 nullable/일정 상태와 화면 표시·정렬·필터 계약을 별도로 바꾸어야 한다.

## 5. 실행 순서와 각 단계의 종료 조건

| 순서 | 작업 | 주요 영향 파일/영역 | 종료 조건 |
|---|---|---|---|
| 1 완료 | 직접 수집 동시성 8, 공통 잠금, 타임아웃·장애 차단 | 수집 서비스, 외부 클라이언트, 실행 잠금, 설정 | 같은 166회가 160.7초→41.1초, 원천 내용·연결 동일. 전체 강제 옵션은 별도 |
| 2 | LH 필드·연결 감사 | 상세 Source/Parser, 목록 후보 해석 | 위 5건의 필수값/기존 관계를 공개·정정·보류로 분류, 실응답 fixture 확보 |
| 3 | LH 독립 원천 수집 | CandidateResolver/Collector, 요청 체크포인트·출처 연결 | 마이홈에 없어도 검증된 LH 후보 수집, 재실행 중복 0, 기존 마이홈 11건 보존 |
| 4 | LH 입력 정제와 원자적 제품 반영 | 기존 mapping/enrichment 입력·Writer, Announcement 출처 연결 | LH→마이홈 후속 유입, 다중 단지·정정·취소·한 API 실패 검증, 임의값 없는 공개 |
| 5 | 운영 적용과 재측정 | Flyway, 실행 보고서·기존 메트릭 | 목록/상세/공급/정제 시간, 요청·실패·보류·SQL 수 확인 후 범위 확대 판단 |

속도와 데이터 확장은 각각 검증·반영할 수 있는 변경으로 나눈다. 첫 변경에서 기존 수집 대상과 제품 데이터를
유지한 채 직접 수집 속도를 먼저 개선한다. 필수 데이터/API 변경은 구체적 diff와 마이그레이션을 검토한 뒤 적용한다.
