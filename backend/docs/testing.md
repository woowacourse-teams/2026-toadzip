# Testing Strategy

> 현재는 기본 규칙만 확정한다. 세부 테스트 전략과 fixture·대역 기준은 추후 팀 합의로 확장한다.

## 테스트 피라미드

| 대상 | 기본 형태 | 검증 내용 |
|---|---|---|
| Domain | 빠른 단위 테스트 | 행위, 불변식, 경계값 |
| Application | 유스케이스 테스트 | 흐름, Port 협력, 실패 전파 |
| Web | 계약 테스트 | 검증, 상태, 오류 매핑 |
| Persistence | DB 통합 테스트 | 매핑, 쿼리, 제약조건 |
| External | 계약·통합 테스트 | 요청, 응답, timeout, 변환 |

## TDD 계약

1. 요구 행동 하나를 나타내는 최소 실패 테스트를 작성한다.
2. 빠진 행동 때문에 실패하는지 직접 실행해 확인한다.
3. 정상 경로와 합의된 오류 경로를 포함한 최소 구현을 만든다.
4. 새 테스트와 관련 기존 테스트가 통과하는지 확인한다.
5. Green 상태에서만 구조를 개선하고 다시 실행한다.

## 테스트 작성

- 구현 세부사항보다 공개 행동과 결과를 검증한다.
- 테스트 이름은 조건과 기대 행동을 드러낸다.
- 하나의 테스트는 하나의 동작만 검증하고 Given-When-Then을 권장한다.
- 테스트 준비 코드에는 객체지향 생활체조를 유연하게 적용한다.
- 시간, 난수, ID와 외부 시스템은 제어 가능한 경계로 주입한다.
- 실제 경계가 중요한 곳을 무분별한 mock으로 대체하지 않는다.
- 같은 fixture가 의도를 가리면 테스트별 최소 데이터로 줄인다.

## 오류와 회귀

- 버그는 실제 증상을 재현하는 테스트로 시작한다.
- 입력 경계, 부재, 중복, 권한, timeout과 외부 실패를 검증한다.
- 예외 타입만 보지 않고 상태 변화와 외부 효과를 함께 확인한다.
- flaky test는 재실행 성공으로 통과시키지 않고 원인을 격리한다.

## 실행 순서

```text
가까운 테스트 → 기능 테스트 묶음 → ./gradlew check
```

환경 때문에 실행하지 못한 검사는 실패와 구분해 미검증으로 보고한다.
