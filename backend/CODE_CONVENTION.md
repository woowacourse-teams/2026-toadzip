# Backend Code Convention

이 문서는 Toadzip 백엔드 코드의 일관성, 가독성과 객체지향 설계를 위한 기준을 정의한다.

## 1. 적용 범위

- 대상은 `backend/src/main/java`와 `backend/src/test/java`의 Java 코드다.
- 모든 Java 코드는 Google Java Style Guide와 프로젝트 예외 사항을 따른다.
- 객체지향 생활체조는 도메인과 비즈니스 코드에 우선 적용한다.
- DTO, JPA, 프레임워크 연동 및 테스트 준비 코드에는 객체지향 생활체조 규칙을 일부 적용하지 않을 수 있다.
- 객체지향 생활체조 규칙을 적용하지 않은 이유가 명확하지 않다면 PR에 근거를 작성한다.

## 2. Google Java Style Guide

[Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)를 기본 코드 스타일로 사용한다.

다음 항목은 Google Java Style과 다르게 적용한다.

- 블록 들여쓰기는 스페이스 네 칸을 사용한다.
- 한 줄은 120자를 넘지 않는다.
- 줄을 바꿀 때는 기존 줄보다 스페이스 여덟 칸 이상 들여쓴다.

## 3. 객체지향 생활체조

객체지향 생활체조(Object Calisthenics)는 작은 객체와 명확한 책임을 만들기 위한 연습 규칙이다. Toadzip에서는 절대적인 제약이 아닌 기본 설계 원칙으로 사용한다.

1. **메서드당 한 단계의 들여쓰기만 사용한다.**

   조건문과 반복문을 중첩하지 않고 빠른 반환과 메서드 추출을 사용한다.

2. **`else`를 사용하지 않는다.**

   빠른 반환, 예외 처리 또는 다형성으로 조건 분기를 단순화한다.

3. **도메인 의미를 가진 원시 값과 문자열을 포장한다.**

   이름, 제목, 금액처럼 의미나 검증 규칙이 있는 값은 값 객체로 표현한다. 반복문 인덱스, 계산용 지역 변수와 DTO 값은 제외할 수 있다.

4. **컬렉션을 일급 컬렉션으로 만든다.**

   도메인 규칙이나 행위를 가진 컬렉션은 별도 클래스로 포장하고 컬렉션 외의 상태를 두지 않는다.

5. **한 줄에 하나의 점만 사용한다.**

   객체의 내부 구조를 연속해서 탐색하지 않고 필요한 행위를 객체에 요청한다. Stream, 빌더, 테스트와 프레임워크 DSL은 예외로 한다.

6. **이름을 축약하지 않는다.**

   이름만 보고 역할을 이해할 수 있게 작성한다. `API`, `URL`, `ID`, `DTO`, `JPA`처럼 의미가 명확한 기술 용어는 허용한다.

7. **클래스와 메서드를 작게 유지한다.**

   메서드는 한 가지 일, 클래스는 하나의 책임만 가진다. 메서드가 10줄, 클래스가 50줄을 넘으면 책임 분리를 검토한다.

8. **도메인 클래스의 인스턴스 변수는 두 개 이하를 지향한다.**

   필드가 많다면 값 객체로 묶거나 책임을 분리한다. JPA Entity, Aggregate Root, DTO와 설정 객체는 예외로 할 수 있다.

9. **무분별한 getter와 setter를 사용하지 않는다.**

   상태를 외부에서 판단하거나 변경하지 않고 도메인 객체에 행위를 요청한다. DTO, record, 직렬화와 JPA 연동은 예외로 한다.

## 4. 프로젝트 규칙

- 삼항 연산자를 사용하지 않는다.
- 배열보다 컬렉션을 우선한다. `byte[]`, 가변 인자와 외부 API 연동은 예외로 한다.
- 사용하지 않는 import를 허용하지 않는다.
- 의존성은 생성자로 주입한다.
- Controller는 요청 검증과 응답 변환, Service는 유스케이스 흐름과 트랜잭션, Repository는 데이터 접근을 담당한다.
- Entity를 API 응답으로 직접 반환하지 않는다.

## 5. 테스트 규칙

- 테스트 이름에 검증하려는 동작을 드러낸다.
- 하나의 테스트는 하나의 동작만 검증한다.
- 테스트는 Given-When-Then 구조를 권장한다.
- 테스트 준비 코드에는 객체지향 생활체조를 유연하게 적용할 수 있다.
