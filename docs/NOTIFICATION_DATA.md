# 알림 신청 데이터와 스키마 점검

현재 서비스는 신청 목록을 관리한다. 이메일 발송과 새 공고의 대상 매칭은 자동화하지 않는다.
운영자가 수동으로 확인할 수 있는 [유효 신청 이메일 조회 쿼리](queries/active-notification-recipients.sql)만 제공한다.
쿼리 결과에는 개인정보가 있으므로 승인된 담당자만 조회하고 공개 로그·저장소에 남기지 않는다.

## 저장 구조

| 마이그레이션 | 변화 |
| --- | --- |
| `V20260927_01` | 노출, 클릭, 신청, 창 닫기 이벤트를 누적하는 `notification_interest_events` 생성 |
| `V20260928_01` | `users.email`, 이벤트의 `email` 컬럼 추가 |
| `V20260929_01` | 이벤트의 `CANCELLED` 값 허용 |
| `V20260929_02` | 로그인 계정의 이메일 설정과 대상별 신청 상태 테이블 추가 |
| `V20260929_03` | 비로그인 브라우저의 이메일 설정과 대상별 신청 상태 테이블 추가 |

신청은 대상 종류와 ID별 행의 `active=true`로, 취소는 같은 행의 `active=false`로 저장한다.
이벤트 이력은 별도로 남는다. 계정의 이메일 설정은 `user_id`, 비로그인 설정은 브라우저에 저장한
임의의 `client_id`로 구분한다. 비로그인 사용자가 다른 기기에서 같은 이메일을 입력해도
동일인으로 연결하지 않는다. 로그인 계정은 다른 기기에서 서버 상태를 조회하며, 열린 창은 다시
포커스될 때 상태를 갱신한다.

과거 이벤트에는 계정 ID나 브라우저 `client_id`가 없어 새 신청 목록에 안전하게 자동 연결할 수 없다.
기존 신청자는 새 버전에서 다시 신청해야 유효 목록에 들어간다.

이 테이블은 주 PostgreSQL DB에 둔다. `users`, 지역·단지·공고가 주 DB에 있어 같은 트랜잭션에서
대상 유효성 검사와 신청 상태 변경을 처리하고 계정 FK를 걸 수 있다. 별도 공유 DB에 놓으면
이 데이터와의 FK와 단일 DB 트랜잭션을 사용할 수 없다. 공유 DB 설정은 알림 기능에서 사용하지 않는다.

## 개발·운영 DB 확인

`develop` 병합은 개발 서버의 코드 배포 대상, `main` 병합은 운영 서버의 코드 배포 대상이다.
병합만으로 DB는 바뀌지 않는다. 각 서버에서 새 백엔드를 기동하면 해당 서버의 `.env`가 지정한
`PRIMARY_DB_HOST`, `PRIMARY_DB_PORT`, `PRIMARY_DB_NAME`의 주 DB에 Flyway가 적용된다.
개발과 운영의 DB 접속값은 별도로 관리하며 데이터가 서로 복사되지 않는다.

배포 전에는 **각 환경의 실제 주 DB**를 백업하고 복제본에서 앱 기동을 시험한다. 특히 Flyway 이력이
없는 기존 DB라면 스키마와 `uk_users_login_identifier` 제약을 [도입 절차](../backend/docs/flyway-adoption.md)와
대조한다. 자동 기준선은 이력이 없는 비어 있지 않은 DB에 `20260922.00`을 기록한 뒤 후속 `V`를
적용한다. 이미 이력이 있으면 미적용 `V`만 실행한다. 빈 DB에는 `B20260922_01`과 후속 `V`가 적용된다.

각 서버에서 DB 접근 권한이 있는 담당자는 배포 전후 다음 읽기 전용 쿼리를 실행한다.
비밀번호는 명령이나 저장소에 적지 않고 `psql` 프롬프트에서 입력한다.

```shell
psql "host=<PRIMARY_DB_HOST> port=<PRIMARY_DB_PORT> dbname=<PRIMARY_DB_NAME> user=<PRIMARY_DB_USERNAME>" \
  -X -W -v ON_ERROR_STOP=1 -f docs/queries/notification-schema-status.sql
```

출력의 DB 이름·서버 주소·포트가 의도한 환경과 같은지 먼저 확인한다. 배포 후에는
`history_present=true`, 버전 `20260927.01`부터 `20260929.03`까지 모두
`applied_successfully=true`, 이력의 `success=false`가 없음, 관련 테이블·컬럼·취소 제약이
모두 `true`인지 확인한다. 이력이 없거나 값이 예상과 다르면 앱 배포를 진행하지 않고
복제본에서 원인을 확인한다. 저장소에는 실제 개발·운영 DB에 대한 연결 정보나 실행 이력이 없어
문서만으로 완료 여부를 단정할 수 없다.
