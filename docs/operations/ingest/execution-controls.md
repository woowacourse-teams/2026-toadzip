# 관리자 수집 실행 제어

## 진행 확인

- 진행 바는 현재 수집 범위의 실제 완료 대상 수 / 전체 대상 수다. 단계 수는 별도 텍스트로 표시한다.
- `workProgress`는 범위 이름·단위·완료/전체 수·범위 시작/최근 완료 시각을 저장한 스냅샷이다.
  마이홈 단지는 전체 지역, LH 목록은 페이지,
  LH 공급/상세는 최신 LH 공고목록에서 정한 이번 실행의 고유 요청을 센다. 대상 요청은 매 실행 실제 조회한다.
  실패가 확정된 대상도 처리 완료로 세며, 재시도는 같은 대상을 중복 완료하지 않는다.
- 예상 남은 시간은 `범위 경과 시간 / 완료 대상 수 × 남은 대상 수`로 계산한다.
  병렬 처리·재시도·저장 시간도 실제 경과 시간에 포함된다. 전체 파이프라인 종료 시각은 아니며,
  화면에 표시한 범위 이후의 작업량은 포함하지 않는다.
- 2개 미만 처리했으면 속도 계산 중, 전체 수가 -1이면 전체 대상 확인 중으로 표시한다.
  최근 완료 이후 60초 또는 평균 대상 처리 시간의 3배를 넘기면 지연으로 보고 추정을 보류한다.
  중지 요청·종료 시에는 예상 시간을 표시하지 않는다.
- `externalRequestCount`는 실행 전체의 외부 요청 처리 횟수이며 실패·재시도를 포함한다.
  `lastRequestDescription`, `lastProgressAt`으로 최근 요청과 활동을 확인한다.
- 전체 수집 건수를 모르는 구간에 예상 퍼센트나 남은 시간을 표시하지 않는다.
- 진행 상태와 중지 요청은 DB에 저장하므로 새로고침하거나 다른 서버에서 조회해도 유지된다.

## 관리자 탐색

- `/admin`은 운영 홈(`/admin/operations`)으로 이동한다. 공고 수집은 `/admin/ingest/announcements`,
  단지 수집은 `/admin/ingest/complexes`다. 기존 `/admin/ingest`·`/admin/ingest-v2`는 해당 도메인의 새 경로로 연결한다.
- 수집 화면의 기본 작업은 `공고 갱신`이다. 기존 공고 수집·정제 통합 실행을 사용하며, 수집 또는 정제만 실행하려면 `공고 추가 작업`을 펼친다.
- 단지 화면은 원천 수집과 위치정보 ZIP 업로드를 실행한다. 단지 정제는 [지원을 종료](../../features/ingest/executions.md#실행-방법)해 정제·저장 탭과 오류 화면의 단지 재정제 버튼은 비활성이며 지난 결과만 보인다.
- 기존 공고의 단지 연결을 다시 시도하려면 공고 추가 작업의 정제를 실행한다.
- 공고 입력은 직접 입력 폼만 연다. 예전 JSON 입력 주소(`?mode=json`)로 들어와도 직접 입력을 연다.
- 단지 저장 후 연결 링크로 직접 공고 입력에 진입한다. 단지 정보는 기존 상세 API에서 확인하므로
  새로고침·직접 접근도 가능하며 조회 실패나 확인 전에는 공고 저장을 막는다.

## 수집 실패 뒤 정제 복구

- 통합 실행은 수집 부분 실패·호출 제한에서 자동 정제를 시작하지 않는다.
- 결과의 `저장된 원천으로 공고 정제 실행`으로 공고 정제만 새로 실행한다. 현재 저장된 원천 전체를 사용하므로 이전 수집 원천이 포함될 수 있다.
- 정제 중에는 통합·독립 실행과 다른 복구 버튼을 잠근다. 현재 수집 화면은 복구 실행을 새 현재 작업으로 표시하며 이전 결과는 실행 이력에서 확인한다.
- 통합 실행 결과에서 수집 요청·정제 행·LH 보강 실패 목록을 각각 열 수 있다. 정제가 이미 시작된 실행에는 정제 미실행 안내를 표시하지 않는다.

## 실행 중지

`POST /api/admin/ingest/pipelines/executions/{executionId}/stop`은 관리자 세션과 CSRF 토큰이 필요하다.

- 요청은 `202`와 실행 상태를 반환한다. `RUNNING + stopRequested=true`는 중지를 기다리는 상태다.
- 수집은 다음 외부 요청·재시도 또는 다음 작업 시작 전에 중지 여부를 확인한다.
- 진행 중인 외부 응답과 저장은 강제로 끊지 않는다. 병렬 작업을 모두 마친 뒤 `STOPPED`로 저장하고
  실행 잠금을 해제한다. 그 전까지 다른 수집·정제는 시작할 수 없다.
- 정제는 현재 단계가 끝난 뒤 다음 단계 진입을 막는다. 단계 내부 중간에 중지하지 않으므로
  메모리에 모은 행별 실패 보고서의 저장을 마칠 수 있다.
- 이미 저장된 원천과 완료 단계 보고서는 보존한다. 아직 저장되지 않은 수집 버퍼는 버린다.
- 중복 요청은 같은 중지 상태를 반환한다. 이미 종료된 실행의 결과는 변경하지 않는다.
- 실제 오류가 발생한 실행은 `FAILED`로 남을 수 있다. 서버 소실 복구는 기존 heartbeat 정책을 따른다.
- `STOPPED` 수집은 정제를 시작하지 않는다. 재실행은 새 실행이다.

## 실패 확인

- 외부 API 수집 실패는 요청 단위이며, 정제·보강 실패는 원천 행 단위다.
- LH·SH·GH 공고 정제 실패는 `refinement`(기관 공고 정제) 분류로 공고 실패에 쌓는다. 키는 SH·GH 공고 원천 식별자(`SH:{seq}`, `GH:{pbancNo}`), LH 공고목록 원천 키, 또는 정제할 원천을 읽지 못한 묶음 이름(`SH 페이지 {seq}` 등)이다. 사유는 `SOURCE_LOOKUP_FAILED`(원천 읽기)와 `SOURCE_REFINEMENT_FAILED`(원천 하나 정제)이고, 상세는 보고서 설명 뒤에 예외 종류를 붙인다. 정제 실행이 끝날 때 그 기관에서 이번에 다시 다룬 키의 지난 실패 중 다시 나오지 않은 것만 해결로 바꾸며, 다른 기관이나 이번에 다루지 않은 원천의 실패는 그대로 둔다. 묶음 읽기 실패의 키는 페이지·묶음의 첫 원천으로 만들어 실행마다 달라지므로, 그 기관의 수집이 실패한 요청 없이 모든 요청을 읽은 실행에서만 키와 상관없이 지난 묶음 읽기 실패를 해결로 바꾸고 이번에 다시 난 것만 남긴다. 호출 제한·호출 상한·실패한 요청으로 멈춘 실행이나 원천 저장 실패·중지 요청 등 예외로 멈춘 실행은 그때까지 본 정제 실패를 기록하되, 지난 묶음 읽기 실패는 건드리지 않는다. SH·GH는 원천 식별자로, LH는 공고 ID(`panId`)가 같은 가장 최근 공고로 제품을 잇는다.
- 화면은 기존 페이징 API로 미해결 목록 또는 해결된 항목을 포함한 이력을 20개씩 조회한다.
- `/api/admin/ingest/failure-reviews`는 `keyword`(최대 200자)와 `executionId`(UUID)를 선택 조건으로 받는다.
  검색은 현재 원천명·제품명·원천 식별자·LH 공고 번호의 부분 일치이며 `%`, `_`도 문자로 검색한다.
  실행 필터는 마지막 발생 실행(`lastExecutionId`) 기준으로 전체 건수와 페이지에 함께 적용한다.
  최초 발생 이력 전체를 검색하는 조건은 아니다. 화면에서 실행 필터를 해제할 수 있다.
- 대상 식별자·공급행 번호·사유·상세 설명·최근 발생 시각을 먼저 보여주고 원본 JSON은 접어서 제공한다.
- API 실패를 빈 목록으로 바꾸지 않고 재시도 안내를 표시한다.
- 오류 상세의 좌표 문제는 ZIP 업로드·단지 정제로, 단지·주택형 문제는 단지 관리로 연결한다. 수정 후 오류 화면에서 재정제할 때는 선택한 오류 한 건이 아니라 해당 도메인의 저장된 원천 전체를 처리한다.
- 상세는 원인·근거 → 조치 → 결과 확인 순서다. 전체 정제는 범위를 확인한 뒤 실행하며,
  공고 하나의 LH 상세·공급 강제 재조회는 LH 공고 ID(`panId`)로 그 공고의 최신 공고목록 요청만 처리한다.
- `/api/admin/ingest/failure-reviews/{category}/{id}`는 목록 필터와 별개로 선택한 기록과 현재 서비스 데이터를 조회한다.
  해결된 오류가 미해결 목록에서 빠져도 상세를 유지한다. 존재하지 않는 기록은 404이며 관리자 권한이 필요하다.
- 실패 검토 응답의 `lastResolvedBy`는 관리자가 PDF 보정으로 공고의 실패를 해결했을 때 그 관리자다. 정제가 해결했거나 수집 실패이면 `null`이며, 정제가 다시 해결하면 비운다.
- 선택한 기록은 `failure=분류:ID`로, 수정·원천 화면의 복귀 경로는 `failureReturnTo`로 보존한다.
  복귀 후 최신 상태를 다시 조회한다. 실행 완료, 오류 해결, 서비스 데이터 등록·노출 조건과 관리자 검토 완료는 서로 다르다.
  결과 조회가 실패하면 이전 표시값을 최신 결과로 판단하지 않도록 안내하고 재처리를 막는다.

## 공급행의 수동 연결 저장

지원을 종료했다. 공고는 LH 공고 정제와 PDF 보정으로만 바뀐다. 공고 수집은 마이홈 공고를 수집하지 않는다.
관리자 화면의 `여기서 바로 복구`, `이 공고만 다시 정제`와 공급행 제외·해제 화면은 없앴다.
공고의 단지·주택형 매칭 오류는 오류 상세에서 단지 후보 검색이나 PDF 보정으로 확인한다.

API 기준 경로는 `/api/admin/ingest/announcement-supply-matches`다.
`POST /{identifier}/refine`·`/rerun`·`/release`·`/exclusion`·`/split`과 공급행 대응 조회 `GET /{identifier}`는 없앴다.
남은 조회는 단지 후보 `GET /complexes`와 주택형 후보 `GET /complexes/{complexId}/housing-types`다.
관리자 화면은 PDF 보정·공급정보 편집표의 주택형 후보 조회에 `GET /complexes/{complexId}/housing-types`만 쓴다.

## LH 공급 원본 연결

지원을 종료했다. 실패 검토의 `LH 행 연결` 버튼과 `/admin/failures/lh-links/{identifier}` 화면은 없앴다.
`/api/admin/ingest/announcement-supply-matches/{identifier}/lh-links`(GET·POST)와 `/lh-links/release`는 없앴다.
LH 공급 원본을 공고 공급표로 쓰는 규칙은 [LH 공고 연결](../../features/ingest/lh-linking.md)을 따른다.

LH 공급 원본 행은 공급표를 정하지 않는다. 공급정보 편집표는 원천 행을 `LH·GH 원천 참고`로만 보이고, 주택형 추가를 막지 않는다.

## 한 원천에서 복수 공급행 보정

원천 한 행을 여러 공급행으로 나누는 `이 원천을 여러 공급행으로 나누기`와 공고 상세의 `원천별 공급행 보정`은 지원을 종료했다.
`POST /api/admin/ingest/announcement-supply-matches/{identifier}/split`은 없앴다.

- 공개 공급행 응답의 선택적 `sharedRecruitment`는 `{id, householdCount}`다. `id`는 여러 주택형이 함께 쓰는 모집수 묶음(`supply_quotas`)의 ID다.
  같은 `id`의 수량은 공고·단지 합계에서 한 번만 더한다. 개별 행은 세대수 미확정으로 표시한다.

공식 공고를 근거로 공통 단지·주택형 정보도 관리자 검토 후 수정할 수 있다.
해당 공고의 A/B 명칭·모집조건과 여러 공고가 공유하는 공통 이름·면적을 구분한다.
공통정보는 기존 관리자 수정 경로를 사용하며 관리자 수정값의 마이홈 재수집·재정제 보호를 유지한다.
추후 PDF 매칭도 확인된 값·적용 범위·근거를 이 경로에 전달하며 자동으로 공통정보 전체를 덮지 않는다.

## 배포

- `V20261114_01__supply_sheet_only.sql`은 공고 공급정보를 공고 공급표 하나로 남기고 옛 구조를 지운다.
  공급표 투영 트리거·함수, `supply_targets`·`supply_target_count_groups`·`supply_row_groups`·`supply_row_housing_types`·
  `lh_supply_row_links`·`announcement_supply_match_decisions`, 공급행의 옛 모집수·대상 비교·대응 열을 지운다.
  지우기 전에 여러 주택형을 함께 가리키던 공급행은 주택형마다 한 행으로 나누고, 원래 행의 칸·수량 묶음·임대조건을 함께 쓰게 한다.
  되돌릴 수 없으므로 적용 전에 DB 백업을 확인하고, 적용 뒤에는 구버전 서버로 되돌리지 않는다.
  아래 옛 마이그레이션 항목의 테이블은 이 마이그레이션 뒤에는 없다.

- `V20261019_04__supply_row_groups.sql`은 원천별 공통 모집수·보정 근거와 공급행의 그룹 참조를 추가한다.
  기존 공급행은 그룹 없이 유지한다. 그룹에 속한 행에 개별 모집수를 중복 저장하는 것은 DB 제약으로 거절한다.
  구버전 서버에는 이 보정의 재정제 보호가 없으므로 보정 생성 이후 구버전 정제 작업을 실행하지 않는다.

  `V20261024_04__lh_supply_link_review_reason.sql`은 LH 보강 오류 사유 제약에
  `LH_SUPPLY_LINK_REVIEW_REQUIRED`를 추가한다. 새 사유가 기록된 뒤에는 구버전 서버로 즉시 되돌리지 않는다.
  구버전 서버는 저장 연결을 읽지 않으므로 연결 저장 이후 구버전 정제를 실행하면 해당 LH 행이 다시 단지 미발견으로 남는다.

- `V20261019_02__announcement_supply_match_decisions.sql`은 원천 공급행별 수동 연결·근거를 보관한다.
  대상 삭제 시 참조를 NULL로 바꿔 재확인 대상으로 남긴다.
- `V20261019_03__manual_supply_match_review_reason.sql`은 기존 오류 사유 제약에
  `MANUAL_MATCH_REVIEW_REQUIRED`를 추가한다. 과거 마이그레이션 파일과 적용 이력은 수정하지 않는다.
  새 사유가 기록된 뒤에는 이를 읽지 못하는 구버전 서버로 즉시 되돌리지 않는다.


실행을 종료한 뒤 서버·관리자 화면을 함께 교체한다. 실행 상태·실패 사유의 구버전 호환성과 롤백은 [파이프라인 배포·복구](../../features/ingest/executions.md#배포와-복구)를 따른다.

## 수집 키

공공데이터포털 수집 키는 서버 설정 `ingest.service-key`(환경변수 `DATA_GO_KR_SERVICE_KEY`)만 사용한다.
관리자 화면은 키를 입력받지 않고 수집을 한 번에 시작한다.

- `POST /api/admin/ingest/pipelines/{type}`은 본문을 받지 않는다. 본문을 보내면(예전 화면의 `{ "serviceKey": "..." }` 포함)
  값을 쓰거나 응답에 되돌리지 않고 HTTP 400 `INVALID_INGEST_REQUEST`로 거절한다. 키를 입력하던 낡은 화면이
  조용히 서버 키로 실행되지 않고 실패하게 하려는 것이다.
- `complex-collection`, `announcement-collection`, `announcement-sync`는 서버 키가 비어 있으면 잠금과 실행 기록 전에
  HTTP 503 `INGEST_SERVICE_KEY_MISSING`으로 거절한다. 정제와 SH 수집은 키 없이 실행한다.
- `GET /api/admin/ingest/pipelines/readiness`는 `{ "serviceKeyConfigured": true|false }`만 돌려준다. 화면은
  `false`이면 "서버 수집 키 미설정"을 알리고 공공데이터포털 수집 버튼을 막는다. 조회에 실패하면 막지 않는다.
- 공공데이터포털이 키를 거부하면(HTTP 401·403, 게이트웨이 사유 코드 20·30·31·32) 요청 실패 사유에
  "서버 수집 키를 거부했습니다"와 `DATA_GO_KR_SERVICE_KEY` 확인 안내를 남긴다. 키 값과 요청 URL은 메시지·원인 예외·
  실행 이력에 남기지 않는다. 키 거부는 요청마다 기록되며 단계를 즉시 멈추지 않는다.
- 기존 관리자 인증과 CSRF 검사를 그대로 적용한다.

## 자동 실행

`INGEST_AUTO_COLLECTION_ENABLED=true`이면 서버가 LH 공고 갱신(`announcement-sync`), SH·GH 공고 수집을 스스로 시작한다.
기본값은 꺼짐이다. 관리자 실행과 같은 실행·잠금·이력·실패 기록을 쓰고, 이력에는 `자동`(LH는 `자동 · 최근분`·`자동 · 전체`)으로 보인다.

- 서버 시작 2분 뒤부터 10분마다(`INGEST_AUTO_COLLECTION_CHECK_INTERVAL`) 최근 실행 기록을 읽어 하나만 시작한다.
  마지막 성공에서 3시간(`INGEST_AUTO_COLLECTION_INTERVAL`)이 지난 유형이 대상이고, 여럿이면 가장 오래 성공하지 못한 유형부터 한다.
  서버가 멈춰 여러 번을 놓쳐도 밀린 횟수만큼 돌리지 않고 한 번만 따라잡는다.
- 관리자 실행도 성공·실패로 센다. 관리자가 방금 돌렸으면 자동 실행은 그만큼 미뤄진다.
- 마지막 성공 뒤 실패(`FAILED`·`COMPLETED_WITH_SKIPS`·`STOPPED`)가 이어지면 마지막 시도에서 10분, 30분, 60분(이후 60분)을 기다린다.
  호출 제한으로 건너뛴 실행도 실패로 세어 한도가 풀릴 때까지 자주 부르지 않는다.
- 대상 일부만 실패한 실행(`FAILED`, 실패 원인 `PARTIAL`)은 자동 실행에서 성공으로 센다(전체 수집 시점 포함).
  실패한 단계에서 성공한 대상이 없으면(`ALL_TARGETS_FAILED`) 실패로 세어 경보가 잡는다.
  나머지는 처리했고 대상별 실패는 실패 검토 목록에 남기 때문이다. 원천 공고 하나가 계속 정제에서 거절되어도
  경보가 계속 울리거나 LH가 매번 전체로 받지 않는다. 그 공고는 실패 검토 목록에서 처리한다.
- 자동 실행은 전용 스케줄러(`auto-run-` 스레드 2개)에서 확인한다. 공고문 PDF 자동 추출도 같은 스케줄러를 쓴다.
- 다른 실행이 잠금을 잡고 있으면 이번 확인은 실행 기록 없이 건너뛰고 다음 확인에서 다시 본다.
- LH는 마지막 전체 성공에서 7일(`INGEST_AUTO_COLLECTION_FULL_INTERVAL`)이 지나지 않았으면 최근분만 받는다.
  최근분은 접수 중·마감 전 공고와 마감 뒤 3일(`LH_ANNOUNCEMENT_INCREMENTAL_ENDED_WINDOW`) 안의 공고 중
  공급·상세를 받아 정제까지 마친 뒤 공고목록 행(이름·상태·공고일·마감일 등)이 바뀐 공고와, 아직 마치지 못한 공고다.
  새 공고, 받다 실패한 공고, 정제가 실패한 공고, 수집만 하고 정제하지 않은 공고는 다음 증분 실행이 다시 받는다.
  상세가 아직 비어 있거나 접수·당첨자 발표 일정이 없어 공고를 만들지 못한 공고와, 원공고를 아직 찾지 못한 정정·취소공고도
  마친 것으로 보지 않아 매 증분 실행이 다시 받는다(공고마다 2회).
  목록 행은 그대로인 채 공급·상세만 바뀐 공고는 주 1회 전체 실행이 받는다. 그래서 이런 변경은 최대 7일 늦게 반영된다.
  증분 실행은 대상이 몇 건뿐이라, 공급·상세·정제 중 한 부분의 대상이 모두 실패해도 실패가 한 건뿐이면
  `ALL_TARGETS_FAILED`가 아니라 `PARTIAL`로 센다. 계속 실패하는 공고 하나만 다시 시도해도 연속 실패로 세지 않게 하려는 것이다.
  받다 실패한 공고는 다음 실행의 대상에 다시 들어가 쌓이므로, 기관 응답이 통째로 고장 나면 곧 두 건 넘게 실패해
  `ALL_TARGETS_FAILED`로 센다. 전체 실행은 실패 수와 관계없이 그대로 판정한다.
  7일이 지나면 마감 뒤 30일까지 받는 전체 실행을 한 번 한다. 공고 목록(최근 2년)은 두 범위 모두 전부 받는다.
  SH·GH는 이미 7일이 지난 상세만 다시 받으므로 범위를 나누지 않는다.
- 서버 수집 키가 없으면 키가 필요한 LH는 건너뛰고 SH·GH만 시작한다.
- 확인할 때마다 유형별 `toadzip_ingest_auto_last_success_seconds`(마지막 성공 시작 시각, 유닉스 초)와
  `toadzip_ingest_auto_failure_streak`(마지막 성공 뒤 실패 수)를 내보낸다. 경보는 [모니터링](../monitoring.md#공고-수집-경보)을 따른다.
- LH 일일 호출 한도는 공공데이터포털 계정에서 확인한다. 로컬에서 LH 전체 한 번은 약 230회, SH 약 40~50회,
  GH 약 38~127회(새 상세가 많을수록 늘어남) 호출했다. LH 최근분은 공고목록 12쪽에 다시 받을 공고마다 2회(공급·상세)를 더한다.
  로컬에서 바뀐 공고가 없을 때 약 15회, 이틀 동안 바뀐 공고를 받은 실행은 43회였다. 로컬 데이터에는 마친 것으로 보지 않는
  공고(계속 실패 1건, 당첨자 발표일 없음 1건, 원공고를 못 찾은 정정공고 1건)가 있어 바뀐 공고가 없어도 약 21회로 본다.
  이 기능을 켠 뒤 첫 최근분은 정제를 마친 기록이 없어 전부(약 200회) 받는다. 3시간마다면 LH는 하루 약 150~200회로 본다
  (하루 바뀌는 공고 수와 마치지 못한 공고 수에 따라 달라지는 추정).
  새 공고는 관리자 검토를 거쳐 공개되므로 3시간 안에 수집되면 공개 시점은 검토가 정한다.
