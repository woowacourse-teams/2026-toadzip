# 관리자 수집 실행 제어

## 진행 확인

- 진행 바는 현재 수집 범위의 실제 완료 대상 수 / 전체 대상 수다. 단계 수는 별도 텍스트로 표시한다.
- `workProgress`는 범위 이름·단위·완료/전체 수·범위 시작/최근 완료 시각을 저장한 스냅샷이다.
  마이홈 단지는 전체 지역, 마이홈 공고는 현재 공급유형의 페이지, LH 목록은 페이지,
  LH 공급/상세는 현재 최대 500개 원천 행 묶음에서 이번 실행에서 아직 처리하지 않은 고유 요청을 센다. 대상 요청은 매 실행 실제 조회한다.
  실패가 확정된 대상도 처리 완료로 세며, 재시도는 같은 대상을 중복 완료하지 않는다.
- 예상 남은 시간은 `범위 경과 시간 / 완료 대상 수 × 남은 대상 수`로 계산한다.
  병렬 처리·재시도·저장 시간도 실제 경과 시간에 포함된다. 전체 파이프라인 종료 시각은 아니며,
  화면에 표시한 범위 이후의 작업량은 포함하지 않는다.
- 2개 미만 처리했으면 속도 계산 중, 전체 수가 -1이면 전체 대상 확인 중으로 표시한다.
  최근 완료 이후 60초 또는 평균 대상 처리 시간의 3배를 넘기면 지연으로 보고 추정을 보류한다.
  중지 요청·종료 시에는 예상 시간을 표시하지 않는다.
- `externalRequestCount`는 실행 전체의 외부 요청 처리 횟수이며 실패·재시도를 포함한다.
  `lastRequestDescription`, `lastProgressAt`으로 최근 요청과 활동을 확인한다.
- 전체 수집 건수를 모르는 구간에 예상 퍼센트나 남은 시간을 표시하지 않는다.
- 진행 상태와 중지 요청은 DB에 저장하므로 새로고침하거나 다른 서버에서 조회해도 유지된다.

## 관리자 탐색

- `/admin`은 운영 홈(`/admin/operations`)으로 이동한다. 공고 수집은 `/admin/ingest/announcements`,
  단지 수집은 `/admin/ingest/complexes`다. 기존 `/admin/ingest`·`/admin/ingest-v2`는 해당 도메인의 새 경로로 연결한다.
- 수집 화면의 기본 작업은 `공고 갱신`이다. 기존 공고 수집·정제 통합 실행을 사용하며, 수집 또는 정제만 실행하려면 `공고 추가 작업`을 펼친다.
- 단지 화면은 원천 수집 → 위치정보 ZIP 업로드 → 정제·저장 순서를 안내한다. ZIP 적재 결과를 확인한 뒤 같은 화면에서 단지 정제를 실행할 수 있다. 업로드 성공만으로 정제가 자동 실행되지는 않는다.
- 단지 정제 결과에서 저장된 단지를 확인하거나 공고 갱신으로 이동한다. 기존 공고의 단지 연결을 다시 시도하려면 공고 추가 작업의 정제를 실행한다.
- 공고 입력은 JSON 가져오기와 직접 입력 중 한 폼만 연다. 선택한 방식과 단지 ID는 URL에 유지한다.
- 단지 저장 후 연결 링크로 직접 공고 입력에 진입한다. 단지 정보는 기존 상세 API에서 확인하므로
  새로고침·직접 접근도 가능하며 조회 실패나 확인 전에는 공고 저장을 막는다.

## 수집 실패 뒤 정제 복구

- 통합 실행은 수집 부분 실패·호출 제한에서 자동 정제를 시작하지 않는다.
- 결과의 `저장된 원천으로 단지/공고 정제 실행`으로 해당 정제만 새로 실행한다. 현재 저장된 원천 전체를 사용하므로 이전 수집 원천이 포함될 수 있다.
- 정제 중에는 통합·독립 실행과 다른 복구 버튼을 잠근다. 현재 수집 화면은 복구 실행을 새 현재 작업으로 표시하며 이전 결과는 실행 이력에서 확인한다.
- 단지 좌표가 부족하면 단지 수집 → `/admin/locations`의 위치정보 ZIP 업로드 → 단지 정제를 실행한다.
- 통합 실행 결과에서 수집 요청·정제 행·LH 보강 실패 목록을 각각 열 수 있다. 정제가 이미 시작된 실행에는 정제 미실행 안내를 표시하지 않는다.

## 실행 중지

`POST /api/admin/ingest/pipelines/executions/{executionId}/stop`은 관리자 세션과 CSRF 토큰이 필요하다.

- 요청은 `202`와 실행 상태를 반환한다. `RUNNING + stopRequested=true`는 중지를 기다리는 상태다.
- 수집은 다음 외부 요청·재시도 또는 다음 작업 시작 전에 중지 여부를 확인한다.
- 진행 중인 외부 응답과 저장은 강제로 끊지 않는다. 병렬 작업을 모두 마친 뒤 `STOPPED`로 저장하고
  실행 잠금을 해제한다. 그 전까지 다른 수집·정제는 시작할 수 없다.
- 정제는 현재 단계가 끝난 뒤 다음 단계 진입을 막는다. 단계 내부 중간에 중지하지 않으므로
  메모리에 모은 행별 실패 보고서의 저장을 마칠 수 있다.
- 이미 저장된 원천과 완료 단계 보고서는 보존한다. 아직 저장되지 않은 수집 버퍼는 버린다.
- 중복 요청은 같은 중지 상태를 반환한다. 이미 종료된 실행의 결과는 변경하지 않는다.
- 실제 오류가 발생한 실행은 `FAILED`로 남을 수 있다. 서버 소실 복구는 기존 heartbeat 정책을 따른다.
- `STOPPED` 수집은 정제를 시작하지 않는다. 재실행은 새 실행이다.

## 실패 확인

- 외부 API 수집 실패는 요청 단위이며, 정제·보강 실패는 원천 행 단위다.
- 화면은 기존 페이징 API로 미해결 목록 또는 해결된 항목을 포함한 이력을 20개씩 조회한다.
- `/api/admin/ingest/failure-reviews`는 `keyword`(최대 200자)와 `executionId`(UUID)를 선택 조건으로 받는다.
  검색은 현재 원천명·제품명·원천 식별자·LH 공고 번호의 부분 일치이며 `%`, `_`도 문자로 검색한다.
  실행 필터는 마지막 발생 실행(`lastExecutionId`) 기준으로 전체 건수와 페이지에 함께 적용한다.
  최초 발생 이력 전체를 검색하는 조건은 아니다. 화면에서 실행 필터를 해제할 수 있다.
- 대상 식별자·공급행 번호·사유·상세 설명·최근 발생 시각을 먼저 보여주고 원본 JSON은 접어서 제공한다.
- API 실패를 빈 목록으로 바꾸지 않고 재시도 안내를 표시한다.
- 오류 상세의 좌표 문제는 ZIP 업로드·단지 정제로, 단지·주택형 문제는 단지 관리로 연결한다. 수정 후 오류 화면에서 재정제할 때는 선택한 오류 한 건이 아니라 해당 도메인의 저장된 원천 전체를 처리한다.
- 상세는 원인·근거 → 조치 → 결과 확인 순서다. 전체 정제는 범위를 확인한 뒤 실행하며,
  LH 보강 오류의 재수집 버튼은 해당 마이홈 공고에 연결된 LH 상세 또는 공급 요청만 처리한다.
- `/api/admin/ingest/failure-reviews/{category}/{id}`는 목록 필터와 별개로 선택한 기록과 현재 서비스 데이터를 조회한다.
  해결된 오류가 미해결 목록에서 빠져도 상세를 유지한다. 존재하지 않는 기록은 404이며 관리자 권한이 필요하다.
- 선택한 기록은 `failure=분류:ID`로, 수정·원천 화면의 복귀 경로는 `failureReturnTo`로 보존한다.
  복귀 후 최신 상태를 다시 조회한다. 실행 완료, 오류 해결, 서비스 데이터 등록·노출 조건과 관리자 검토 완료는 서로 다르다.
  결과 조회가 실패하면 이전 표시값을 최신 결과로 판단하지 않도록 안내하고 재처리를 막는다.

## 공급행의 수동 연결 저장

오류 상세의 `단지·주택형 매칭`에서 원천과 후보를 비교한다. 같은 이름의 주택형은
전용·공급면적과 제공된 타입별 세대수로 구분한다. 단지 전체 세대수와 공고 모집호수는 다른 값이다.

- 기본 `선택 적용·정제 실행`은 이번 정제에만 선택을 사용한다. 기존 요청 계약을 유지한다.
- `이 선택을 저장해 다음 정제에도 사용`을 선택하면 모든 공급행의 주택형을 명시적으로 지정하고
  공식 출처 URL과 확인 근거를 입력해야 한다. 저장 후 같은 오류의 최신 결과를 다시 조회한다.
- 저장한 연결은 후속 공고 정제에서 자동 매칭보다 먼저 사용한다. 연결 판단에 쓰는 원천값이나
  대상 단지·주택형이 바뀌거나 삭제되면 자동 대체하지 않고 `MANUAL_MATCH_REVIEW_REQUIRED`로 표시한다.
  공고명·수집시각만 바뀐 경우에는 연결을 무효화하지 않는다.
- 공고 관리의 공급정보 보정(PDF 보정 포함)에서 원천행이 있는 공급행의 주택형 연결을 바꾸면, 같은 트랜잭션에서
  그 원천행의 저장 매칭을 만들거나 갱신한다. 근거 URL과 이유는 보정 요청의 값을 쓰며 이력은 보정 이력 한 건으로 남긴다.
  연결을 지우면 저장 매칭도 해제한다. 분할 보정 행, 원천이 없는 직접 추가 행, 원천과 공급유형이 다른 단지 연결은 저장하지 않는다.
- 관리자가 수정한 공급행도 저장 매칭이나 이번 선택이 있으면 재정제가 연결을 그 값으로 맞춘다.
  공고 형명·면적·모집수 같은 표기값은 덮어쓰지 않는다. 저장 매칭이 없으면 자동 매칭 결과로 연결을 바꾸지 않는다.
- 마이홈 공고 매핑은 재확인이 필요한 기존 공급행의 연결·원천값을 유지한다. 원천에서 사라진
  수동 연결 행도 삭제하지 않고 현재 원천행 뒤에 표시한다. 원천에서 사라진 행의 별도 재검토·해제 UI,
  모든 공급조건의 수정 보호, 공급행 분할·추가는 이 기능의 범위에 포함되지 않는다.
- 저장한 선택 해제에는 이유가 필요하다. 해제는 저장한 매칭만 제거하고 현재 서비스 데이터는
  변경하지 않는다. 다음 정제부터 자동 매칭을 사용하므로 그 전에 후보와 영향을 확인한다.
- URL과 근거는 관리자가 입력한 기록이다. 서버가 공식 문서 내용이나 실제 대응 관계를 인증하지 않는다.

API 기준 경로는 `/api/admin/ingest/announcement-supply-matches`다.

| 요청 | 계약 |
|---|---|
| `GET /{identifier}` | 현재 공급행의 `token`과 선택적 `savedMatch`(대상 ID, 근거, 작업자·시각, 재확인 여부) 반환 |
| `GET /complexes/{complexId}/housing-types` | 후보의 면적, nullable `householdCount`, 현재 대상의 `token` 반환 |
| `POST /{identifier}/refine` | 기존 `rows`에 선택적 `remember`, `sourceUrl`, `reason`, `splits` 추가. `remember=true`이면 각 행의 `housingTypeId`와 후보의 `targetToken` 필수 |
| `POST /{identifier}/release` | `rowIdentifier`, 최신 행 `token`, `reason`을 받아 선택을 해제하고 최신 공급행 목록 반환 |
| `POST /{identifier}/rerun` | 본문 없음. 선택 없이 저장한 매칭·자동 매칭으로 이 공고만 다시 정제하고 결과 건수를 반환한다. 매칭이나 LH 보강이 하나라도 실패하면 400으로 전체를 되돌리며 실패 기록은 바꾸지 않는다. 원천이 없는 공고도 400이다. 기존 `refine`은 빈 선택을 계속 거절한다. |

두 POST는 관리자 세션·CSRF와 기존 전역 수집·정제 쓰기 잠금을 사용한다. 작업자는 서버 세션으로 결정한다.
조회 뒤 원천·저장 선택·후보가 바뀌면 409로 거절하므로 최신 자료를 다시 비교한다.

`refine`의 `rows`에는 연결을 바꿀 원천행만 보낸다. 보내지 않은 행은 저장한 매칭과 자동 매칭으로
정제하며, `remember`는 보낸 행의 선택만 기억한다. 저장 후 공고의 모든 원천행이 매칭되어야 하므로
보내지 않은 행이 매칭되지 않으면 전체를 거절한다. 조회 뒤 추가된 원천행도 같은 기준으로 판정한다.
분할 보정 그룹에 속한 원천행은 `rows`로 선택할 수 없고, 다른 행의 선택은 그룹을 그대로 유지한다.

`splits`는 `split` 요청과 같은 `rowIdentifier`, `token`, `rows`를 원천행마다 받는다.
연결과 분할을 같은 트랜잭션에서 저장하므로 한 공고의 일부 행은 연결하고 다른 행은 나눌 수 있다.
`splits`가 있으면 `remember`와 관계없이 `sourceUrl`과 `reason`이 필요하다.
같은 원천행을 연결과 분할에 함께 넣거나 두 번 나눌 수 없다. 이력은 `SAVE_SUPPLY_MATCH`와 `SPLIT_SUPPLY`를 남긴다.
공고 한 건의 선택 저장, 정제·LH 보강과 `SAVE_SUPPLY_MATCH` 이력은 같은 트랜잭션으로 처리한다.
중간 실패 시 모두 롤백하며 해제도 `RELEASE_SUPPLY_MATCH` 이력을 남긴다.

## LH 공급 원본 연결

LH 보강 실패 오류 상세의 "1. 원인과 근거 확인"에는 실패한 주택형 비교를 표시한다. 공고명·공고 ID·LH 공고 번호와
공고 원문 링크, 실패한 LH 행의 주택형·전용면적·모집수, 그리고 LH 공급 원본 값과 비교한 공고 공급행 값(단지명·주택형·
연결 단지)을 나란히 보여 주고 다른 칸을 표시한다. 비교 후보는 단지명이 안 맞으면 같은 주택형 공급행, 주택형이 안 맞으면
같은 단지 공급행이다. 이 비교는 조회할 때 현재 원천과 등록 공급행으로 보강 매칭을 다시 해 본 결과이며 저장하지 않는다.
따라서 오류 기록 시점과 다를 수 있다. 비교한 공급행에 단지가 연결되어 있지 않으면 마이홈 단지 매칭이 실패한 상태다.
이때 정제는 LH 연결도 기록하지 않아 재정제로 풀리지 않으므로 `단지·주택형 매칭`부터 안내한다(예: 공고 21391의 대전중촌2).
정제 기준으로는 이미 이어지는 LH 행이면 연결 대신 공고 정제 재실행을 안내하고,
현재 실패가 없으면 이전 정제의 오류임을 알린다. 후보가 있으면 `포함된다면: 이 LH 행을 {단지}에 연결`로 아래 연결 화면을
해당 LH 행과 마이홈 원천행이 선택된 상태로 연다.

오류 상세의 `LH 공급 원본 연결`에서 LH 공급 원본 행과 현재 마이홈 원천행을 비교한다. 이 버튼은 LH 보강 오류의
`COMPLEX_NOT_FOUND`·`AMBIGUOUS_COMPLEX`·`LH_SUPPLY_LINK_REVIEW_REQUIRED`와, 정제 직후 보강이 같은 사유로 실패해
공고 정제 오류(`INVALID_VALUE`, 상세 `LH 보강 실패: {사유} - …`)로 남은 경우에 표시한다.
단지명 표기가 달라 자동으로 붙지 않는 LH 행을 고르고 연결할 마이홈 원천행, 공식 출처 URL, 확인 근거를 입력해 저장한다.
각 LH 행에는 자동 연결·저장 연결 사용 중·재확인 필요·연결 없음 상태를 표시하고, 재확인 필요와 연결 없음 행을 위에 모아
개수를 요약한다. 재확인 행의 `이 연결 다시 확인해 저장`은 이전 연결과 근거 URL을 폼에 채우며 확인 근거는 새로 입력한다. 연결 규칙은
[LH 공고 연결의 관리자가 저장한 LH 공급 연결](../../features/ingest/lh-linking.md#관리자가-저장한-lh-공급-연결)을 따른다.

- 저장·해제는 다음 정제와 LH 보강부터 반영한다. 이미 등록한 공급행은 바로 바꾸지 않으므로 저장 후 공고 정제를 다시 실행한다.
- 연결이 없어 정제가 롤백되어 공고가 아직 없더라도 저장할 수 있다.
- 복수 공급행으로 보정한 마이홈 원천행은 연결 대상이 아니다.
- 해제는 해당 LH 행에서 저장 근거와 별도의 해제 이유를 입력해야 한다. 해제한 LH 행은 다음 정제부터 단지명 자동 연결 규칙을 다시 사용한다.

API 기준 경로는 `/api/admin/ingest/announcement-supply-matches/{identifier}/lh-links`다.

| 요청 | 계약 |
|---|---|
| `GET` | 조회 `token`, 공고(`announcement`: 공고명·원문 URL·LH 공고 번호), 현재 마이홈 원천행(`splitCorrected` 포함), LH 공급행별 현재 연결 원천행(`linkedRowIdentifier`)과 선택적 `savedLink`(근거, 작업자·시각, 재확인 여부), 현재 데이터 기준 보강 매칭 실패(`failures`: LH 행, 사유, 비교 후보 공급행) 반환 |
| `POST` | `token`, `myhomeRowIdentifier`, `lhRowIdentifiers`(1~200), `sourceUrl`, `reason`을 받아 LH 행마다 연결을 저장·갱신하고 최신 조회 결과 반환 |
| `POST /release` | `token`, `lhRowIdentifier`, `reason`을 받아 저장 연결을 삭제하고 최신 조회 결과 반환 |

두 POST는 관리자 세션·CSRF와 기존 전역 수집·정제 쓰기 잠금을 사용한다. 조회 뒤 어느 원천이나 저장 연결이
바뀌면 409로 거절한다. 공고가 없을 수 있어 이력은 `admin_data_changes`에 `LH_SUPPLY_LINK` 자원(연결 ID)으로
`SAVE_LH_SUPPLY_LINK`·`RELEASE_LH_SUPPLY_LINK`를 남기며, 값에 공고 ID와 LH 행 식별자를 함께 기록한다.

## 한 원천에서 복수 공급행 보정

마이홈 공고 API의 원천 한 행이 제품의 주택형 공급행 한 개를 뜻하지는 않는다.
예를 들어 한스빌 API는 주택유형 `아파트`·모집호수170의 한 행이고, 단지 API에는 이름26의 두 타입이 있다.
`이 원천을 여러 공급행으로 나누기`에서 공고에 표시할 A/B 형명과 같은 단지의 서로 다른 주택형을 지정한다.
관리자가 확인한 공식 URL·쪽수 등 근거와 함께 저장한다. 이름이나 면적만으로 A/B 대응을 자동 확정하지 않는다.

- `POST /api/admin/ingest/announcement-supply-matches/{identifier}/split`:
  `rowIdentifier`, 최신 `token`, `sourceUrl`, `reason`, `rows`(2~50개)를 받는다.
  각 행은 `name`, `complexId`, `housingTypeId`, 후보 `targetToken`을 제공한다.
  기존 보정을 수정할 때는 각 행의 `id`를 함께 보내며 기존 행을 누락·중복하거나 다른 보정의 ID를 사용할 수 없다.
- 같은 단지·서로 다른 주택형과 중복되지 않는 공고 형명을 검증한다. 관리자 세션·CSRF·수집 쓰기 잠금을 유지한다.
  원천, 보정, 후보가 바뀐 요청은 거절한다. 반복 전송으로 행을 중복 생성하지 않는다.
- 공통 모집수는 현재 마이홈 원천의 `sumSuplyCo`를 그룹에 한 번만 저장한다.
  A/B 각 행의 모집수는 NULL이다. 170을 각 행에 복제하거나 임의 배분하지 않는다.
  이것은 원천의 합계 보관이며 실제 공동 모집 자격·개별 모집수를 확정한 판정이 아니다.
- 공개·관리자 공급행 응답의 선택적 `sharedRecruitment`는 `{id, householdCount}`다.
  같은 그룹 ID의 수량은 공고·단지 합계에서 한 번만 더한다. 개별 행은 미확정으로 표시한다.
  보정이 없는 공개 공급행은 기존 JSON 모양을 유지한다.
- 보정 행의 ID·공고 형명·주택형 연결은 재정제와 LH 재보강에서 유지한다.
  원천이 사라져도 삭제하지 않는다. 확인한 모집수·원천값 또는 대상이 바뀌면 기존 보정을 유지하며 재확인을 요구한다.
  재확인 저장 때만 새로운 원천의 공통 모집수를 적용한다.
- 오류 상세는 보정 후 같은 오류의 최신 결과를 조회한다. 등록 공고에서는 `공급정보·단지 연결`의
  `원천별 공급행 보정`에서 같은 폼을 사용한다. 저장은 관리자 검토 전체 완료를 뜻하지 않는다.
- 기존 대상 조건이나 관리자 보정값이 있는 일반 공급행을 자동으로 삭제·배분하지 않는다.
  조건 이동을 확인해야 하면 전체 작업을 거절하고 기존 데이터를 유지한다.
  보정된 행을 삭제·합치거나 개별 모집수를 배분하는 동작은 별도 범위다.
- 공고 한 건의 보정·연결·공통 모집수·감사 이력과 LH 검증은 함께 성공하거나 롤백한다.
  신규 등록은 기존 알림 정책을 따르며 기존 공고의 보정은 신규 알림을 만들지 않는다.

공식 공고를 근거로 공통 단지·주택형 정보도 관리자 검토 후 수정할 수 있다.
해당 공고의 A/B 명칭·모집조건과 여러 공고가 공유하는 공통 이름·면적을 구분한다.
공통정보는 기존 관리자 수정 경로를 사용하며 관리자 수정값의 마이홈 재수집·재정제 보호를 유지한다.
추후 PDF 매칭도 확인된 값·적용 범위·근거를 이 경로에 전달하며 자동으로 공통정보 전체를 덮지 않는다.

## 배포

- `V20261019_04__supply_row_groups.sql`은 원천별 공통 모집수·보정 근거와 공급행의 그룹 참조를 추가한다.
  기존 공급행은 그룹 없이 유지한다. 그룹에 속한 행에 개별 모집수를 중복 저장하는 것은 DB 제약으로 거절한다.
  구버전 서버에는 이 보정의 재정제 보호가 없으므로 보정 생성 이후 구버전 정제 작업을 실행하지 않는다.

- `V20261024_01__lh_supply_row_links.sql`은 관리자가 저장한 LH 공급 연결 테이블을 만든다.
  `V20261024_02__lh_supply_link_review_reason.sql`은 LH 보강 오류 사유 제약에
  `LH_SUPPLY_LINK_REVIEW_REQUIRED`를 추가한다. 새 사유가 기록된 뒤에는 구버전 서버로 즉시 되돌리지 않는다.
  구버전 서버는 저장 연결을 읽지 않으므로 연결 저장 이후 구버전 정제를 실행하면 해당 LH 행이 다시 단지 미발견으로 남는다.

- `V20261019_02__announcement_supply_match_decisions.sql`은 원천 공급행별 수동 연결·근거를 보관한다.
  대상 삭제 시 참조를 NULL로 바꿔 재확인 대상으로 남긴다.
- `V20261019_03__manual_supply_match_review_reason.sql`은 기존 오류 사유 제약에
  `MANUAL_MATCH_REVIEW_REQUIRED`를 추가한다. 과거 마이그레이션 파일과 적용 이력은 수정하지 않는다.
  새 사유가 기록된 뒤에는 이를 읽지 못하는 구버전 서버로 즉시 되돌리지 않는다.


실행을 종료한 뒤 서버·관리자 화면을 함께 교체한다. 실행 상태·실패 사유의 구버전 호환성과 롤백은 [파이프라인 배포·복구](../../features/ingest/executions.md#배포와-복구)를 따른다.

## 수집 실행의 일회성 서비스키

관리자의 수동 수집 시작 요청은 선택 JSON 본문 `{ "serviceKey": "..." }`를 받는다.
경로는 `POST /api/admin/ingest/pipelines/{type}`이며 `complex-collection`, `announcement-collection`,
`complex-sync`, `announcement-sync`가 입력키를 받는다. 통합 실행은 같은 실행 범위에서 수집 후 정제를 수행한다.
본문을 보내지 않으면 서버 설정키를 사용한다.

- 본문이 있으면 `serviceKey`가 필수이며 공백만 있는 값과 4096자를 넘는 값은 HTTP 400으로 거부한다.
- 입력키의 양끝 공백을 제거한다. 원문 키와 URL 인코딩된 키를 모두 지원한다.
- 정제 시작에 키 본문을 보내면 HTTP 400 `INVALID_INGEST_REQUEST`로 거부한다.
- 기존 관리자 인증과 CSRF 검사를 그대로 적용한다.

입력키는 해당 비동기 수집 실행과 그 병렬 작업에만 전달한다.
실행별 scope는 닫힐 때 이전 스레드 상태를 복원하고 키가 없던 스레드에서는 제거한다.
입력키를 실행 Entity, 응답 DTO, 실행 로그 맥락이나 요청 조건에 저장하지 않는다.
외부 오류 메시지에 반영된 키를 가리고 요청 URL을 포함할 수 있는 원본 예외는 전파하지 않는다.
입력 DTO의 `toString()`도 키 값을 숨긴다.

브라우저 입력키를 다음 실행에 재사용하지 않는다.
