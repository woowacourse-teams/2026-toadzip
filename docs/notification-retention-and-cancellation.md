# 알림 이메일 보관과 비로그인 취소

## 사용자에게 적용되는 규칙

- 알림 신청은 대상별로 신청하거나 다시 활성화한 때부터 12개월간 유효하다. 기간이 지나면 버튼 상태와 수동 발송 대상 목록에서 빠진다. 계속 받고 싶다면 이메일을 다시 입력해 신청한다.
- 마지막 알림 신청을 종 버튼으로 취소하면 알림용 이메일을 즉시 삭제한다. 비활성화된 로그인 신청 행은 최대 90일 후 삭제한다. 비로그인 신청 행은 이메일 행과 함께 삭제한다.
- 로그인 계정 자체의 이메일(`users.email`)은 계정 정보이므로 알림 신청 취소로 삭제하지 않는다.
- 클릭·신청·취소 이벤트에는 이메일을 저장하지 않는다. 기존 이벤트의 이메일 열도 Flyway 마이그레이션에서 제거한다. 이벤트 행은 90일이 지나면 삭제한다.
- 취소 요청이 완료되면 요청 이메일과 확인 코드 해시를 삭제한다. 미완료 요청은 30일 후 삭제한다. 서버는 15분마다 정리 작업을 실행한다. 이 사이에도 만료된 신청은 조회와 발송 대상에서 제외한다.
- 알림 이메일 자체는 팀이 수동으로 보낸다. 이 기능은 이메일을 자동 발송하지 않는다.

## 브라우저 데이터를 지운 비로그인 사용자

1. `/notifications/cancel`에서 신청 이메일을 입력한다. 신청 여부와 관계없이 같은 접수 응답을 받는다.
2. 관리자는 `/admin/notification-cancellations`에서 요청을 확인하고 일회용 코드를 발급한다. 코드는 발급할 때 한 번만 화면에 표시된다. 관리자가 신청 주소로 직접 보낸 뒤 **이메일 발송 완료 기록**을 누른다. 발송 시각과 관리자 계정이 남으며, 코드는 DB에 원문으로 저장되지 않는다.
3. 사용자가 이메일과 코드를 입력하면 해당 주소의 **모든 비로그인 신청**과 알림용 이메일이 삭제된다. 로그인 사용자의 신청은 영향을 받지 않는다.

코드는 24시간 유효하고 성공 시 한 번만 사용할 수 있다. 잘못된 입력 5회 후에는 사용할 수 없다. DB에는 원문 코드 대신 SHA-256 해시만 저장된다. 관리자는 만료 후 새 코드를 발급할 수 있다. 신분증이나 별도의 신원 자료는 수집하지 않는다.

**코드는 언제 쓰나요?** 브라우저 데이터를 지워 종 버튼으로 취소할 수 없는 **비로그인 사용자**가 알림 중단을 요청할 때만 쓴다. 평소에 종 버튼을 다시 눌러 취소하는 사용자와 로그인 사용자는 코드가 필요 없다. 코드를 입력하기 전까지는 비로그인 신청이 계속 유효할 수 있으므로 팀은 요청을 정기적으로 확인해야 한다.

## 팀의 수동 발송 담당

- 팀 도메인과 메일 서비스가 확인되면 `notifications@<팀 도메인>` 같은 **공용 메일함**을 만든다. 실제 주소가 정해지기 전에는 고객에게 임의 주소를 안내하지 않는다. 자동 발송 기능은 추가하지 않는다.
- 주 담당자 1명과 대체 담당자 1명을 지정한다. 둘 다 개인 계정으로 공용 메일함에 위임 접근하고 MFA를 사용한다. 비밀번호를 공유하지 않는다.
- 업무일에 최소 오전·오후 한 번씩 관리자 요청을 확인한다. **발송 준비가 됐을 때** 코드를 발급하고, 요청에 표시된 이메일로만 코드를 보낸 뒤 관리자 화면에 발송 완료를 기록한다. 기록은 실제 메일 발송의 증명이 아니므로 메일함의 보낸 편지도 함께 확인한다.
- 코드 원문을 작업 티켓·메신저·로그에 남기지 않는다. 발송을 못 한 채 화면을 닫았다면 기존 코드를 다시 볼 수 없으므로 24시간 만료 후 새 코드를 발급한다. 팀 외부 문의가 오면 코드나 신분증을 요구하지 말고 신청 주소로 받은 메일 확인 절차를 안내한다.

## DB와 배포 확인

- 주 DB에 `notification_subscriptions.expires_at`, `notification_guest_subscriptions.expires_at`, `notification_guest_cancellation_requests`가 추가된다. `notification_interest_events.email`은 삭제된다. 취소 요청에는 수동 발송 시각·관리자 계정을 위한 `code_sent_at`, `code_sent_by`가 추가된다. Flyway 버전은 `20260929.04`, `20260929.05`, `20260930.01`이다. 기존 요청의 발송 기록은 비어 있는 값으로 시작한다.
- 개발 서버에 브랜치를 병합·배포하면 개발 **주 DB**, 운영 서버에 배포하면 운영 **주 DB**에 각 서버 시작 시 Flyway가 적용된다. 공유 DB에는 알림 신청을 쓰지 않는다. 알림은 사용자 계정·세션과 묶인 서비스 데이터이므로 같은 주 DB 트랜잭션으로 관리한다.
- 배포 후 각 환경의 DB 이름과 연결 대상을 먼저 확인하고 `scripts/check-notification-schema.sh` 또는 `scripts/check-notification-schema.sql`을 읽기 전용으로 실행한다. Flyway 이력 성공, 테이블·열·제약 조건을 자동 검사한다. `docs/queries/notification-retention-status.sql`로 정리 작업이 밀렸는지 확인한다.
- 백업은 DB 서버의 별도 작업으로 하루 한 번 S3에 저장하고 **30일 보관**한다. 실제 설정 절차, 자동 검사와 격리 복원 절차는 [DB 백업 운영](../infra/db/BACKUP.md)에 있다. 복원 시 Flyway와 만료 데이터 정리만 실행하면 백업 시점 이후에 취소한 알림이 되살아날 수 있다. `scripts/reset-restored-notifications.sql`은 **격리된 복원 DB**에서 알림 신청·이메일 설정·취소 요청을 비운다. 서비스를 열기 전에 0건을 확인하고 사용자에게 재신청을 안내한다. AWS 계정과 버킷이 아직 확인되지 않아 실제 30일 정책과 자동 실행은 미적용 상태다.

## 수동 운영 순서

1. 관리 화면의 취소 요청을 정기적으로 확인한다. 요청 이메일로만 코드를 보낸다.
2. 코드를 화면에서 복사해 발송한 다음 발송 완료를 기록한다. 코드가 유효한 동안은 화면에서 다시 조회할 수 없으므로 발급 시점에 처리한다.
3. 신청 이메일이 같은 다른 브라우저의 비로그인 신청도 함께 취소된다는 점을 안내한다.
4. 개발·운영 배포 후 스키마 검사와 보관 상태 검사를 각각 실행하고 결과를 배포 기록에 남긴다.
