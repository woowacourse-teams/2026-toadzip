# 알림 수요 수집 구현 계획

## 목표와 범위

- 실제 발송 없이 지역·단지·공고 알림 수요를 자체 DB에 저장한다.
- 동일 브라우저에서 최초 알림 클릭에만 신청 의사를 묻는다.
- 확인·취소·닫기로 질문을 마치면 localStorage에 기록하고 이후에는 클릭만 수집한다.
- 다른 대상, 새로고침, 브라우저 재시작에도 다시 묻지 않는다. 저장소 삭제나 다른 브라우저는 새 방문이다.
- 저장소 사용 불가 시 현재 페이지 메모리로 유지한다.
- 실제 알림을 발송하지 않는다는 안내를 제공한다.
- 이메일, 로그인, 발송, 구독 목록, 취소 API, 대시보드, 분석 SDK는 추가하지 않는다.

## 커밋

1. 알림 수요 이벤트 저장 API: 테이블 하나, 익명 POST, CSRF 유지, 대상 검증, 재전송 멱등성.
2. 단지 알림과 최초 질문: 브라우저 공통 상태, 최초 확인·취소, 이후 클릭, 실패·재시도.
3. 지역 검색 종 버튼: 지역 이동 버튼과 분리하고 기존 검색 결과의 지역 코드 사용.
4. 독립 알림 설정: 기존 검색으로 지역·단지 선택 후 동일 알림 버튼 사용.
5. 공고 알림: 상세 진입점과 수요 집계 SQL, 통합 검증.

## 데이터와 지표

- 이벤트: EXPOSED, CLICKED, CONFIRMED, DECLINED.
- eventId, sessionId, type, source, targetType, targetId, createdAt(서버 시각).
- 노출은 실제 화면에 보일 때 세션·진입점·대상별 한 번 수집한다.
- 클릭은 매번 수집한다. 최초 질문의 확인·취소는 별도 이벤트다.
- 같은 eventId 재전송은 한 번만 저장한다.
- 세션은 sessionStorage로 유지하며 고유 사용자 식별로 해석하지 않는다.
- 클릭률: 노출 세션 중 클릭 세션의 비율. 진입점·대상별 집계.
- 최초 의사 확인은 한 번만 묻기 때문에 이후 클릭과 분리하여 집계한다.
- 기록은 익명 이벤트이며 실제 구독 데이터가 아니다. 실험 종료 후 집계·삭제한다(최대 90일).

## 완료 조건

- 최초 질문 후 다른 대상·새로고침에서는 확인창 없이 클릭 기록.
- 취소는 신청으로 기록하지 않음. 실패는 성공으로 표시하지 않음.
- 재시도는 동일 이벤트 ID 사용. 병렬 요청에서도 중복 저장 없음.
- 키보드·Escape·포커스 복원과 모바일 확인.
- frontend npm run check, 테스트 PostgreSQL에서 backend ./gradlew --rerun-tasks check.
- 마이그레이션 SQL을 배포 전에 적용하고 실제 DB 저장·집계를 확인.
