# 개인정보 처리 정책과 운영 책임

## 적용 범위

공공주택 복덕방의 회원 로그인, 선택적 이용 분석, 관심 대상 알림 설정과 개인정보 권리행사에
적용한다. 처리 목적·항목·기간이 바뀌면 공개 안내 원문, 서버 정책, 화면과 파기 코드를 함께 검토한다.
동의 선택의 유효기간과 수집 데이터의 보유기간은 별개의 정책이다.

이 문서는 처리 목적·보유기간·권리행사·운영 확인 항목의 원본이다. 구현 상세는 다음 문서에서 관리한다.

| 동의 API·유효 상태·파기 동시성 | [개인정보 안내와 이용 분석 동의](../backend/docs/features/PRIVACY.md) |
| 신규 테이블 소유권·연결 지점·제거 범위 | [모듈 분리 계약](../backend/docs/features/PRIVACY_STORAGE.md) |

## 운영 주체와 연락 창구

| 항목 | 기준 |
| --- | --- |
| 운영 주체 | 공공주택 복덕방 |
| 공개 담당 부서 | 공공주택 복덕방 운영팀 |
| 개인정보 문의·열람·정정·삭제 요청 | toadzip.official@gmail.com |
| 내부 총괄책임 | 실제 운영팀 대표 1명을 내부 기록으로 특정한다. 인물 지정은 운영 전 완료해야 한다. |

공개 정책에는 담당 부서와 연락처를 표기한다. `공공주택 복덕방 운영팀 대표`라는 직책만으로
내부 담당자 지정이 완료되지는 않는다. 실제 담당자, 지정일, 권한, 대리 처리자와 인수인계 책임은
접근을 제한한 내부 운영 기록으로 관리하며 저장소에 실명을 기록하지 않는다.
개인정보 보호법 [제30조](https://www.law.go.kr/법령/개인정보보호법/제30조)는 책임자 성명 또는
담당 부서 명칭과 연락처를, [제31조](https://www.law.go.kr/법령/개인정보보호법/제31조)는 내부
총괄책임을 규정한다. 소상공인 예외 여부는 사업 형태와 규모를 확인한 후 판단한다.

## 처리 결정

| 처리 | 목적과 정책 |
| --- | --- |
| 회원 이메일 | 소셜 제공자가 반환한 이메일의 수집·저장을 유지한다. 실제 목적은 관리자의 회원 조회·검색이다. 이메일 알림은 발송하지 않는다. |
| 로그인 | 정책 조회 실패·버전 누락·변경에도 로그인한다. 전달된 보관 정책 버전만 state별 선택 메타로 보존하고 신규 가입 시 기록한다. 열람·동의·노출 확인의 증거가 아니다. |
| 선택적 분석 | 회원은 계정별, 비회원은 해당 브라우저별 선택을 적용한다. 로그인·로그아웃 때 두 선택을 자동 복사하지 않는다. |
| 알림 설정 | 모달에서 목적·정책을 확인하고 신청 버튼을 눌렀을 때 저장한다. 분석 동의와 독립적이다. 업무 요청에 이메일·분석 식별자를 받지 않는다. |
| 분석 안내 | GA client ID·PostHog distinct ID는 행동을 연결할 수 있으므로 완전한 익명 집계라고 표현하지 않는다. 이름·이메일·회원 ID를 보내거나 연결하지 않고, 현재 범위의 유효한 허용 후 SDK와 자체 분석을 시작한다. |

공개 원문과 해시·버전은 `backend/src/main/resources/privacy/`에서 관리하고 공개 API로 제공한다.
화면에서 정책 원문을 복제하지 않는다. 버전 원문은 수정하지 않고 새 버전을 발행한다.
분석 안내 v2는 식별자 기반 이벤트 수집 범위를 공개하며 `analytics-scope-2`를 요구한다. 기존 v1 허용은 자동 승계하지 않고 재동의를 받는다. 거부·철회는 보존한다.
회원 이메일과 최소 증빙 보존의 법적 근거는 운영 전 검토 대상이다. 정책값 자체를 법적 근거로 보지 않는다.

## 보유·파기 정책

| 대상 | 기한과 처리 |
| --- | --- |
| 기존 회원 식별자·이메일 | 기존 수집·저장 유지. 삭제·탈퇴 요청은 본인 확인 및 별도 승인 절차로 처리하며 신규 개인정보 배치가 기존 자료를 삭제하지 않음 |
| 회원 분석 허용 | 명시적 선택부터 180일. 거부·철회 및 현재 revision은 계정 존속 중 보존 |
| 비회원 선택 | 명시적 선택부터 180일. 방문·조회로 기간을 연장하지 않음 |
| 미선택 비회원 context | 생성부터 24시간 후 파기 |
| 대체·만료·범위 변경된 분석 선택 이력 | 효력을 잃은 때부터 최대 90일. 현재 유효한 선택 증빙은 유지 |
| 브라우저 거부·철회 재시도 표식 | 생성 후 180일. 모든 계정 범위를 정리하며 이전 허용 부활은 비식별 재선택 기준으로 차단 |
| 브라우저 재선택 기준 시각 | 기록 후 180일. 계정·명령 정보를 포함하지 않으며 방문으로 연장하지 않음 |
| 만료 비회원 context | 만료부터 최대 90일 후 토큰 해시·연결 이력과 함께 파기 |
| 알림 고지 메타 | 신청 시각·고지 버전·기존 업무상 만료일을 별도 신규 테이블에 보유 |
| 취소·만료 알림 고지 메타 | 실제 비활성 시각부터 90일 후 신규 메타만 파기. 기존 알림 설정 행은 새 배치 대상 아님 |
| 새 알림 업무 영수증·자체 행동 이벤트 | 발생부터 90일. 별도 신규 테이블에서만 파기 |
| 가입 고지·알림 revision | 회원 계정 존재 중 보존, 사라진 회원의 신규 메타만 다음 성공 배치에서 파기 |
| 개인정보 요청 처리 기록 | 완료 후 최대 90일. 불필요한 본인 확인 원자료는 즉시 폐기 |
| 외부 분석 원자료 | GA4·PostHog 프로젝트의 실제 보유 설정과 삭제 절차를 운영 담당자가 확인해야 한다. 동의 180일·자체 증빙 90일 정책과 다르며 아직 확인되지 않았다. |
| 별도로 만든 익명 집계 | 집계 기준월 말일로부터 최대 12개월. 외부 도구의 식별자 포함 원자료를 익명 집계로 취급하지 않음 |
| 백업 | 최대 7일. 실제 백업 제공자의 수명주기·복구 설정 확인 필요 |

새 개인정보 영속 자료의 코드 정책 원본은 `PrivacyRetentionPolicy`다. 기존 테이블의
컬럼·제약·인덱스·데이터를 이 기능 때문에 변경하지 않고 소급 보유기한도 부여하지 않는다.
기존 회원·알림·이메일·행동 기록은 신규 자동 파기의 대상이 아니다.

표의 모든 기간을 DB 배치가 강제하는 것은 아니다. 실행 책임은 다음과 같이 구분한다.

- **신규 DB 자료:** 만료 시각부터 사용을 중지하고, 15분 주기의 다음 성공 배치에서 물리 삭제한다.
  서버 중단·잠금·실패 중 15분 내 삭제를 보장하지 않는다. 잠금·재시도·지연 계산은 위 구현 문서를 따른다.
- **브라우저 표식:** 다음 성공한 상태 확인 때 정리한다. 닫힌 브라우저의 자료를 서버가 원격 삭제하지 못한다.
- **문의 처리 기록·별도 익명 집계:** 위 기간은 운영 기준이다. 해당 자료에 대한 자동 파기 경로는 제공하지 않는다.
  기록·집계를 보유하는 운영자가 기산점과 삭제 결과를 관리해야 한다.
- **메일·백업·외부 분석:** 서비스 DB 배치의 대상이 아니다. 운영 담당자가 제공자 설정과 실제 삭제를 확인한다.

## 권리행사와 탈퇴 절차

1. 팀 이메일로 요청을 접수하고 요청 범위를 확인한다. 기존 계정 인증 등 필요한 최소 정보로 본인을 확인한다.
2. 데이터 위치와 처리 근거를 확인하고 본인 확인이 끝난 대상 회원 ID를 확정한다. 신분증·주민번호를 일괄 요구하지 않는다.
3. 기존 회원·알림 자료의 삭제 범위와 방법을 별도 검토·승인한다. 이 모듈은 기존 자료를 삭제하는 관리자 API나 자동 배치를 제공하지 않는다. 수동 SQL의 임의 실행도 완료 절차가 아니다.
4. 승인된 별도 절차로 처리한 DB 및 DB 밖 메일·백업·위탁 저장소의 결과를 각각 확인해 통지한다.

로그아웃·알림 해제·분석 철회를 회원 탈퇴나 기존 자료의 일괄 삭제로 안내하지 않는다.
회원 이메일은 관리자의 회원 조회·검색을 위해 계속 수집·저장한다. 이 기능의 철회·제거는
이메일 수집 중단이나 `users.email` 정리 작업을 발생시키지 않는다.
회원 삭제를 별도로 완료한 경우 가입 고지·동의·알림 메타의 고아 자료는 신규 테이블의 파기 작업이 정리한다.

## 운영 점검과 출시 조건

작업별 Micrometer 지표를 아래 의미로 사용한다. job 태그는 `consent`, `notification`, `registration-notice`이다.

| 지표 | 의미 |
| --- | --- |
| `privacy.retention.last.success.seconds` | 마지막 성공의 UTC epoch seconds |
| `privacy.retention.deleted.total` | 삭제 행 수 |
| `privacy.retention.consecutive.failures` | 연속 실패 횟수 |
| `privacy.retention.overdue.count` | 실효 파기 기한을 지난 잔여 행 수 |
| `privacy.retention.oldest.overdue.seconds` | 최대 파기 지연 시간(초) |

- 성공 시각 0은 미실행이다. 서버 기동 후 유예를 포함해 30분 이상 성공이 없거나 파기 지연이 30분을 넘으면
  외부 모니터링에서 운영팀에 경보한다. 지표 제공만으로 경보 전달이 완료된 것으로 보지 않는다.
- 완료일 기준 문의 메일·첨부를 주간 점검하고 90일 기한 내 휴지통까지 정리한다. 메일 서비스의 복구 보관도 확인한다.
- 백업 복원 환경을 개방하기 전에 백업 시점 이후 탈퇴·삭제를 다시 적용한다. 최소 처리 대장에는 요청 ID·회원 ID·완료 시각만
  남기고 처리 기록 90일 정책을 적용한다. 재적용 여부를 검증할 수 없으면 복원본을 서비스에 공개하지 않는다.

다음은 운영 공개 전에 확인할 미확정 항목이다. 코드·브라우저 검증만으로 완료 처리하지 않는다.

| 확인 항목 | 필요한 결정·증거 |
| --- | --- |
| 내부 책임자 | 실제 담당자 지정과 권한·인수인계 기록 |
| 이메일·최소 증빙 | 실제 목적에 맞는 처리 근거, 기존 회원·알림 자료의 보유·삭제 절차 |
| 외부 분석 | GA4·PostHog의 실제 전송 항목, 보유·삭제 설정, 처리 국가·국외이전 조건과 공개 안내 |
| 문의·백업 | 메일 휴지통·복구 보관을 포함한 삭제 확인, 백업 7일 수명주기와 복원 후 삭제 재적용 절차 |
| 운영 기록·집계 | 문의 처리 기록 90일 및 별도 익명 집계 12개월 기준의 실행 담당·삭제 확인 방법 |
| 가입 고지 파기 목표 | 24시간 내 처리 문구는 코드의 보장이 아니다. 운영 목표로 채택할지와 지연 대응 책임을 확정해야 한다. 자동 처리는 다음 성공 배치 기준이다. |
| 경보 | 작업별 마지막 성공·지연을 감시하는 외부 모니터링과 실제 운영팀 수신 확인 |

유효한 동의가 있으면 코드가 수집을 허용한다. 미확정 운영 항목을 전면 차단 플래그로 대체하거나,
관련 문장을 삭제하는 것으로 운영 설정이 완료됐다고 판단하지 않는다.
