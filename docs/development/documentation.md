# 문서 작성·관리 규칙

사람과 AI가 함께 사용하는 팀 문서의 배치, README 형식과 유지 기준이다.
문서가 독자의 다음 행동이나 판단에 도움을 주는지를 기준으로 내용을 고른다.

## 문서 배치

| 분류 | 담을 내용 |
|---|---|
| `docs/setup/` | 설치·환경변수 준비와 최초 실행 |
| `docs/development/` | 구조·구현·API·테스트·디자인·문서 작성 기준 |
| `docs/features/` | 현재 기능의 사용 흐름·API 계약·데이터 정책·실패 조건 |
| `docs/operations/` | 반복 배포·관측·점검·DB 전환·장애 복구 |

- 프로젝트를 실행하려면 setup, 코드를 바꾸려면 development, 기능 동작을 이해하려면 features, 서비스를 운영하려면 operations에서 찾을 수 있게 배치한다.
- 개발 기준은 공통 계약과 백엔드·프론트엔드 기준을 구분한다. 기능 문서는 구현 영역보다 기능을 기준으로 묶고 서버·화면의 서로 다른 계약은 구분해 보존한다.
- 예시 입력은 `docs/fixtures/`, 운영 점검 SQL은 `docs/queries/`에 둔다. 두 폴더는 기술 문서의 추가 분류가 아니라 관련 자료다.
- 루트 소개·기여 규칙, 코드 컨벤션 원본, 영역별 AGENTS와 역할 설정은 기존 위치를 유지한다. 앱이 직접 읽는 고지 원문·SQL, 테스트 fixture와 도구 옆 사용 안내도 해당 프로젝트 경로에 둔다.
- 개인 메모·계획·진행 기록·실험·로컬 검증 자료는 [로컬 작업 자료 기준](../../CONTRIBUTING.md#로컬-작업-자료)을 따른다. 미추적·개인 자료는 정식 문서의 원본으로 임의 사용하거나 이동·삭제하지 않는다.
- 작업 완료와 당시 테스트 통과 결과는 이슈·PR에 남긴다. 기술 문서에는 재현 가능한 검증 방법, 복구 조건과 알려진 한계를 남긴다. 필요한 과거 점검 기록을 보존할 때는 당시 자료임을 명시한다.

## 폴더 README 형식

문서 폴더마다 `README.md`를 두고 제목, 폴더 목적과 문서 안내를 작성한다.
문서는 읽는 목적을 분명히 하고 일률적인 줄 수 제한 대신 필요한 계약·제약·검증 방법의 보존을 우선한다.

`.github/`에는 README를 만들지 않는다. GitHub은 이 위치의 README를 루트보다 먼저 저장소 메인에 표시하므로, 서비스 소개는 루트 README로 유지한다. 협업 규칙은 [기여 가이드](../../CONTRIBUTING.md), CI/CD와 서버 배포 안내는 [배포 운영](../operations/deployment.md)에서 확인한다.

| 구성 | 작성 기준 |
|---|---|
| 제목 | 폴더 이름만 반복하지 않고 다루는 주제를 표현한다. |
| 폴더 설명 | 무엇을 다루는지와 필요한 범위를 짧게 설명한다. |
| 문서 안내 | 해당 폴더의 문서·바로 아래 폴더를 링크하고 각각의 내용을 구분한다. |
| 관련 문서 | 다른 폴더의 선행 조건·연결된 절차가 필요할 때만 추가한다. |
| 읽는 순서 | 실제 선행 관계가 있을 때만 추가한다. |

기본 형식은 다음과 같다. 빈 절이나 해당하지 않는 항목은 만들지 않는다.

```markdown
# 주제

이 폴더가 다루는 대상과 범위를 설명한다.

## 문서 안내

| 문서 | 다루는 내용 |
|---|---|
| 문서명과 상대 링크 | 다른 문서와 구분되는 내용 |

## 관련 문서

필요한 경우에만 선행 조건이나 연결된 절차를 링크한다.
```

- 문서가 하나면 표 대신 설명이 붙은 링크 한 줄로 안내해도 된다. JSON·SQL 자료 폴더에서는 `자료 안내`를 사용해 파일별 용도와 조건을 안내한다.
- 상위 README는 바로 아래 폴더를, 하위 README는 그 안의 문서를 안내한다. 전체 문서 목록을 여러 단계의 README에 복제하지 않는다.
- 최상위 `docs/README.md`는 Git으로 관리하는 문서 폴더의 역할을 트리로 보여주고 하위 목차를 연결한다. 기술 문서는 `setup/`, `development/`, `features/`, `operations/`로 분류하며, 개별 파일의 추가·이동은 해당 폴더 README에 반영한다. 폴더 구조가 바뀌면 최상위 트리도 갱신한다.
- 저장소 루트 README의 서비스 소개·팀 정보와 애플리케이션 README의 설치·실행·검증 안내는 유지한다. 소스·인프라·도구 폴더에서는 문서 안내 외에 프로젝트 고유 구성·사용법을 필요한 만큼 설명한다.
- 기술 정책·구현 세부사항·운영 명령은 담당 문서에 작성하고 README에서는 연결한다. 도구 옆 README가 사용법의 원본이면 해당 실행 전제·명령·실패·복구 조건을 보존한다.
- 필수 템플릿을 채우기 위해 새 내용이나 이미 아는 도구 설명을 늘리지 않는다.

## 설명을 포함할 기준

파일 존재 자체보다 읽고 나서 해야 할 행동이나 판단이 달라지는지를 본다.

| 내용 | 처리 |
|---|---|
| 파일명·도구명만으로 알 수 있는 일반 역할 | 생략한다. 예: Gradle의 의존성 관리, Dockerfile의 이미지 빌드 역할 |
| 프로젝트 고유 동작·설정·제약 | 포함한다. 예: 환경값은 프론트 빌드에 포함되므로 변경 후 재빌드 필요 |
| 문서를 고를 때 필요한 차이 | 포함한다. 예: 실행 상태 전이 설명과 실제 잠금 복구 절차의 차이 |
| 명령 실행 전제·위치·대상·결과 해석 | 사용법의 원본에 보존한다. |
| 표준 설정·소스 파일 전체 목록 | 생략한다. 실행·설정·문제 해결에 직접 필요한 원본만 연결한다. |

- `이 기능을 설명한다`처럼 모호하게 쓰지 않고 적용 범위·핵심 계약·실패 조건 등 문서가 답하는 질문을 적는다.
- 이유는 문단, 비교·매핑은 표, 절차는 번호 목록으로 표현한다.
- 사람용·AI용 기술 문서를 별도로 복제하지 않는다. AGENTS에는 필수 행동 기준과 해당 원본의 링크를 둔다.
- 문서 수를 줄이기 위해 서로 다른 계약·실패·복구 조건을 지우거나, 형식을 맞추기 위해 새 폴더를 미리 만들지 않는다.

## 원본과 변경 관리

- 같은 정책·규칙·명령은 한 곳을 원본으로 두고 다른 문서에서는 링크한다.
- 바뀌기 쉬운 버전·명령·설정은 실제 설정 파일을 원본으로 연결한다. 문서에는 선택 이유·사용 조건·프로젝트 제약을 남긴다.
- 문서와 코드·설정이 다르면 실제 동작과 의도를 확인해 갱신한다. 품질·보안 기준을 임의로 낮추거나 확인하지 않은 운영 상태를 성공으로 쓰지 않는다.
- 반복 실패에서 나온 규칙은 재현 가능한 테스트·자동 검사로 옮길 수 있는지 검토한다.
- 통합한 문서는 필요한 내용이 새 원본에 보존되고 참조를 갱신한 뒤 제거한다. 연결용 복사본이나 심볼릭 링크를 남기지 않는다.

문서를 추가·이동·수정할 때는 다음을 확인한다.

1. 새 문서의 배치가 폴더 목적과 맞고 해당 README에 설명이 있는가.
2. 같은 정책을 설명하는 기존 원본과 중복되거나 서로 모순되지 않는가.
3. 내부 파일 링크·제목 앵커와 이전 경로의 참조가 올바른가.
4. 명령의 실행 위치·상대 경로·환경변수·대상·실패 및 복구 조건이 실제 설정과 맞는가.
5. 실제 인증정보·개인 자료·범위 밖 변경이 없고 앱이 읽는 고지·SQL 등 보호 대상이 유지되는가.
6. 검증한 내용과 확인하지 못한 실제 서버·외부 서비스 상태를 구분했는가.
