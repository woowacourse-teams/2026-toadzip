# LH 공고 연결 조회와 복구

## LH 공고 정제 (`announcement-refinement`)

공고 정제는 LH 공고 정제(`MAP_LH_ANNOUNCEMENTS`) 한 단계다. 공고 수집은 마이홈 공고를 수집하지 않는다. 마이홈 공고 정제·LH 보강·단건 등록과
공급행 매칭·분할·제외·LH 행 연결 보정은 지원을 종료해 코드와 API를 걷어냈다. 단건 등록(`announcement-registration`) 시작만 본문 없는 요청을 410(`INGEST_OPERATION_RETIRED`)으로 거절하고, 지난 실행 이력은 남긴다.

- 대상: 최신 공고목록의 임대 공고 중 상세 원천이 저장된 요청. 공고일·공고 ID 순(원공고 먼저)으로 공고마다 한 트랜잭션에서 정제하고, 한 공고가 실패해도 다음 공고를 계속한다.
- 공고: 같은 `lh_pan_id`의 휴지통이 아닌 가장 작은 ID 공고를 이어받는다. 없으면 `LH:{공고 ID}`로 만든다. 같은 공고 ID가 모두 휴지통이면 만들지 않는다.
  값은 공고목록(이름·공고일·URL·마감)과 상세(접수·당첨자 발표)로 정하고, 관리자가 고친 공고와 확정한 접수 기간은 덮지 않는다. 새 공고는 당첨자 발표일이 있어야 만들고, 공고일이 7일 넘게 지났으면 알리지 않는다.
  정정·취소공고는 머리말을 뗀 이름이 같은 가장 최근 이전 공고에 잇는다.
- 공고 단지: 상세 단지(공급 원천에만 있는 단지명 포함)마다 하나다. 원천에서 사라지면 지우지 않고 `원천에 없음`으로 둔다.
  새로 만들 때만 연결한다: 기존 공급행이 이 단지에서 휴지통이 아닌 제품 단지 하나만 가리키면 `MIGRATED` → 정정공고는 원공고의 같은 이름 공고 단지 연결 →
  상세 주소의 (시도, 도로명, 건물번호)와 공급유형이 같은 휴지통 아닌 LH 단지가 하나면 `AUTO` → 미연결. 붙은 연결은 정제가 다시 계산하지 않는다.
- 공급행: LH 공급 한 행이 공급행 하나다. 키는 `LHROW:{공고 단지 ID}:{주택형명}#{같은 이름 안 순번}`이다. 대표 주택형은 연결 단지에서 LH 대표 전용면적과 면적이 같은 주택형이 하나일 때만 정한다.
  매칭 상태는 `COMPLEX_UNLINKED` → `AREA_UNMATCHED` → `VALUES_MISSING` → `MATCHED` 순이다. LH 원천 소유 공고는 이 공고의 다른 공급행을 지운다(첫 정제에서 공급행 ID가 바뀐다).
  공고문 소유 공고는 공급행을 만들거나 지우지 않고 비어 있는 공고 단지 참조만 채운다(공고 단지가 하나뿐이거나 그 행의 단지에 연결된 공고 단지가 하나일 때).
- 재확인: 공고 단지 순서와 공급 원천 행 값의 지문을 남긴다. 공고문 소유 공고는 지문이 바뀌면 `supply_recheck_required`를 켠다.
- 단지·주택형은 만들거나 바꾸지 않는다. 같은 입력의 두 번째 실행은 아무것도 바꾸지 않는다.
- 공급 감소 보류 승인: 품질 화면에 LH 공고 ID(`panId`, 원천 식별자 형식 `LH:{공고 ID}`도 받음)를 넣어 승인한다. 최신 공고목록의 그 공고 요청과 같아야 하고(종료 정책과 관계없음), 승인 뒤 그 요청만 다시 받는다. 마이홈 공고 ID로는 승인하지 않는다.

아래 절은 지원을 종료한 마이홈 공고 정제·LH 보강의 동작이다. 지난 실행과 남은 코드를 읽을 때 참고한다.

## 조회 기준

- 매핑과 보강은 `LhAnnouncementLinkResolver`에서 같은 공고별 성공 연결을 조회한다.
- 공급·상세 연결이 모두 현재 수집 요청의 해시와 `panId`에 일치해야 정제를 진행한다.
- 매핑과 보강은 연결된 요청의 해시와 `panId`가 모두 일치하는 LH 원천 행만 읽는다.
  같은 `panId`를 다른 조회 조건에 사용해도 원천 행이 섞이거나 덮어써지지 않는다.
- 현재 요청은 수집의 `LhAnnouncementCollectionCandidateResolver`로 해석한다.
  수집·매핑·보강은 `MyHomeAnnouncementCurrentSources`로 활성 원천을 우선하고 최신 관찰 실행을 고른다.
  모두 비활성이면 마지막 관찰 실행을 사용한다. 수집은 500행 배치 밖의 같은 공고 원천도 함께 확인한다.
  수집 대상 공고의 현재 원천에서 LH 요청이 서로 다르면 실패를 기록하고 기존 연결을 보존한다.
  현재 원천 모두 종료 후 30일이 지났으면 정기 수집에서 제외한다. 강제 갱신은 충돌 검사를 유지한다.
  현재 원천 모두 수집 대상에서 빠지면 이전 충돌 이력은 `SKIPPED`로 남긴다. 다시 충돌하면 같은 이력을 재개한다.
  보류 중인 충돌 이력은 배치마다 한 번 조회하고, 성공한 공고 중 이력이 있는 대상만 해결한다.
  요청이 일치하는 원천도 매 실행 실제 조회하고 같은 실행의 공유 요청만 합치며, 매핑·보강은 성공 연결을 검증한다.
  URL은 요청 일치 확인에만 쓰며, URL에서 얻은 `panId`로 원천을 직접 선택하지 않는다.
- LH 연결 확인에 실패하면 해당 공고의 매핑·보강 저장을 보류하고 기존 정제 데이터를 보존한다.
  최초 정제라면 LH 공고를 생성하지 않는다. LH 외 기관의 기본 매핑은 유지한다.
- 공급·상세 중 한쪽만 새 요청 수집을 마쳐도 두 단계 모두 보류한다.
- 수집 응답 전체의 파싱·원천 저장 후에만 해당 API의 연결을 갱신한다.
  공급·상세 응답의 `dsSch` 조회 조건이 요청 공고 ID·유형 코드와 일치해야 저장한다.
  조회 조건이 없거나 다르면 이전 성공 원천·연결을 유지하고 실패로 기록한다.
  같은 조회 조건에서 이전 원천이 있었는데 상세·공급 응답이 비면 기존 원천을 보존하고 실패로 기록한다.
  이전 원천이 없는 최초 빈 응답은 허용하며, 마이홈 데이터로 제품 공고를 구성할 수 있다.
  원천과 성공 수집 기록은 함께 커밋하고, 공고 연결과 실패 기록 해결은 후속 트랜잭션에서 함께 커밋한다. 수집 실패 시 이전 연결을 보존한다.
  같은 실행의 성공 요청을 공유하는 공고도 자신의 연결을 기록한다.

새 LH 연결의 보강이 성공하면 해당 공고의 이전 성공 연결에서 만든 일정·첨부를 정리한다.
금액은 주택형 매칭이 성공한 공급행의 이전 LH 보강 대상만 교체한다. 매칭 실패 시 이전 금액을
보존하며 복구 후 교체한다. 관리자가 고친 값, LH 원천이 아닌 수기 값과 이전 원천 데이터는 보존한다. 공고의 LH 공고 ID·정정 사유·접수처는 보강이 갱신한다.
서로 다른 LH 공급행이 하나의 제품 공급행에 연결되면 마지막 행으로 금액을 덮지 않고
해당 공고의 보강을 보류한다.

## LH 목록 기반 재조회

`announcement-collection`은 **LH 공고 목록 → LH 공급 → LH 상세** 순서다. 마이홈 공고는 수집하지 않는다.
이전에 저장한 마이홈 공고 원천·실행 이력은 지우지 않고 조회만 한다. 지난 실행에 남은 `COLLECT_MYHOME_ANNOUNCEMENTS` 단계는 이력으로 읽으며 다시 실행하지 않는다.
LH 공급·상세는 최신 LH 목록의 임대주택 공고(상위유형 06의 공급유형 060~063, 신혼희망타운 임대 42·51)를
목록의 조회 코드 그대로 수집한다. 마이홈 원천이 없는 LH 공고도 같은 기준으로 수집·정제한다. 종료 후 30일 기준은 목록의 마감일로 적용한다.
같은 조회 조건은 한 실행에서 한 번만 호출한다. 진행 기록은 `lh-catalog:{목록 원천 키}`로 남긴다.
공급이 줄어 보류되면 LH 공고 ID로 승인한다. LH 공고 정제가 목록의 공고를 `LH:{공고 ID}` 공고로 만든다.

목록은 [LH 공고목록 API](https://www.data.go.kr/data/15058530/openapi.do)에 `PAGE`·`PG_SZ=500`과
검색 기간 `PAN_ST_DT`~`PAN_ED_DT`(공고게시일, 오늘부터 `LH_ANNOUNCEMENT_CATALOG_WINDOW` 전까지, 기본 `P2Y`)로
조회한다. 공고 유형은 제한하지 않고 그 기간의 전체 페이지를 읽는다. 기간을 보내지 않으면 API가 최근 약 2개월만 반환해
게시 후 오래 접수하는 상시모집 공고가 빠진다. 응답의 검색 기간이 요청과 다르면 저장하지 않는다.
날짜 기반 증분 수집에는 의존하지 않는다.

- 페이지 번호·전체 건수·순번·검색 기간·필수 식별자·중복을 검증한 후 목록 전체를 한 트랜잭션에 저장한다.
  빈 목록에는 `ALL_CNT` 검증 근거가 없어 실패로 처리한다. 불완전한 목록은 이전 목록을 덮어쓰지 않는다.
  현재 기간에서 빠진 과거 원천도 삭제하지 않고 현재 목록 후보에서 제외한다.
- `(PAN_ID, CCR_CNNT_SYS_DS_CD, UPP_AIS_TP_CD)`와, URL에 있으면 `AIS_TP_CD`까지 같은 목록 행이 하나뿐이면
  그 행의 값(`SPL_INF_TP_CD` 포함)으로 요청을 다시 만든다. 일치하는 행이 없거나 모호하면 마이홈의 기존 해석을 유지한다.
- 이름·상태·날짜·URL·조회 코드의 변경 시각은 목록에 보존한다. 목록이 같아도 공급·상세의 불변을 보장하지 않으므로 현재 대상 요청을 매 실행 실제 조회한다.
- 종료일 누락·해석 실패·진행 중·종료 후 30일 이내는 일반 수집 대상이다. 더 오래된 종료 공고는 공고별 재조회로 확인한다.
- 동일 조회 조건은 실행 단위로 합친다. 500행 배치 밖의 공유 공고도 성공 후 연결하며 실패한 요청을 같은 실행에서 반복하지 않는다. 다음 실행에는 다시 조회한다.
- 응답이 같아도 실제 성공 수집 시각과 새 수집 기록을 남긴다. 실패하면 기존 원천·성공 시각·연결을 보존한다.
- 원천을 추가 공고에 연결한 시각은 실제 수집 시각을 연장하지 않는다. 정제 단독은 저장 원천을 사용하며 재조회하지 않는다.

## 마이홈 원천행과 LH 공급행 대응

마이홈 원천 한 행(예: `아파트` 240)은 LH 공급정보의 주택형 행으로 나눠 공급행을 만든다.
LH 공급행은 단지 라벨이 원천 단지명과 호환되는 원천행 하나에 붙인다. 숫자 토큰이 다르면
(`중동한라1단지` ↔ `중동한라10단지`) 다른 단지로 보고 붙이지 않는다.

단지명으로 붙이고 남은 행은 다음을 모두 만족하면 남은 LH 공급행을 전부 그 원천행으로 나눈다.

- 단지명으로 붙지 않은 현재 마이홈 원천행이 하나뿐이다.
- 남은 LH 공급행의 공급호수를 모두 읽을 수 있고, 합계가 그 원천행의 모집호수와 같다.

예: `아산읍내` 240 ↔ `아산읍내1 영구임대아파트` 26(200)·45.3400(40),
`의령동동` 73 ↔ `의령동동 5블록 행복주택` 16형(50)·26형 2행(8·15).
`평화주공1단지`가 `전주평화주공1단지`에 이름으로 붙은 뒤 남은 `평화주공4단지` 300 ↔ `전주평화4 영구임대주택` 300도 같다.
남은 원천행이 둘 이상이거나 합계가 다르면 기존처럼 원천행을 그대로 두고 주택형 매칭 실패로 남긴다.
단지명 정규화를 느슨하게 하지 않는다. 표기 차이를 넓게 허용하면 다른 공고의 단지끼리 잘못 이어질 수 있다.

정제는 관리자가 보정한 공급행에도 이 LH 원천 식별자를 기록한다. 관리자가 정한 모집수는 바꾸지 않는다.
LH 보강은 정제가 공급행에 기록한 LH 원천 식별자(`LH:{panId}:SUPPLY:{순번}`)가 같고 주택형명이 맞으면
단지명을 다시 비교하지 않고 그 공급행에 금액을 붙인다. 그런 공급행이 없으면 공급행 전체를 원천 단지명 또는 연결된 단지 이름과 주택형명으로 대조한다(`LhAnnouncementSupplyMatcher`).
복수 공급행으로 보정한 공통 모집 묶음 행은 매칭 대상에서 뺀다. 그 묶음 행에 붙는 LH 공급(매칭된 행이 묶음 행이거나, 매칭된 행이 없어도 같은 단지 행이 모두 묶음 행인 경우)은 보강이 건너뛰며 실패로 남기지 않는다. 관리자 연결 화면의 매칭 진단도 같은 규칙(`LhEnrichmentSupplyRows`)을 써서 이 LH 행을 실패로 보이지 않는다.

### 관리자가 저장한 LH 공급 연결

위 규칙으로 풀리지 않는 행은 관리자가 공고문을 확인해 LH 공급행을 마이홈 원천행에 연결한다
(예: 남은 원천행이 둘 이상인 `평화주공4단지`·`평화주공5단지`와 `전주평화4 영구임대주택`).
연결은 `lh_supply_row_links`에 공고별 LH 공급행 하나당 한 건으로 저장한다. 마이홈 원천행 하나에는 여러 LH 행을 연결할 수 있다.

- 정제는 저장 연결을 단지명 비교보다 먼저 쓴다. 저장 연결에 걸린 LH 행과 마이홈 원천행은 단지명 연결과
  남은 한 행 연결 규칙에서 뺀다.
- LH 보강은 같은 LH 원천 식별자를 기록한 공급행(주택형도 맞는 행)을 먼저 쓴다. 그런 행이 없을 때 저장 연결이 있으면
  단지명 대신 그 마이홈 원천행(`SupplyRow.myhomeSourceRowIdentifier`)으로 만든 공급행에서 주택형을 찾는다.
  그래서 연결을 저장하거나 해제할 때 같은 트랜잭션에서, 연결이 바뀐 LH 행을 기록한 공급행 가운데 그 LH 행이 이제 다른 원천행으로
  해석되거나 어느 원천행으로도 해석되지 않는 공급행의 LH 원천 식별자를 지우고, 그 LH 행으로 붙었던 보강 금액(`…:TARGET`)도 지운다.
  보강이 단지 이름으로 맞춰 기록한 공급행도 같다. 관리자 보정 행도 LH 식별자는 지우며,
  관리자가 정한 모집수와 관리자가 고친 금액은 그대로 둔다. 재정제 없이 보강해도 금액은 새 원천행의 공급행에 붙는다.
- 저장 당시 양쪽 원천의 지문을 함께 보관한다. LH 쪽은 요청 해시·순번·단지명·주택형·면적·세대수,
  마이홈 쪽은 단지명·주택유형·PNU·공급유형·모집호수·URL이다. 보증금·임대료 변경은 재확인 사유가 아니다.
- 지문이 다르거나 어느 한쪽 행이 현재 원천에서 사라지면 연결을 쓰지 않는다. 그 LH 행과 원천행을
  자동 연결로도 대체하지 않는다. 지문이 다르거나 마이홈 쪽 행이 사라지면 보강은 `LH_SUPPLY_LINK_REVIEW_REQUIRED`로 남기고,
  같은 연결을 다시 저장하면 해결된다. LH 쪽 행이 사라지면 그 행은 보강 입력에 없으므로 사유도 남지 않는다.
- 원천이 사라져도 연결을 자동으로 지우지 않는다. 해제는 관리자가 이유와 함께 명시적으로 한다.
- 원천 이름(`source_complex_name`, `source_housing_type_name`)은 정제가 소유하는 읽기 전용 매칭 기준이며 이 연결이 바꾸지 않는다.
- 묶음으로 보정한 원천행은 연결 대상이 아니라 저장을 409로 거절한다.
- LH 연결을 저장하거나 해제해 LH 행 구성이 바뀐 마이홈 원천행은 해석 결과(주택형·면적)가 달라지므로, 그 행과 그 행에서 펼친
  공급행의 저장 매칭(`announcement_supply_match_decisions`)을 같은 트랜잭션에서 해제하고 `RELEASE_SUPPLY_MATCH` 이력을 남긴다.
  응답의 `releasedSupplyMatches`에 해제한 행이 담긴다. 주택형은 재정제 뒤 PDF 보정에서 다시 확인한다.

저장·해제 절차와 API는 [실행 제어의 LH 공급 원본 연결](../../operations/ingest/execution-controls.md#lh-공급-원본-연결)을 따른다.

## 기존 LH 공고의 재정제

이미 LH 보강을 마친 공고는 마이홈 재매핑과 LH 보강을 공고 단위의 한 트랜잭션에서 반영한다.
보강 입력이 잘못됐거나 공급행 매칭에 실패하면 매핑 변경까지 롤백하고 매핑 실패를 기록한다.
주택형이 바뀐 공급행에 새 임대금액이 없으면 이전 주택형의 금액을 이어 붙이지 않고
공고 전체의 변경을 보류한다. 금액이 없는 같은 주택형의 기존 값 보존 정책은 유지한다.
주택형이 없던(미연결) 공급행이 새로 연결되는 경우는 이어질 이전 금액이 없으므로 이 보류 대상이 아니다.
LH 금액이 `공고문 참조`처럼 비어 있어도 연결을 저장하고 금액 대상은 빈 상태로 둔다.
매핑 실패가 남아 있으면 뒤따르는 독립 보강 단계도 기존 LH 공고를 수정하지 않는다.
두 단계는 같은 전역 수집·정제 실행 잠금 아래에서 실행되고, 쓰기 트랜잭션마다 실행 소유권을 다시 확인한다.
정상 원천으로 매핑을 다시 완료하면 실패 기록이 해결되고 새 주택형·금액을 함께 반영한다.

전체 정제에서 최초 LH 공고는 공급·상세의 현재 성공 연결을 확인한 뒤 마이홈 매핑 결과를 공개하고
LH 보강을 시도한다. 보강에 실패해도 확인된 공고·공급행은 유지한다. 단건 등록과 관리자 보정 재정제는 최초 공고여도
보강까지 같은 트랜잭션에서 검증하고, 실패하면 공고 한 건을 되돌린다. 처음부터 임대금액이
없으면 금액 대상은 빈 목록으로 응답하며 이전 금액을 끌어오지 않는다. 따라서 최초 공고의
보강 실패만을 이유로 공고 전체를 숨기지 않는다. 이미 LH 보강을 마친 공고의 재정제는
기존 금액과 새 주택형이 섞이지 않도록 위 트랜잭션 경계를 적용한다.

## 실패 사유

| 사유 | 의미와 조치 |
|---|---|
| `LH_COLLECTION_REQUEST_UNSUPPORTED` | 현재 URL·공급유형으로 수집 요청을 확정할 수 없음. 수집 실패·건너뜀 기록과 원천을 확인 |
| `LH_COLLECTION_LINK_NOT_FOUND` | 공급 또는 상세의 성공 연결이 없음. 공고 수집 재실행 |
| `LH_COLLECTION_LINK_MISMATCH` | 현재 요청과 이전 성공 연결이 다름. 새 요청 수집 실패 원인 해결 후 재실행 |
| `LH_DETAIL_SOURCE_NOT_FOUND` | 성공 연결은 있지만 상세 원천이 없음. 원천 저장 상태와 성공 수집 기록 확인 |
| `LH_SUPPLY_LINK_REVIEW_REQUIRED` | 관리자가 저장한 LH 공급 연결의 원천이 바뀜. 공고문을 다시 확인해 연결을 저장하거나 해제 |

상세 원천 누락은 보강에서 기록한다. 연결 실패의 상세 메시지에는 공급·상세 구분을 남긴다.
기존 공고가 없거나 공급유형이 지원되지 않으면 보강의 기존 선행 검증 사유가 기록될 수 있다.
`PAN_ID_NOT_FOUND`는 기존 실패 이력 호환을 위해 enum에 남기지만 새 연결 조회에서는 사용하지 않는다.

## 불완전한 공급 응답의 원천 보존

- 같은 조회 조건(수집 버전을 뺀 조회 조건 해시)의 공급 원천이 있으면 전체 0행 결과로 교체하지 않는다.
  저장 트랜잭션에서 삭제 전에 거절하고 수집 실패를 기록하며, 원천·성공 수집 기록·연결을 보존한다.
- 비어 있지 않아도 기존 단지명·주택형·전용면적·공급면적 조합별 행 수가 줄면 전체 교체를 거절한다.
  중복 행도 개수로 비교하며, 순서 변경과 행 추가는 허용한다. 식별 조합이 유일한 행의
  금액·세대수 변경도 허용한다. 면적의 숫자 표기는 정규화한다.
- 같은 조합의 기존 행들이 서로 다른 세대수·금액 값을 가지면 값별 행 수도 보존해야 한다.
  모두 같은 값인 중복 행은 행 수를 유지하면서 함께 값을 갱신할 수 있다. 서로 다른 값의 행을
  구분할 추가 식별값이 없어 어느 행이 바뀌었는지 알 수 없는 변경은 자동 교체를 보류한다.
- 현재 조회 조건의 마지막 성공 원천과 비교한다. 수집 버전이 바뀌어도 같은 조회 조건이면 기존 원천 보호 규칙을 유지한다.
  서로 다른 조회 조건은 비교하지 않는다.
- 비교할 기존 원천이 없는 최초 빈 결과는 마이홈 공급행과 LH 상세를 사용하는 기존 동작을 유지한다.
- 정상 재수집은 실패를 해결한다. 실제 공급 철회, 이름·면적 정정, 구버전 식별값 누락 행의 보정은
  자동 교체를 보류한다. 원문과 보존된 원천을 확인한 별도 데이터 정정이 필요하며 수집 재시도로 우회하지 않는다.
- API 명세에는 전체 행 수가 없어 최초 수집의 완전성이나 처음부터 누락된 신규 행은 증명할 수 없다.
  이 검사는 이미 저장한 행의 누락으로 인한 삭제를 막는다. 반복되는 부분 응답도 성공으로 승격하지 않는다.

## 연결 복구와 재정제

1. `POST /api/admin/ingest/pipelines/announcement-collection`을 실행한다. 수집은 현재 조회 조건의 원천을 실제 조회하고 성공한 요청의 공고별 연결을 갱신한다. 실패한 재수집은 마지막 성공 원천·이력·연결을 보존한다.
2. 종료 후 30일이 지나 일반 수집에서 제외된 공고는 LH 공고 ID(`panId`)로 아래 두 원천을 재조회한다. 최신 공고목록에 있는 그 공고의 요청만 받으며, 목록에 없는 ID는 400으로 거절한다. 같은 요청의 일정·금액·첨부를 다시 가져올 때도 이 API를 사용한다.
   - `POST /api/admin/ingest/lh/announcements/details/{panId}/refresh`
   - `POST /api/admin/ingest/lh/announcements/supplies/{panId}/refresh`
3. 공급·상세의 현재 요청 해시와 성공 연결을 모두 확인한 뒤 `POST /api/admin/ingest/pipelines/announcement-refinement`를 실행하고 실패 기록을 확인한다. 한쪽 연결만 있거나 현재 요청과 다르면 기존 제품 데이터를 보존하고 정제를 보류한다.

조회·정제는 현행 저장 구조를 사용한다. 기존 원천 이관·보존과 배포는 [수집 저장 구조 전환](../../operations/database/ingest-upgrade.md)을 따른다.
요청 성공률과 제품 정보 충족률, 확인된 공급 감소 처리는 [LH 품질 운영](../../operations/ingest/lh-quality.md)을 따른다.
