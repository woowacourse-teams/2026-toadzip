# 단지 등록 현황

마이홈 원천 수집과 서비스 단지 등록은 별도 작업이다. 관리자 단지 수집 화면의 3단계 ‘단지 등록’에서
기존 단지와 신규 등록 대상을 구분하고, 등록 준비 상태와 다음 작업을 확인한다.

현재는 기존 단지 판별과 준비 상태의 확인·저장·조회까지 지원한다. 신규 단지·주택형의 실제 등록과
실패 대상 재처리는 후속 단계에서 구현한다. 지원 종료된 전체 정제 실행은 다시 열지 않는다.

## 대상과 기존 단지 판별

- 대상은 마이홈의 `hsmpSn:공급유형 코드`마다 하나다. 한 단지의 여러 주택형은 함께 검증한다.
- 건설임대 제외 정책은 [단지 연결·통합](complex-linking.md#적용-범위)과 같다. 지원하지 않거나 누락된 공급유형은
  `hsmpSn:UNKNOWN`으로 모아 정보 보완 대상으로 남긴다.
- 서비스의 원천 연결(`myhome_complex_links`)을 먼저 확인하고, 연결이 없으면 단지의 마이홈 식별자를 확인한다.
  원천 테이블에 행이 있다는 이유로 기존 단지나 등록 완료로 표시하지 않는다.
- 연결이 없으면 PNU, 정규화한 도로명주소, 같은 시군구의 단지명으로 기존 후보를 찾는다. PDF로 먼저 등록한 단지도 포함한다.
  후보가 하나이고 단지명·주소·PNU·공급유형·공급기관이 모두 같을 때만 기존 단지로 분류한다.
  후보가 여러 곳이거나 값이 다르면 ‘정보 보완 필요’와 후보 단지 ID를 표시한다. 자동으로 원천 연결을 만들지 않는다.
- 원천 연결이나 마이홈 식별자로 찾은 기존 단지가 휴지통에 있으면 ‘정보 보완 필요’로 남기고 복구 여부를 확인하도록 안내한다.
  중복 후보로만 발견한 휴지통 단지는 기존 단지로 확정하지 않고, 다른 불명확한 후보와 같이 관리자 확인 대상으로 남긴다.

## 상태와 보존

| API 상태 | 화면 이름 | 의미와 다음 작업 |
|---|---|---|
| `EXISTING` | 기존 단지 | 서비스에 이미 등록되어 건너뜀 |
| `LOCATION_REQUIRED` | 좌표 준비 필요 | 주소 누락, 주소 불일치, 좌표 미제공·변환 문제 확인 |
| `INFORMATION_REQUIRED` | 정보 보완 필요 | 필수값·원천 충돌, 중복 후보 또는 누락된 원천 확인 |
| `READY` | 등록 가능 | 필수 정보와 지도용 좌표 확인 완료 |
| `FAILED` | 등록 실패 | 후속 등록 단계에서 저장 실패를 기록한 상태 |
| `COMPLETED` | 등록 완료 | 후속 등록 단계에서 단지·주택형·원천 연결 저장을 마친 상태 |

`EXISTING`은 기존 단지로 판별한 대상, `COMPLETED`는 후속 등록 단계에서 새로 등록한 대상이다.
대상 상태 확인은 `EXISTING`·`LOCATION_REQUIRED`·`INFORMATION_REQUIRED`·`READY`를 판정한다.
상태 재확인으로 `FAILED`를 `READY`로 바꾸거나 `COMPLETED`를 새로 만들지 않는다.

상태·사유·서비스 단지 ID·확인 시각은 `initial_registration_targets`에 저장하므로 화면을 닫거나 서버가 재시작되어도 유지한다.
대상의 단지명과 도로명주소는 원천 값을 잘라내지 않고 저장한다.
완료 대상은 재확인하지 않으며 기존 상태와 연결을 보존한다. 원천이 사라져도 대상 기록은 삭제하지 않는다.
이때 `EXISTING`·`COMPLETED`는 상태를 유지하고, 나머지는 ‘정보 보완 필요’와 원천 누락 사유를 남긴다.
등록 가능은 마지막 확인 시점의 준비 상태이며, 실제 저장 직전의 원천 변경 검증을 대신하지 않는다.

## 상태 확인 시점

마이홈 단지 수집 후 대상 상태를 자동 확인한다. ZIP 좌표 적재는 위치정보와 상태 갱신을 같은 트랜잭션에서 반영한다.
이미 수집한 원천이 있거나 수집 중 중단되어 일부 원천만 저장된 경우에는 화면의 ‘대상 상태 확인’을 실행한다.
이 작업은 외부 수집을 반복하지 않으며 서비스 단지·주택형·원천 연결을 변경하지 않는다.

## 주소·좌표 준비

2단계 ‘주소·좌표 준비’에서 ZIP을 올리거나 저장된 준비 현황을 확인한다.
ZIP 결과의 주소 수는 원천 도로명주소의 중복을 제거한 수다. `matchedRoadAddressCount`는 주소가 일치한 수,
`preparedRoadAddressCount`는 이번 ZIP에서 WGS84 변환·범위 검증까지 통과한 고유 주소 수다.
원천 주소가 없는 단지는 고유 주소 수에 포함할 수 없으므로 아래 단지별 현황에서 별도로 집계한다.

단지별 준비 현황은 기존 단지·등록 완료 대상을 제외하고 좌표 준비 완료와 다음 실패 사유를 표시한다.
좌표 준비 완료 수에는 보존한 정상 ZIP 좌표와 관리자 보완값도 포함한다. 나머지 필수 정보가 부족하면
좌표가 준비되어도 등록 상태는 ‘정보 보완 필요’로 남는다.

| 사유 | 의미와 보완 방법 |
|---|---|
| `INVALID_ADDRESS` | 주소 누락·형식 오류. 원천 주소를 확인하고 검색 또는 직접 입력으로 보완한다. |
| `ADDRESS_NOT_FOUND` | 주소 불일치. ZIP에서 원천 도로명주소를 찾지 못했으므로 올바른 주소를 확인한다. |
| `COORDINATE_NOT_FOUND` | 주소는 일치하지만 원본 좌표가 없다. 검색으로 좌표를 찾거나 위도·경도를 직접 입력한다. |
| `COORDINATE_CONVERSION_ERROR` | 원본 좌표를 지도용 위도·경도로 변환·검증하지 못했다. 좌표를 다시 확인한다. |

보완 목록에는 단지명·원천 주소·실패 사유를 표시한다. ‘주소·좌표 보완’에서 기존 관리자 주소 검색을 이용하고,
검색 실패·결과 없음·좌표 미제공이면 직접 입력한다. 주소를 직접 바꾸면 입력한 좌표를 비우므로 새 주소의
위도·경도를 다시 확인해야 한다. 서버도 주소와 위도·경도를 함께 받아 검증하며 부분 저장을 허용하지 않는다.
저장 직후 준비 상태를 다시 확인하므로 ZIP을 다시 올리거나 3단계 등록을 실행할 필요가 없다.

원천 주소는 보완값으로 덮어쓰지 않는다. 적용 주소·위도·경도, 출처(`ZIP`·`ADMIN`), 확인 시각과
관리자 보완의 처리자를 대상 테이블에 별도로 저장한다. 원천 주소가 달라지면 이전 주소의 보완 좌표를 재사용하지 않는다.
잘못된 ZIP이나 좌표 없는 ZIP은 기존 정상 좌표와 관리자 보완값을 지우지 않는다.
ZIP 저장 정책과 파일 검증 조건은 [주소 좌표 적재](../../operations/ingest/location-import.md)를 따른다.

## 관리 화면

- 단지 수집 화면은 선택한 단계만 표시한다. ‘단지 등록’ 탭을 오가도 상태 필터·표시 건수·페이지를 유지한다.
- 상태별 건수는 전체 대상을 기준으로 집계한다. 상태 필터는 대상 목록과 목록의 총건수·페이지 수에만 적용한다.
- 화면은 실행 종료·ZIP 처리 후 목록을 다시 읽는다. 상태 필터로 남은 대상과 사유를 조회하며,
  조회 실패는 오류와 재조회 버튼으로 안내한다.
- 표시 건수는 10·20·50·100건 중 고른다. 첫 방문에는 20건을 조회하고, 마지막 선택을 브라우저에 저장해
  새로고침하거나 다시 방문해도 사용한다. 상태 필터를 바꿀 때는 선택 건수를 유지하고, 표시 건수를 바꾸면 첫 페이지로 돌아간다.
  저장된 값이 없거나 지원하지 않는 값이면 20건을 사용한다. 브라우저 저장소가 차단되면 현재 화면에서만 선택을 유지한다.
- 지난 정제 결과는 ‘실행 이력’에서 확인한다. 지원 종료 전에 시작한 정제가 실행 중이면 별도 안내에서 중지할 수 있다.

## API

- `GET /api/admin/ingest/myhome/initial-registration`: 상태별 전체 건수(`counts`)와 대상 목록(`targets`)을 반환한다.
  `status`는 선택 사항이고 `page`는 0부터 시작한다. `size`를 생략하면 50건, 최대 200건을 조회한다.
  화면은 선택한 표시 건수를 `size`로 전달하므로 첫 방문에는 20건을 조회한다.
  목록은 원천 식별자 순으로 정렬한다. `counts`는 상태 필터와 무관한 전체 집계이며,
  `targets`·`totalElements`·`totalPages`는 선택한 상태를 기준으로 반환한다.
- `POST /api/admin/ingest/myhome/initial-registration/refresh`: 저장된 원천과 제품을 다시 비교해 상태를 저장하고 204를 반환한다.
  관리자 세션·CSRF와 기존 수집 쓰기 잠금을 사용한다. 다른 수집·적재 실행과 겹치면 기존 잠금 정책으로 거절한다.
- `GET /api/admin/ingest/myhome/initial-registration/locations`: 단지별 좌표 준비·실패 사유별 전체 건수(`counts`)와
  보완 목록(`targets`)을 반환한다. `page`는 0부터, `size`는 기본 20·최대 200이며 원천 식별자 순으로 정렬한다.
- `POST /api/admin/ingest/myhome/initial-registration/locations`: `sourceComplexIdentifier`, `address`,
  `latitude`, `longitude`를 받아 관리자 보완값을 저장하고 상태를 다시 판정한 뒤 204를 반환한다.
  위도·경도는 WGS84이며 소수 여덟 자리까지, 위도 -90~90·경도 -180~180 범위를 허용한다.
  관리자 세션·CSRF·수집 쓰기 잠금을 적용한다. 기존 단지·완료 대상과 현재 원천에 없는 대상은 보완할 수 없다.
  원천·서비스 단지·주택형·원천 연결은 수정하지 않는다.

## 배포

`V20261105_02`로 상태 테이블과 조회 인덱스를 만들고, `V20261105_03`으로 단지명·주소를 `text`로 확장한 뒤
서버·화면을 배포한다. 확장 시 기존 대상 기록은 보존한다. 기존 제품 행을 변경하거나
전체 원천을 마이그레이션에서 일괄 판정하지 않는다. 배포 후 기존 원천은 ‘대상 상태 확인’으로 준비한다.
이전 서버는 이 테이블을 사용하지 않으므로 되돌릴 때 테이블을 삭제할 필요가 없다.

주소·좌표 준비는 `V20261108_01`로 nullable 준비 컬럼과 좌표 완전성·범위 제약을 추가한 뒤 서버·화면을 배포한다.
기존 원천·진행 상태·서비스 연결은 유지하며, 기존 대상의 위치 준비 결과는 ‘주소·좌표 상태 확인’으로 채운다.
이전 서버는 추가 컬럼을 무시하므로 애플리케이션을 되돌릴 때 보완값을 삭제할 필요가 없다.
