# 수집·정제 실행 계약

진행 표시·중지 API·실패 조회와 배포 조건은 [관리자 실행 제어](../../operations/ingest/execution-controls.md)를 따른다.

## 실행 상태

- API의 통합 실행은 `단지 수집·정제`(4단계), `공고 수집·정제`(6단계)다. 수집·정제 단독 실행 네 유형도 유지한다.
- 단지 수집·정제와 공고 수집·정제는 각자의 최신 실행 상태를 독립적으로 보존한다.
- 관리자 파이프라인은 PostgreSQL advisory lock을 획득한 실행만 시작한다.
- 시작 직후 `RUNNING` 실행을 저장하고 단계 시작·완료마다 현재 상태를 갱신한다.
- 전체 단계가 끝나면 `COMPLETED`, 정제·보강에서 처리되지 않은 원천 행이 있으면
  `COMPLETED_WARNINGS`, API 호출 제한으로 건너뛴 단계가 있으면 `COMPLETED_WITH_SKIPS`로
  저장한다. 누락과 건너뜀이 함께 있으면 `COMPLETED_WARNINGS`이며 두 단계 보고서를 모두 보존한다.
- 원천 행 누락은 단계 보고서에 남긴다. 현재 단지·공고 매칭 실패는 개별 실패 이력에도 남지만,
  LH 주택형 누락은 보고서의 건수로만 남는다. 운영 장애로 분류된 부분 실패는
  후속 단계를 한 번씩 계속 실행한 뒤 최초 실패를 대표 실패로 저장하고 실행을 `FAILED`로 끝낸다.
- 예상하지 못한 서버 오류가 발생하면 이후 단계를 실행하지 않고 즉시 `FAILED`로 기록한다.
- 한 단계의 실패가 모두 외부 API 호출 제한이면 해당 단계와 응답을 건너뜀으로 보존하고 다음 단계를 실행한다. 단, LH 공고 수집 단계(목록·공급·상세)가 호출 제한에 걸리면 뒤의 LH 공고 수집 단계도 건너뛴다. 통합 실행에서는 어느 수집 단계든 호출 제한에 걸리면 정제를 건너뛴다.
- 호출 제한은 재시도하지 않으며, 전국 병렬 수집 중이면 대기 중인 지역 요청도 취소한다.
- 호출 제한과 다른 운영 실패가 섞인 결과는 부분 실패로 처리하되, 동일 실행에서 실패한 단계 전체를 다시 실행하지 않는다.
- 단지 정제의 좌표 변환 오류(위치정보 DB 조회의 `COORDINATE_CONVERSION_ERROR`)와 저장 오류(`PERSISTENCE_ERROR`)는 운영 실패로 분류한다. 주소 형식 오류·위치정보 DB에 없는 주소·좌표 미제공(`INVALID_ADDRESS`·`ADDRESS_NOT_FOUND`·`COORDINATE_NOT_FOUND`)과 정제·보강의 매칭 불가·원천값 오류, 매칭된 LH 단지 안의 주택형 누락은 행별 누락으로 분류한다.
- 상태 조회는 애플리케이션 메모리가 아니라 DB의 유형별 최신 실행을 사용한다.
- 완료 단계와 실패 응답을 보존하므로 다른 인스턴스나 클라이언트 재접속에서도 같은 결과를 조회한다.
- 실행 중에는 30초마다 실행 행의 heartbeat를 갱신한다. 새 실행이 advisory lock을 획득하면
  시작 전에 2분 넘게 갱신되지 않은 과거 RUNNING 실행을 실패로 복구하고 마지막 단계를 남긴다.
  실행 ID 또는 유형별 최신 상태 조회에서도 잠금이 없고 heartbeat가 만료된 실행을 복구한다.
  복구 직전 상태와 heartbeat를 다시 확인한다.
- 실행 범위 안의 쓰기 트랜잭션은 잠금 세션과 실행 소유자·세대값을 확인하고 소유권 행의 공유 잠금을
  커밋까지 유지한다. 커밋 직전에도 잠금 세션을 확인해 소유권을 잃은 실행의 쓰기를 롤백한다.
  후속 실행의 소유권 이전은 기존 쓰기 트랜잭션이 끝날 때까지 기다린다.

`COMPLETED`는 선택된 작업의 완료 상태다. 모든 공고의 최신성이나 금액·일정 충족률을 보증하지 않는다. 요청 성공률과 제품 정보 충족률은 [LH 품질 운영](../../operations/ingest/lh-quality.md)에서 구분한다.

수집 구간은 일부 실패가 있어도 뒤의 LH 단계를 계속 실행하며, 성공한 원천 저장은 되돌리지 않는다. 후속 단계가 읽는 저장 원천에는 이번 실행과 이전 실행의 데이터가 섞일 수 있다. 통합 실행의 자동 정제 차단과 독립 정제 복구는 아래 실행 방법을 따른다.

## 실행 방법

- 수집·정제는 관리자 요청으로만 시작한다. 서버 부팅·예약·장애 복구는 새 ingest 실행을 만들지 않는다.
- 알림 보관 기간 정리는 공통 스케줄링으로 실행하는 별도 작업이다.
- 관리자가 `POST /api/admin/ingest/pipelines/{type}`으로 본문 없이 직접 시작한다. 공공데이터포털 수집 키는 서버 설정만 쓴다([수집 키](../../operations/ingest/execution-controls.md#수집-키)). `announcement-sync`(화면 이름 LH 공고 갱신)는 하나의 실행 ID·잠금으로 LH 공고 수집 후 정제를 수행한다.
- 단지 정제는 지원을 종료했다. 단지는 원천 수집(`complex-collection`)만 실행하고, 이후 단지·주택형은 공고와 PDF 보정으로만 바뀐다. `complex-refinement`·`complex-sync` 시작, `POST /api/admin/ingest/myhome/complex-mappings`, LH 세대수 보강(`/api/admin/ingest/lh/housing-type-households`)의 실행·단지 연결·대상 결정 `POST`는 `410 INGEST_OPERATION_RETIRED`로 거절하고 실행을 만들지 않는다. 지난 실행 이력과 실패·비교 조회(`GET`)는 그대로 쓴다.
- 통합 실행에서 수집 부분 실패가 있으면 수집 구간 뒤 `FAILED`로 끝내고 정제를 시작하지 않는다. 호출 제한만 있으면 정제 단계를 사유와 함께 건너뛰어 `COMPLETED_WITH_SKIPS`로 끝낸다.
- 공고 통합 실행(`announcement-sync`)은 `LH 공고 목록 수집` 뒤 `LH 공고 수집·정제` 한 단계다. 후자는 최신 목록의 후보를 같은 조회 조건의 요청 묶음으로 나눠, 묶음마다 공급을 받고 성공하면 상세를 받은 뒤 그 묶음의 공고를 정제한다. 외부 호출만 병렬(공고 ID가 같은 요청은 동시에 실행하지 않음)이고 정제는 실행 스레드에서 묶음이 끝나는 순서대로 한다. 공급이나 상세를 다 받지 못한 묶음은 정제하지 않고 이전 값을 유지하며 대기 상태로 남아 다음 실행이 이어받는다. 호출 제한이면 새 요청을 시작하지 않고 `COMPLETED_WITH_SKIPS`로 끝나며, 이미 끝난 묶음은 정제돼 있다. 실행 끝에는 이번 실행에서 목록 값이 바뀌었지만 묶음에서 정제하지 않은 공고(종료 정책 밖 공고)를 정제하고, 원공고를 찾지 못한 정정·취소공고를 다시 이어 재정제한다. 목록 수집이 호출 제한이면 수집·정제 단계는 건너뛴다. 공고 수집 단독 실행(`announcement-collection`, 정제 없음)과 전체 정제 단독 실행(`announcement-refinement`, 90일 밖 옛 원천 포함)은 그대로다. 이전 이력의 공급·상세·정제 세 단계는 그대로 읽을 수 있다.
- 단지 화면의 실행 진입점과 좌표 업로드 후 동작은 [관리자 가이드](../admin/guide.md#단지-수집)를 따른다.
- `complex-collection`, `announcement-collection`, `announcement-refinement`의 기존 단계·동작을 보존한다.
- 마이홈 공고 한 건 등록(`announcement-registration`)은 지원을 종료했다. `POST /api/admin/ingest/pipelines/announcement-registration`은 다른 실행 유형과 같은 경로로 받아 본문 없이 부르면 `410 INGEST_OPERATION_RETIRED`로 거절하고(본문을 보내면 400이 된다) URL 등록 API는 없앴다. 지난 등록 실행 이력은 그대로 읽는다.
- 새 실행은 `MANUAL`로 기록한다. 과거 자동 실행의 `SCHEDULED`·`RECOVERY` 트리거와
  예정 시각·상위 실행 ID는 기존 실행 이력 조회를 위해 읽을 수 있다.

## 단지 화면의 결과와 오류 조회

- 단계별로 독립 실행과 기존 `COMPLEX_SYNC` 중 시작 시각이 더 늦은 결과를 표시한다. 통합 실행이 진행 중이면 해당 실행을 우선한다.
- 수집·정제의 결과 오류는 실행이 끝나거나 중지된 뒤 `GET /api/admin/ingest/failure-reviews`에 `domain=complex`, `status=ALL`, `executionId`와 선택한 분류를 전달해 조회한다. 검색어와 페이지도 서버 조회에 반영한다.
- 오류 API는 해당 실행에서 마지막으로 발생한 오류의 현재 기록을 반환한다. 같은 오류가 이후 실행에서 재발하면 과거 실행 필터에서 빠질 수 있다. 실행 이력에는 개별 오류의 스냅샷을 제공하지 않는다.
- `좌표 문제`는 API에 사유 필터가 없어 단지 정제 오류의 모든 페이지를 조회한 뒤 `GEOCODING` 사유를 분류한다. 한 페이지라도 조회에 실패하면 부분 결과를 성공이나 오류 없음으로 표시하지 않는다.
- 실패 검토 API가 지원하지 않는 세대수 보강 오류 분류는 제공하지 않는다. 세대수 보강 결과는 단계별 보고서의 집계로 확인한다.
- 기존 통합 실행은 현재 처리 중인 구간에 중지 버튼을 표시한다. 새 정제는 저장 원천 전체를 처리하는 별도 실행이며, 이전 실행의 재개가 아니다.

## 배포와 복구

DB 초기화와 마이그레이션은 [Flyway 도입 절차](../../operations/database/flyway.md)를 따른다. `ddl-auto=validate`는 스키마 변경을 적용하지 않는다.

- 실행 중인 ingest를 종료하고 이전 서버 인스턴스를 중지한 뒤 서버·관리자 화면을 함께 교체한다. 실행 유형·상태·실패 사유를 모르는 구버전과 혼합 실행하지 않는다.
- 배포 후 실행·단계 테이블, 실행 소유권 테이블, 실패 테이블의 상태·발생 횟수·실행 ID와 관련 인덱스를 확인한다.
- 실패 이력은 장애·재발 추적에 사용하며 자동 삭제하지 않는다. 현재 실패와 이력 API는 `page`(0부터 시작), `size`(기본 100, 최대 200)로 조회하고 `/failures/page`도 같은 계약을 제공한다.
- 롤백 전에 실패 테이블을 백업한다. 구버전 ingest는 실패 이력을 삭제할 수 있으므로 실행을 중지한 상태에서 호환성을 확인하고 복구한다. 실행·실패 이력 테이블은 별도 백업과 승인 없이 삭제하지 않는다.

기존 원천의 이관·보존과 누락된 마이그레이션 확인은 [수집 저장 구조 전환](../../operations/database/ingest-upgrade.md)을 따른다. 일정 단지명 컬럼과 기존 일정 재정제는 [공고 일정 대상](announcement-mapping.md)을 따른다.

## SH 공고 수집·정제

`POST /api/admin/ingest/pipelines/sh-announcement-collection`은 API 키 없이 SH 검색·상세 원천을 목록 한 페이지씩 수집하고, 페이지를 마칠 때마다 그 페이지에서 고른 글을 바로 미확정 공고로 정제한다. 상세를 이번에 새로 받은 글뿐 아니라 목록 값이 같아 상세를 다시 받지 않은 글도 함께 정제하며, 상세를 받지 못한 글은 저장된 원천이 있을 때만 정제한다. 실행은 `SH 공고 수집·정제` 한 단계이고 보고서는 수집 수치(`collection`)와 정제 수치(`refinement`)를 함께 담는다. 실행 결과 화면은 완료 뒤 공개 전 확인이 필요한 공고 목록(`/admin/announcements?unconfirmed=true&provider=SH`)으로 안내하고, GH도 `provider=GH`로 같다. 호출 제한(429)이면 재시도 없이 남은 요청을 멈추고 `COMPLETED_WITH_SKIPS`로 끝나며, 이미 처리한 페이지는 정제돼 있고 남은 글은 `pending_collection_targets`에 남아 다음 실행이 이어받는다. 호출 제한이 아닌 수집 실패나 정제 실패가 섞이면 처리한 페이지의 정제는 남기고 실패로 끝난다. 이전 이력의 `SH 공고 원천 수집`·`SH 공고 정제` 두 단계는 그대로 읽을 수 있다. 정제 범위는 이번 실행이 고른 글(조회 기간 안의 글과 이어받는 대기 글)이라, 조회 기간 밖에 보관된 옛 원천은 정제 규칙이 바뀌어도 다시 정제되지 않는다. 통합 게시판(`m_241`)에 `모집` 검색 폼을 POST한다. 건설임대만 다루므로 주택임대 분류(`multi_itm_seqs=2`)만, `itm_seq_1=1`, `notType1=0`, `annType1=on`, `srchTp=0`과 폼의 페이지 번호를 사용한다. 첫 GET으로 세션을 확보하고 쿠키·Referer를 유지한다.

상세 제목·등록일을 목록 값과 대조한 뒤 제목, 담당부서, 등록일, 본문 텍스트와 첨부 메타데이터를 `sh_announcement_source`에 저장한다. 본문은 공백·빈 줄을 정리하고 문단과 표의 행 구분을 유지한다. 첨부에는 게시판 코드·게시글 ID·실제 파일 ID·파일명·크기·미리보기 URL이 포함된다. PDF 외 첨부도 보존한다. 목록·상세 HTML과 HTML 조각은 DB에 저장하지 않는다.

- 주택임대 분류에도 올라오는 매입임대·기존주택 전세임대 글(제목에 `매입임대`·`전세임대`)은 상세를 받지 않는다. 분양·토지·상가/공장·주택매입·채용 분류는 요청하지 않는다.
- 게시글 키는 `SH:{seq}`다. `seq`는 SH 사이트가 부여한 게시글 번호이며, 같은 글을 다시 수집하면 기존 행을 갱신한다. 게시판 URL 경로는 키에 포함하지 않는다.
- 재시도를 포함한 모든 요청 앞에 1초(`ingest.sh.request-interval`)를 둔다.
- 목록의 제목·등록일이 저장값과 같고, 본문·첨부를 모두 읽어 두었고, 그 글(`seq=…`)에 열린 수집 실패가 없고, 마지막 수집 뒤 재수집 기한(`ingest.board-announcement.refetch-after`, 기본 7일)이 지나지 않았으면 상세를 다시 받지 않고 건너뛴 수로 센다. 실행 ID는 쓰지 않는다.
- 상세 호출 또는 파싱이 실패하면 기존 값을 보존하고 수집 실패 목록에 `seq`와 사유를 기록한다. 본문이나 첨부 중 일부만 읽으면 읽은 부분만 저장하고 실패를 열어 두어 다음 실행에서 다시 받는다. 제목이나 등록일이 바뀐 새 판에서 못 읽은 부분은 옛 판 값을 남기지 않고 비운다. 다른 게시글은 계속 처리하며, 다시 다 읽으면 실패를 해소한다.
- `attachments = []`는 첨부가 없는 공고다. `body_text = ''`는 추출할 텍스트가 없는 본문이다. 값이 NULL이면 아직 읽지 못한 부분이다. 이미지의 텍스트를 추정하지 않는다. 첨부파일 다운로드·내용 파싱은 수행하지 않는다.
- 신청 일정·자격·공급호수는 게시글마다 구조가 달라 별도 필드로 추정하지 않는다. 본문 텍스트에 있는 내용은 그대로 제공한다.
- HTML을 보관하지 않으므로 파서 수정 후에는 다시 수집한다. 기본 수집 대상은 등록일 기준 최근 90일이다. 전체 과거 공고가 필요하면 `ingest.sh.lookback-days=0`으로 실행한다.

### SH·GH 정정공고 연결

게시판 목록에는 정정공고와 원공고를 잇는 값이 없어서, 공고명의 정정 표시를 뗀 이름으로 원공고를 찾는다(`BoardRevisionName`, 연결은 `BoardRevisionLinker`). 정정 표시는 SH가 앞 `(수정)`·`[수정]`·`[정정]`, 뒤 `(정정)`·`(수정)`·`(수정-…)`, GH가 `[정정공고]`·`(수정)`이다. 표시가 없는 공고(`…서류심사대상자 발표` 같은 후속 안내 포함)는 정정공고로 보지 않는다.

- 같은 기관의 이전 공고 중 정정 표시를 뗀 이름이 같고, 공고일이 정정공고보다 늦지 않으며 90일 안이고, 휴지통 공고가 아니며, 다른 공고가 이미 이어 가지 않은 공고 중 가장 최근 것이 하나일 때만 `previous_announcement`로 잇고 상태를 정정으로 바꾼다. 하나로 정해지지 않거나 없으면 잇지 않고 미확정 공고로 둔다(관리자 확정).
- 정정공고를 정제할 때 시도하고, 원공고가 뒤 페이지라 아직 없었던 정정공고는 실행 끝(수집이 429로 멈춘 뒤에도)에 이번 실행에서 정제한 연결 안 된 정정공고만 다시 시도한다. 이미 이어졌거나 관리자가 고친 공고는 바꾸지 않는다.
- 보고서의 `revisionsLinked`는 이번 실행에서 이은 수, `revisionsUnlinked`는 마무리 뒤에도 원공고를 정하지 못한 정정공고 수다. 소유권 상실·중지 요청이면 마무리 재연결은 실행하지 않는다.

### SH 공고 정제

`ShAnnouncementRefinementService.begin()`이 돌려주는 실행은 수집이 넘긴 페이지의 SH 원천을 등록일·게시글 번호 순으로 원천마다 한 트랜잭션(`REQUIRES_NEW`)에서 미확정 공고로 정제하고 결과를 실행 동안 누적한다. 저장된 원천 전체를 한꺼번에 읽는 정제는 없다. 생성·갱신·동일·원천 검토·휴지통·실패 건수를 보고서의 `refinement`에 표시한다. 실행 소유권을 잃으면 원천 실패로 삼키지 않고 즉시 멈춘다.

- 공고: 식별자 `SH:{게시글 번호}`의 미확정 공고를 만들고, 공고명·게시일·원문 URL 갱신과 공개·관리자 수정·휴지통 공고 보호는 GH 정제와 같다. 공개와 신규 공고 알림은 관리자가 PDF 보정을 적용할 때만 한다.
- 일정: 본문 요약에서 읽은 인터넷 접수기간·당첨자 발표일 후보(`ShAnnouncementBodyParser`)를 미확정 공고에 채운다. 관리자가 고치거나 접수 일정을 확인하기 전까지는 원천이 이 값을 가지므로 본문을 따라 바꾸고, 읽지 못한 값은 비운다. 그 뒤나 공개된 공고는 덮지 않고, 원천이 읽은 값이 다를 때만 원천 검토 대상으로 표시한다. 본문을 못 읽은 원천은 일정을 그대로 둔다. 공급유형·모집유형은 채우지 않는다.
- 첨부: 원천 첨부 중 PDF만 공고문으로, 첨부 식별자(`brdId:fileSeq`)로 한 번만 붙인다. 첨부를 못 읽은 원천은 붙인 첨부를 그대로 둔다.
- 공고 단지·공급행: 본문에 단지·주택형·세대수가 없으므로 만들지 않는다. 관리자가 PDF 보정에서 공고문으로 만든다.

구형 SH 원천에서 전환할 때는 ingest를 중지하고 원천을 백업한 뒤 새 키의 재수집 결과를 확인한다. `V20261011_01__sh_announcement_content.sql`은 본문·첨부 열을 추가하고 HTML 열을 제거하지만 기존 행을 삭제하거나 키를 변환하지 않는다. 서버·관리자 화면은 같은 원천 형식으로 함께 교체한다.

## GH 공고 수집

`POST /api/admin/ingest/pipelines/gh-announcement-collection`은 API 키 없이 GH주택청약센터(`apply.gh.or.kr`)의 청약공고 원천을 목록 한 페이지씩 수집하고, 페이지를 마칠 때마다 그 페이지의 글을 같은 실행에서 미확정 공고로 정제한다. 실행 단계와 호출 제한·실패 처리는 [SH 공고 수집·정제](#sh-공고-수집정제)와 같다. `www.gh.or.kr`의 분양/임대 공고 게시판은 `robots.txt`가 전체 수집을 막고 있어 쓰지 않는다.

건설임대만 다루므로 임대주택(`sr7150`) 게시판만 수집한다. 매입임대(`sr7155`)와 임대상가(`sr7170`)는 수집하지 않는다. 목록은 `selectPbancRentHouseList.do?pageIndex={page}`, 상세는 `selectPbancDetailView.do?pbancNo=…&pbancKndCd=…&previewYn=N`을 GET으로 읽고, 재시도를 포함한 모든 요청 앞에 `ingest.gh.request-interval`(기본 1초) 간격을 둔다.

상세의 공고명·유형·공고일을 목록 값과 대조한 뒤 게시판, 공고 번호, 공고 종류 코드, 공고명, 공급유형, 지역, 게시일, 마감일, 공고 상태와 상세의 의미 단위를 `gh_announcement_source`에 저장한다. 목록·상세 HTML과 줄글 본문은 DB에 저장하지 않는다. 값은 화면에 보이는 원문 그대로 두고 숫자·날짜 해석은 읽는 쪽에서 한다.

| 열 | 내용 |
|---|---|
| `districts` | 공급정보 지구 JSON 배열. 화면에서 탭을 눌러야 보이는 지구도 모두 담는다. 지구마다 지구명·소재지·전용면적 범위·모집호수·난방방식·입주예정월, 단지 관련 이미지(평면도·조감도·배치도 이름과 주소), 주택형(주택형 코드·사업 코드·모집 회차·이름·전용면적·금회공급 세대수·임대보증금·월임대료·인터넷청약 상태, 팝업 요청 값 `detailRequest`, 상세공급정보 팝업의 `detail`: 공급면적·주거공용면적·기타공용면적·지하주차장면적·계약면적·세대수·금회분양 세대수·금액 원문·주택형 이미지), 공급일정(이름·값), 지구 안내사항, 지구 접수처(행복주택)를 둔다. 공급정보가 없는 공고는 `[]`다. |
| `reception` | 공고 단위 접수처(소재지·전화번호·운영기간) JSON 객체. 지구마다 접수처가 있는 행복주택은 `{}`다. |
| `notice`, `other_notes` | 공고 단위 안내사항·기타사항 텍스트. 줄바꿈을 유지하고 구획이 없으면 빈 문자열이다. |
| `attachments` | 공고문 첨부의 첨부 묶음·파일 식별자, 파일명, 크기와 다운로드 URL |

상세를 읽은 뒤 주택형마다 상세공급정보 팝업(`selectPblancHouseTyDetail.do`)을 같은 요청 간격·재시도로 POST한다. 팝업을 받지 못한 주택형은 `detail` 없이 두고 `주택형 상세(지구 주택형)`을 사유로 공고 실패를 열어 두며, 팝업이 호출 제한(429)을 받으면 남은 팝업과 다음 요청을 멈춘다. 임대보증금·월임대료는 화면·팝업 모두 대부분 `공고문 확인`으로만 나와 원문 그대로 저장한다. 위 구획 외의 제목이 상세에 나오면 사이트 구조가 바뀐 것으로 보고 `알 수 없는 구획(제목)`을 사유로 실패를 열어 둔다.

- 게시글 키는 `GH:{pbancNo}`다. 한 실행에서 페이지를 넘어 같은 공고 번호가 다시 나오면 뒤 목록 페이지를 실패로 기록한다. 같은 공고를 다시 수집하면 기존 행을 갱신한다.
- 목록에 `-`로 표시된 마감일·공고 상태는 `NULL`로 저장한다. `attachments = []`는 공고문 행이 없는 공고다.
- 같은 게시판에 저장된 공고의 제목·게시일이 목록과 같고, 모든 구획을 읽어 두었고, 그 공고(`pbancNo=…`)에 열린 수집 실패가 없고, 마지막 수집 뒤 재수집 기한(`ingest.board-announcement.refetch-after`, 기본 7일)이 지나지 않았으면 상세를 다시 요청하지 않고 `skippedRequestCount`에 센다. 제목·게시일이 저장값과 같고 모든 구획을 읽어 둔 공고는 상세를 다시 받든 건너뛰든 목록에서 바뀌는 지역·마감일·공고 상태를 먼저 저장값에 맞추며, 이때 수집 시각은 그대로 둔다.
- 상세는 게시판·공고명·유형·공고일이 목록과 맞을 때만 저장한다. 공급정보·접수처·안내사항·기타사항·첨부는 구획마다 따로 읽어, 읽지 못한 구획은 저장값을 덮지 않고(새 공고면 `NULL`) 그 구획을 사유로 실패를 열어 두어 다음 실행에서 다시 받는다.
- 실패는 목록 `board={게시판 코드}&page={page}`, 상세 `pbancNo={공고 번호}` 단위로 기록하고 기존 값을 보존한다. 목록 실패는 뒤 페이지를 받지 않는다. 호출 제한(429)을 받으면 남은 요청을 모두 멈춘다.
- 기본 수집 대상은 게시일 기준 최근 90일이다. 전체 과거 공고가 필요하면 `ingest.gh.lookback-days=0`으로 실행한다. HTML을 보관하지 않으므로 파서 수정 후에는 다시 수집한다.

### GH 공고 정제

`GhAnnouncementRefinementService.begin()`이 돌려주는 실행은 수집이 넘긴 페이지의 GH 원천을 게시일·공고 번호 순으로 원천마다 한 트랜잭션에서 미확정 공고로 정제한다. 한 원천이 실패하면 그 원천만 되돌린다. GH 제품 단지 색인은 실행당 한 번 만든다. 보고서의 `refinement`에 생성·갱신·동일·원천 검토·휴지통·공급 재확인·실패 건수를 실행 보고서에 표시한다.

- 공고: 식별자 `GH:{공고 번호}`의 미확정 공고를 만든다. 이미 있으면 공고명·게시일·원문 URL이 다를 때만 맞춘다. 공개됐거나 관리자가 고친 공고는 덮지 않고 원천 검토 대상(`source_review_required`)으로 표시하며, 휴지통 공고는 건드리지 않는다. 일정·공급유형은 채우지 않는다. 공개와 신규 공고 알림은 관리자가 PDF 보정을 적용할 때만 한다([PDF 보정 계약](../admin/review-api.md#공고-전체-json-선택-갱신)).
- 첨부: 원천 첨부 중 PDF만 공고문으로, 첨부 식별자(`atchFileSn:atchFileDtlSn`)로 한 번만 붙인다. 첨부를 못 읽은 원천은 붙인 첨부를 그대로 둔다.
- 공고 단지: 지구마다 공고 단지를 만들고, 새 공고 단지만 GH 제품 단지 하나를 미리 고른다(AUTO). PNU의 산 여부·본번·부번이 소재지 지번과 같고, 도로명 주소에 소재지 시군구가 있고, 공급유형이 같은 단지가 정확히 하나일 때만 고른다. 소재지는 지번이라 도로명 키를 쓰지 않으며, 여러 필지(`일원`, `일대`, `외 N필지`)·블록 소재지는 고르지 않는다. 같은 이름의 지구는 한 공고 단지로 보고 이름이 빈 지구는 건너뛴다. 공고 단지의 주소 칸에는 지번을 그대로 두므로 도로명 주소로 쓰지 않고, 모집호수는 총 세대수가 아니라 비운다. 지구를 못 읽은 원천은 공고 단지를 빠진 것으로 보지 않는다.
- 공급행 틀: 지구의 주택형마다 `{공고 식별자}:{지구명}:{주택형 코드}` 공급행을 만든다. 공급행은 지구의 공고 단지를 가리켜 관리자가 공고 단지를 다시 연결하면 따라간다. 단지는 미리 고른 제품 단지, 세대수는 금회공급 세대수이고 주택형 연결은 비운다. 금회공급 세대수는 공고문 공급표의 모집 칸 합이라 공고에 따라 예비당첨자 수가 들어 있다(대구신서 33A: 당첨자 34 + 예비 22 = 56). 사용자 공고 상세는 PDF 보정한 공급행이 없으면 세대수에 예비 입주자가 포함될 수 있다고 안내한다. 제목에 `예비입주자`가 있으면 재공급, 아니면 신규공급으로 둔다. 관리자가 PDF 보정 등으로 공고를 손댔거나(휴지통에서 복구한 공고 포함) 공개했거나 공고 단지를 직접 연결한 공고는 틀을 다시 쓰지 않는다. 그 뒤 원천 공급(행 키·주택형명·세대수·공급구분)이 바뀌면 공급 재확인 대상(`supply_recheck_required`)으로 표시한다. 미리 고른 단지는 관리자가 바꾸는 값이라 원천 변경으로 보지 않는다. 원천과 같으면 아무것도 바꾸지 않는다.

SH·GH 정제에서 개별 원천이 실패하면 실행 보고서의 `failures`에 원천 키와 확인 안내를 보존한다. 관리자 실행 단계에서 원천을 조회하고 해당 기관 수집을 다시 실행한다. 내부 저장 오류의 SQL·스택은 보고서에 넣지 않으며 실행 ID에 해당하는 서버 로그로 확인한다.
