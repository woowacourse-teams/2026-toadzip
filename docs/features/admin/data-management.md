# 관리자 데이터 관리

## 화면

- `/admin/complexes`: 단지 검색, 기관·임대유형·지역 필터, 검토 대상과 휴지통 조회.
- `/admin/announcements`: 공고 검색, 단지 연결 조건과 공통 필터.
- 상세 화면: 기본정보, 연관 데이터, 출처·수정 이력으로 분리한다.
- 공고 상세에서 공급정보의 단지·주택형 연결과 근거가 있는 접수 일정을 수정한다.
- 공급정보 편집표의 행 편집에서 대표 주택형과 `함께 모집하는 주택형`(세부 타입 26B·26C)을 보고 고친다. 연결이 있는 행은 펼칠 때 단지 주택형을 불러와 이름·전용면적으로 보여 준다. 같은 단지의 기존 주택형을 고르거나(대표·이미 연결한 주택형과 전용면적이 같은 주택형은 후보에서 뺀다) 새 주택형을 이름·전용·공급면적으로 만들어 연결하고, `빼기`로 연결을 뺀다. 새 주택형을 만들 때는 단지 주택형을 불러온 뒤에만 연결할 수 있고, 단지에 같은 전용면적 주택형이 있으면 새 주택형 대신 그 주택형을 고르게 한다. 고친 행은 고친 목록 전체를 `linkedHousingTypes`로 보내고(모두 빼면 빈 목록으로 대표만 남김), 손대지 않은 행은 조회한 값을 그대로 둔다. 대표나 단지를 바꾸면 빈 목록을 보내 연결을 비우므로, 대표를 바꿨다가 되돌려도 이전 연결이 살아나지 않는다. 공통 모집 묶음 행(저장된 묶음이나 PDF로 채운 새 묶음)은 서버가 연결을 받지 않으므로 이유만 보여 주고 고칠 수 없다. 미리보기는 바뀐 연결을 `주택형 #id`·새 주택형 값으로 보여 준다.
- 단지 상세의 주택형·연결 공고 탭에서 주택형을 추가하거나 이름·전용면적·세대수를 수정하고, 주택형 하나만 휴지통으로 옮기고 복구하며, 연결 공고의 기본정보·일정·공급정보를 같은 탭에서 편집한다.
- `/admin/ingest/announcements`·`/admin/ingest/complexes`: 공고·단지 실행 요약, 기술 상세와 이력. 기존 `/admin/ingest`·`/admin/ingest-v2`는 새 경로로 이동한다.
- LH 정확성 지표와 확인된 공급 감소 재조회는 [운영 절차](../../operations/ingest/lh-quality.md)를 따른다.
- `/admin/failures`: 수집·정제 실패 확인과 전체 작업 재실행. 개별 행 재시도가 아니다.
- 단지 등록 화면의 주소 자동 채우기는 기존 등록 단지의 주소를 검색한다.
- PDF 보정은 단지 DB에 연결되지 않은 공급행을 PDF 단지명별로 묶어 `단지 정하기`에서 한 번 정한다. 기존 단지를 고르거나 새로 등록하면 같은 단지명의 공급행 전체에 연결하고, 맞는 주택형이 없는 행은 PDF 형명·면적으로 새 주택형을 추가하도록 고른다.
- 최초 입주자 공고처럼 단지에 연결되지 않은 LH 원천행이 있으면, `단지 정하기`에서 새 단지를 등록할 때 공고문 주택형(형명·전용·공급면적)도 함께 만들고 원천행을 공고문 행에 맞춘다. LH 행 표기(`26A/B/C(고령자)`)의 세부 타입이 공고문 행 하나면 그 행에 연결한다. 여럿이면 대상·금액이 같을 때 그 공고문 행들을 원천행 하나의 세부 타입 묶음으로 접어, 모집수는 LH 행의 이번 공급 수로 두고 세부 타입 주택형을 모두 그 행에 연결한다. 대상·금액이 행마다 다르면 원천행을 첫 세부 타입으로 고쳐 쓰고 나머지를 새 행으로 더해 LH 행의 이번 공급 수를 공통 모집수로 묶고 확인하게 한다. 공고문 행 하나가 여러 LH 공급대상 묶음에 대응하면 행을 묶음마다 복사하고 대상은 묶음 이름으로 나누며, 어느 묶음에도 없는 대상은 첫 묶음에 넣어 확인하게 한다. 공고문에 대응하는 행이 없는 원천행은 그대로 둔다. 기존 단지를 고르면 주택형은 만들지 않고, 없는 주택형은 `공고문 주택형 N개 추가`로 만든다.
- 새 단지 등록 양식은 PDF 추출 결과의 `data.complexes` 단지 개요(주소·전체 세대수·주차대수)로 미리 채우고, 개요에 없는 주소·전체 세대수는 수집한 마이홈 공고 원천(`full_adres`·`tot_hshld_co`)으로 채운다. PNU는 연결하지 않은 원천 공급행의 PNU를 먼저 쓰고, 없으면 마이홈 공고 원천의 `pnu`를 쓴다. 주소 검색 후보를 정해도 원천 PNU와 법정동이 같으면 원천 PNU를 유지해 다음 정제에서 원천행이 이 단지를 찾게 한다. 마이홈 공고의 난방·주택유형도 함께 저장한다. 전체 세대수·주차대수는 공고문에 없으면 비워 둘 수 있다. 미확인은 `null`로 저장하고 실제 0과 구분하며, 모집수로 대신하지 않는다. 마이홈 개요는 같은 단지의 원천만 사용한다. 행정안전부 도로명주소 검색·좌표제공 API로 그 주소를 찾아 주소·PNU·행정구역 코드·좌표를 채운다. 서버가 추출 주소와 같은 주소로 판정한 후보(`matchesKeyword`)가 하나면 고르지 않아도 채우고, 그 후보에 좌표가 없으면 좌표만 직접 입력하게 안내한다. 판정한 후보가 없거나 여럿이면 직접 고른다. 주소를 정하면 서버가 알려 준 같은 곳의 등록 단지(`registeredComplexes`)를 새로 만들기 전에 먼저 보이고 그 단지에 연결하는 버튼을 둔다. 단지만 만들고 주택형·공급행 연결을 마치지 못했으면 이어서 연결하거나 다른 단지에 연결할 수 있다. PDF 단지명으로 검색한 기존 단지가 없으면 새 단지 등록을 바로 연다. 주소 상세와 선택 항목은 펼쳐서 수정한다. 행정구역 코드는 검색 결과의 코드를 쓰므로 PNU가 없어도 등록할 수 있다. 좌표는 서버가 받는 소수 여섯 자리로 맞춘다. 좌표가 없는 후보는 `좌표 없음 · 직접 입력`으로 안내하며 이전 주소의 좌표를 재사용하지 않는다. 키가 없거나 결과가 없으면 직접 입력한다.
- 새 단지를 등록하면 PDF의 형명·전용면적으로 주택형을 함께 추가하고 같은 단지의 공급행에 연결한다. 서버와 같이 같은 전용면적은 재생성하지 않는다. 후속 생성·조회가 실패해도 생성된 단지 ID를 검토 초안에 보존하고 `등록한 단지에 이어서 연결`로 재시도한다. 연결을 마치기 전에는 보정 적용을 막는다.
- 단지 PNU와 공급행 소재지 PNU는 지번을 모르면 비워 둔다(마이그레이션 `V20261102_02`이 `housing_complexes.pnu`의 NOT NULL을 풀고 빈 문자열만 막는다). 값이 있으면 빈 문자열은 받지 않는다. PNU 없는 단지는 PNU로 찾는 마이홈 단지 연결과 공고 등록의 단지 후보에서 나오지 않는다.

## API

`/api/admin/housing-complexes`, `/api/admin/announcements`에 다음 경로를 제공한다.

| 요청 | 동작 |
|---|---|
| `GET /` | 필터와 페이지 기반 목록. 공고는 `unconfirmed=true`로 공개 전 확인이 필요한(미확정) 공고만 볼 수 있다 |
| `GET /{id}` | 관리자 상세 |
| `PUT /{id}` | 현재 `version`과 변경값으로 수정 |
| `DELETE /{id}?version=...` | 휴지통 이동 |
| `POST /{id}/restore?version=...` | 복원 |
| `GET /{id}/changes?page=...` | 변경 전후 값·작업자·시각 이력 |

- 공고의 `PUT /{id}/supply-rows/{rowId}`로 공급정보와 연결 대상을 수정한다. `supplyRow`에는 원천 이름 대신 선택적 `announcementHousingTypeName`을 보낸다. 대표 주택형을 바꾸면 함께 모집하던 주택형은 빠지고 새 대표만 남는다. 이력의 변경 전후 값에는 연결 전체(대표 포함)를 `housingTypeIds`로 남긴다.
- 단지의 `POST /{id}/housing-types`는 단지 `version`, `name`, `exclusiveArea`와 선택값 `supplyArea`, `householdCount`로 주택형을 추가한다. 같은 이름은 409로 거절한다. PDF 보정의 새 단지 등록처럼 공고문 값으로 만들 때는 `fromAnnouncement: true`를 보내 관리자 수정으로 보호하지 않는다.
- 단지의 `PUT /{id}/housing-types/{typeId}`는 단지 `version`, `name`, `exclusiveArea`, `householdCount`를 받는다. 면적은 소수점 네 자리까지, 세대수는 `null`(미확인)과 0을 구분한다.
- 단지의 `DELETE /{id}/housing-types/{typeId}?version=...`과 `POST /{id}/housing-types/{typeId}/restore?version=...`은 주택형 하나를 휴지통으로 옮기거나 복구하고 단지 상세를 반환한다. 공급행이나 공급 매칭 판단이 가리키는 주택형은 409로 거절한다. 휴지통 주택형은 기록을 보존하고 관리자 상세에만 `deleted: true`로 남으며 공개 상세·면적 필터·매칭 후보에서 빠진다. 마이홈 재정제는 같은 원천 주택형을 다시 만들지 않는다. `DELETE_HOUSING_TYPE`·`RESTORE_HOUSING_TYPE` 이력을 기록한다.
- 공고 수정의 접수처 연락처는 미확인이면 `null`을 유지한다. 접수처명·접수방식·URL 검증과 공고 신규 등록의 연락처 필수 규칙은 유지한다.
- 기존 `PUT /{id}/application-schedules`는 선택적 `version` 쿼리로 충돌을 확인한다.
- `/api/admin/ingest/pipelines/history?page=...&size=...`는 실행 이력을 제공한다. `domain=complex`는 단지 실행만, `domain=announcement`는 LH 공고와 SH·GH 공고 수집 실행을 돌려준다.
- `GET /api/admin/addresses?keyword=...`는 주소 후보(최대 5개)의 도로명·지번주소, PNU, 법정동·시도·시군구 코드, 위도·경도를 돌려준다. 좌표가 없는 주소(건물 없는 지번 등)나 좌표를 위경도로 변환하지 못한 후보는 위도·경도가 `null`이고 나머지 값은 그대로 돌려준다. `matchesKeyword`는 검색어와 후보가 같은 곳인지다. 도로명주소는 (시도, 도로명, 건물번호), 지번은 (시도, 법정동·리, 산 여부, 번지)가 같으면 `true`이며, 시·도 약칭·옛 이름(`서울시`, `강원도`, `전라북도`), 띄어쓰기, 괄호 참고항목, 건물명 차이는 무시한다. 시·도가 없는 검색어는 `false`다. `registeredComplexes`는 후보와 같은 필지(PNU)이거나 같은 시(시군구 코드 앞 네 자리)의 같은 (도로명, 건물번호)인 휴지통 밖 단지이며, 저장 주소가 구를 빼거나 시도를 줄여 써도 찾는다. 선택 파라미터 `sourcePnu`(원천행·마이홈 필지)를 주면 후보와 법정동이 같을 때 그 필지의 단지도 포함한다. 키는 `JUSO_ADDRESS_API_KEY`(도로명주소 검색), `JUSO_COORDINATE_API_KEY`(좌표제공)이고, 없거나 외부 API가 실패하면 503 `ADDRESS_LOOKUP_UNAVAILABLE`, 검색어 문제는 400 `INVALID_ADDRESS_KEYWORD`다. 요청은 연결 2초, 응답 3초 제한이며 재시도하지 않는다.
- 세션 인증과 쓰기 요청의 CSRF 검증을 유지한다. 관리자 CORS는 PUT·DELETE도 허용한다.
- 이름·주소는 부분 일치, 원천 식별자는 정확한 일치로 검색한다. 장기전세도 조회·수정한다.
- 목록은 `totalElements`와 `totalPages`를 반환하고 등록 시각 내림차순, 같은 시각은 ID 내림차순으로 정렬한다.
- `V20260926_06`부터 등록 시각을 기록한다. 과거 등록 시각은 추정하지 않고 NULL로 유지하며, 새 등록 건 뒤에서 ID 내림차순으로 표시한다.

### PDF 자동 추출

- 추출은 AI 작업 큐(`ai_jobs`)로 한다. Spring은 작업을 넣고 상태·결과를 읽으며, 관리자 취소와 마감 정리로만 진행 중 작업을 `FAILED`로 끝낸다. 꺼내기·lease·재시도·완료 기록과 추출은 저장소 최상위 `ai-worker/`의 Python 워커가 한다. 워커는 FOR UPDATE SKIP LOCKED로 작업을 꺼낸다.
- `POST /api/admin/announcements/{id}/pdf-extractions`는 multipart `file`(공고문 PDF, 30MB 이하)을 받아 작업을 넣고 202와 작업 상태를 돌려준다. 빈 파일·30MB 초과·읽을 수 없는 PDF는 400 `ANNOUNCEMENT_PDF_INVALID`, 없는 공고는 404다. 화면은 관리자가 내 PC에서 고른 PDF에만 쓴다.
- `POST .../pdf-extractions/attachments/{attachmentId}`는 공고에 수집된 첨부를 서버가 공개 첨부 API와 같은 경로·제한으로 받아 작업을 넣는다. 응답과 30MB·PDF 검사, 409는 업로드와 같고, 첨부를 받지 못하면 첨부 API와 같은 `ATTACHMENT_*` 오류다. 진행 중 작업이 있으면 첨부를 받지 않는다.
  - 같은 공고에 진행 중 작업(`PENDING`·`RUNNING`·`RETRY`)이 있으면 새로 넣지 않고 409 `ANNOUNCEMENT_PDF_EXTRACTION_IN_PROGRESS`다. 화면은 진행 중 작업을 이어서 기다린다.
  - 작업을 넣을 때 이 공고의 LH 공급 API 행(공고 번호마다 공급행이 있는 가장 최근 원천, LH가 보낸 문자열 그대로)을 입력 스냅숏으로 담는다. 워커는 도메인 테이블을 읽지 않는다.
- `POST .../pdf-extractions/jobs/{jobId}/cancel`은 진행 중 작업을 `FAILED`(`CANCELLED_BY_ADMIN`)로 끝내고 그 작업 상태를 돌려준다. 이미 끝난 작업은 바꾸지 않고 현재 상태를 돌려준다. 워커가 작업을 가져가지 않을 때 화면이 기다림을 멈추고 다시 요청하게 하는 데 쓴다.
- 작업을 넣거나 상태를 읽기 전에, 넣은 지 40분(워커 마감과 같음)이 지난 진행 중 작업을 `FAILED`(`DEADLINE_EXCEEDED`)로 끝낸다. 워커가 멈춰 있어도 오래된 작업이 새 추출을 막지 않는다.
- 작업 상태는 `GET .../pdf-extractions/jobs/{jobId}`, 진행 중 작업은 `GET .../pdf-extractions/jobs/active`(없으면 `null`)로 읽는다. 다른 공고의 작업 ID는 404 `ANNOUNCEMENT_PDF_EXTRACTION_JOB_NOT_FOUND`다.
  응답 `data`는 `jobId`, `status`(`PENDING`·`RUNNING`·`RETRY`·`SUCCEEDED`·`FAILED`), `fileName`, `pdfSha256`, `attempts`, `createdAt`, `completedAt`(끝나기 전 `null`), `failure`(`FAILED`일 때 `{code, message}`), `retryReason`(`RETRY`일 때 직전 일시 오류 `{code, message}`), `extraction`(`SUCCEEDED`일 때 추출 결과)이다.
- 추출 결과는 `json`(추출 JSON 문자열, 근거 쪽 번호는 원본 PDF 기준), `pages`(모델에 보낸 원본 쪽, 1부터), `totalPages`, `warnings`, `usage`(`promptTokens`·`outputTokens`·`thinkingTokens`, 모르면 `null`)다. 워커와 주고받는 입력·결과 형식은 [계약 예시](../../../ai-worker/contract/README.md)를 원본으로 한다.
- 워커는 첫 쪽과 공급표·임대조건표·일정·문의처·선정 순위가 있는 쪽만 골라 쪽 텍스트와 표를 DeepSeek(`deepseek-flash`, 생각 수준 low)에 보낸다. 공급표나 임대조건표를 찾지 못하면 전체 쪽을 보내고 경고를 남긴다. LH 공고는 입력 스냅숏의 LH 공급 API 행을 공급행 틀로 함께 보낸다.
  응답이 JSON 객체가 아니거나 `data`가 없으면 `FAILED`다. 날짜 형식·표기 규칙 위반, 근거 인용문이 그 쪽 원문에 없음, LH API와 다른 공급행 수·모집수는 값을 고치지 않고 `warnings`에 담는다.
- 일시 오류(네트워크, 429, 5xx, 시간 초과)만 1분, 5분 뒤 다시 시도하며 처리는 작업당 최대 3번(워커 `MAX_ATTEMPTS`)이다. 잘못된 PDF, 인증·잔액 오류는 바로 `FAILED`다. 한 번의 처리는 10분 안에 끝내며 마감까지 그만큼 남지 않은 작업은 꺼내지 않는다. 다시 시도할 시각이 그 기한을 넘으면 기다리지 않고 그 오류로 바로 `FAILED`다. 워커는 처리하는 동안 lease를 늘리고, 멈춘 워커의 작업은 lease(3분)가 끝나면 다른 워커가 다시 꺼낸다. 넣은 지 40분이 지난 작업은 상태와 관계없이 `FAILED`(`DEADLINE_EXCEEDED`)로 끝낸다. 큐 상태 전이 규칙은 [계약 예시](../../../ai-worker/contract/README.md)에 둔다.
- 화면은 3초마다 작업 상태를 묻고, 재시도를 기다리는 동안 `retryReason`을 보여 준다. 기다린 지 3분이 지나도 `PENDING`이면 워커가 처리를 시작하지 않았다고 알린다. 워커 마감보다 조금 긴 45분이 지나면 기다리기를 멈춘다. 진행 중인 작업이 다른 PDF의 것이면 이어 기다리지 않고 알린다.
- PDF는 처리 중에만 작업 행에 보관하고 `SUCCEEDED`·`FAILED`가 되면 비운다(DB 제약으로 강제). 공고 데이터에는 반영하지 않고, 공고를 지우면 작업도 함께 지운다.
- 워커는 `ai_jobs`만 읽고 상태·결과 열만 고칠 수 있는 DB 역할 `toadzip_ai_worker`를 쓴다. 역할은 [`infra/db/create-ai-worker-role.sql`](../../../infra/db/create-ai-worker-role.sql)과 [배포 운영](../../operations/deployment.md#ai-워커) 절차가 만든다. 마이그레이션은 역할이 있을 때만 권한을 주고, 스크립트는 이미 마이그레이션된 DB에도 같은 권한을 준다.
- `GET /api/admin/announcements/{id}/pdf-extractions/latest`는 가장 최근에 성공한 작업의 결과를 모델 호출 없이 돌려준다. `data`는 `fileName`, `pdfSha256`(소문자 16진수), `createdAt`(작업이 끝난 시각), `extraction`이며 성공한 작업이 없으면 `null`이다. 예전 동기 추출 결과(`announcement_pdf_extractions`)는 `V20261103_01`에서 성공 작업으로 옮겼다.
- 자동 테스트는 실제 모델을 부르지 않는다. 실제 호출은 키를 설정한 로컬 워커에서 확인한다.

## 데이터 규칙

- 삭제는 복구 가능한 상태 변경이며 공개 목록·검색·지도·상세에서 제외한다.
- 사용 중인 연결 공고가 있는 단지는 삭제할 수 없다.
- 후속 정정·취소 공고가 있으면 이전 공고를 먼저 삭제할 수 없다.
- 복원 시 이전 공고와 연결 단지가 먼저 복원되어 있어야 한다.
- 버전이 다르면 409로 응답한다. 입력은 유지하고 새 조회 후 다시 수정한다.
- 변경과 이력 저장은 한 트랜잭션이다. 데이터 수집 실행권으로 동시 정제와 충돌을 차단한다.
- 관리자 수정 단지·공고는 레코드 단위로 자동 덮어쓰기를 막는다. 원천과 차이가 있으면 검토 대상으로 표시한다.
- 관리자 수정 공급정보 역시 자동 덮어쓰기를 막는다. 원천 식별자와 원본 수집 데이터는 보존한다.
- 공급행의 원천 단지명·원천 주택형명은 정제만 바꾸는 매칭 기준이다. 관리자 수정 행도 재정제가 이 두 값을 원천에 맞춰 갱신한다.
  관리자는 공급행의 `announcementHousingTypeName`(이 공고의 주택형 표기)만 수정한다. 비었거나 연결한 단지 주택형 이름과 같으면 저장하지 않는다.
  공개 화면의 주택형 이름은 공고 표기 → 단지 주택형 이름 → 원천 주택형명 순서이고, 단지명은 연결한 단지 이름을 쓴다.
  단지·주택형 이름 자체는 단지 상세에서 고친다. `V20261024_02`는 보정·공통 모집 행 중 원천 이름이 단지 주택형 이름과 다른 행을 공고 표기로 옮겨 배포 직후 표시를 유지한다.
- 관리자 수정 주택형의 이름·면적은 마이홈 재정제가, 세대수는 LH 세대수 보강이 바꾸지 않으며 원천에서 사라진 주택형 정리의 대상에서도 제외한다. PDF 보정은 공고 값으로 주택형 이름·공급면적·세대수를 갱신하되 관리자가 실제로 바꾼 이름·세대수만 덮지 않는다(필드 단위 보호). 단지 상세에서 만든 주택형은 입력한 이름과 세대수를 보호하고, PDF·공급정보 보정(새 단지 등록 포함)으로 만든 주택형은 보호하지 않는다. 기본 임대조건(보증금·월 임대료)은 PDF 보정 검토 화면의 '주택형 가격'에서 고른 공급대상 금액으로 갱신한다. 대상 금액이 모두 있고 같으면 그 금액, 다르거나 금액을 읽지 못한 대상이 있으면 '일반' 대상을 미리 고르고 없으면 지금 값 유지가 기본이며, 관리자가 대상이나 유지를 고른다. 지금 값이 이전 PDF 보정에서 고른 공고문 값(`ANNOUNCEMENT`)이고 기본값과 다르면 확인 필요로 띄우고 기본은 유지한다. 가격 칸은 저장할 주택형(반영한 연결 주택형, 아니면 저장 위치의 주택형)을 기준으로 정하며 필터에 보이는 공급행마다 함께 보이고, 그 주택형의 지금 값을 불러오지 못하면 기본은 유지다. 연결 주택형을 바꾸면 고른 가격 대상은 풀린다. 보증금과 월 임대료는 함께 보내야 한다. 공급정보 편집표의 'PDF로 공급정보 채우기'는 주택형 값을 저장하지 않으므로 가격 칸을 보이지 않는다. 더 최근 공고의 값과 같은 주택형을 고른 공급행끼리 다른 금액은 지금 값을 유지한다. 공고 값으로 바꾼 조건은 출처 `ANNOUNCEMENT`로 남고 마이홈 재정제가 덮지 않는다. 저장 시 단지 버전·최종 변경 시각을 갱신하고 `UPDATE_HOUSING_TYPE` 이력을 기록한다. 단지 기본정보의 자동 정제 보호 상태는 바꾸지 않는다.
- 삭제된 데이터가 재수집으로 자동 복원되지 않는다.

## 변경 근거와 임대조건 수정

- 단지·공고·주택형·공급행 수정 요청의 선택적 `documentEvidence`는 공식 출처 URL, 파일명,
  SHA-256, 관리자 메모와 `citations`(항목·쪽수·인용)를 받는다. 기존 요청은 근거 없이도 처리한다.
- 근거는 변경 후 값의 `documentEvidence`로 기존 수정 이력에 같은 트랜잭션으로 저장한다.
  서버는 원문 내용의 진위를 자동 보증하지 않는다. 선택적 문서 근거 계약과 과거 이력은 호환성을 위해 유지한다.
  화면은 연결된 공고문 보기, 수동·JSON 입력과 [PDF 자동 추출](#pdf-자동-추출)을 제공한다. PDF는 추출 작업이 처리되는 동안에만 서버에 두고, 추출 결과는 다시 불러올 수 있게 남긴다.
- 공고 상세의 `supplyTargets`는 공급행·대상별 임대조건을 반환한다. 금액은 정밀도를 보존하는 원 단위 정수 문자열이다.
- `PUT /api/admin/announcements/{id}/supply-targets/{targetId}`는 현재 공고 버전과 공급대상·순위·세대수·예비자수·
  보증금·월임대료·전환보증금·신청조건·선택적 문서 근거를 받아 기존 공급대상 하나를 수정한다.
- 공급대상 수정의 `expectedValues`는 상세 응답의 해당 공급대상 `data`를 그대로 보낸다. 공고 버전이 같아도
  수집기가 임대조건을 바꿨으면 `409`로 중단해 선택하지 않은 최신 값을 보존한다.
- 수정 대상의 공고 소속·삭제 상태·버전·권한·CSRF를 확인하고 공급대상과 공급행을 관리자 수정으로 보호한다.
  LH 재보강·철회·원천 변경 정리에서도 확인한 공급대상을 유지하고, 원천에서 사라진 보호 공급행을 삭제하지 않는다.
  LH 응답 순서가 바뀌어 공급 식별자가 달라져도 같은 공급행에 임대조건을 중복 생성하지 않는다.
- `V20261016_05__protect_admin_supply_target_updates.sql`의 `supply_targets.admin_modified`를 적용한 뒤
  서버와 관리자 화면을 함께 배포한다. 구버전 수집기는 보호 상태를 해석하지 못하므로 혼용하지 않는다.
  앱 롤백 시 열과 근거 이력을 보존하고 공급정보 정제를 중지한다.

## 적용

- Flyway `V20260926_05__admin_data_management.sql`을 적용한다.
- 주택형 편집에는 `V20261008_03__protect_admin_housing_type_updates.sql`이 필요하다. 새 `admin_modified` 열은 기존 행에 false로 추가된다. 스키마 적용 후 새 백엔드·프론트엔드를 배포하며, 구버전 수집기는 주택형 수정 보호를 해석하지 못하므로 혼용하지 않는다. 앱 롤백 시 열을 남겨 데이터는 보존하되 주택형 정제는 중지한다.
- 주택형 휴지통에는 `V20261025_02__housing_type_admin_deleted.sql`이 필요하다. 새 `admin_deleted` 열은 기존 행에 false로 추가된다.
- 구버전 서버는 삭제 상태를 해석하지 못하므로 구·신버전 혼용 운영을 피한다.
- 기존 서버와 수집 작업을 중지한 뒤 마이그레이션을 포함한 백엔드와 프론트엔드를 함께 교체한다.
- 운영 데이터에서 실제 수집 재실행은 이 작업의 검증에 포함하지 않았다.

## 검증 방법과 한계

- 실제 PostgreSQL에서 인증·CSRF, 버전 충돌, 공개 조회 제외, 복원 순서, 원천 덮어쓰기 방지와 접수 일정 변경을 검증한다.
- 프론트엔드 검사 후 실제 브라우저에서 검색 → 상세 → 수정 → 휴지통 → 복원 → 변경 이력을 확인한다.
- 관련·전체 검증 기준은 [백엔드 검증](../../development/backend/testing.md)과 [프론트엔드 검증](../../development/frontend/testing.md)을 따른다.
- 운영 데이터에서 실제 수집 재실행은 기존 검증 범위에 포함되지 않았다. 로컬 검사나 이 문서 정리는 운영 재실행의 성공 증거가 아니다.
- 실행 중 표시되는 번들·Gradle 사용 중단 경고는 해당 실행 버전의 로그에서 별도로 확인한다.
