# 관리자 사용 가이드

## 작업공간과 수집 도구

관리자 기본 진입은 `운영 홈`이다. 왼쪽 메뉴의 매일 하는 작업에서 검토·단지·공고·실패 검토를 연다. 로그인이 만료되면 다시 로그인한 뒤 보던 관리자 화면으로 돌아간다.
수집·원천 도구와 회원·알림 메뉴는 펼쳐서 사용하며, 해당 경로로 직접 접근하면 소속 그룹이 열린다.
모바일에서는 `메뉴`로 탐색을 열고 Escape 또는 다른 페이지 이동으로 닫는다.
데스크톱에서는 `메뉴 접기`로 모든 메뉴를 아이콘만 남길 수 있다. 현재 메뉴의 강조를 유지하며,
아이콘에 마우스를 올리거나 키보드로 접근하면 메뉴명이 표시된다. `메뉴 펼치기`로 복원한다.

### 데이터를 확인하고 수정하기

- 검토 작업실에서 확인할 대상을 찾는다. 빠른 조건·이름·대상·사유 필터는 URL에 남는다.
- 목록의 결과 수는 현재 검색 조건의 총 개수다. 현재 페이지 항목으로 전체 통계를 추정하지 않는다.
- 단지·공고 일반 상세는 읽기로 진입한다. `수정`으로 입력을 열고 저장·취소 후 읽기로 돌아온다.
- 공고 상세는 기본정보 → 공급정보·단지 연결 → 접수 일정 → 공고문·첨부파일 → 출처·수정 이력 순으로 확인한다. 기본정보 수정은 상단 버튼으로 시작한다.
- 공고 상세 상단에 출처(LH 원천·직접 등록·마이홈(과거))와 공급정보 주인(원천 반영·공고문 확정)을 표시한다. 관리자가 공급행·공급대상을 고치거나 PDF로 보정하거나 매칭을 저장하거나 공급행을 나누거나 제외하면 `공고문 확정`이 된다. 지금 정제는 이 값을 읽지 않는다. LH 공고 정제로 바꾼 뒤에는 `공고문 확정` 공고의 공급행을 정제가 원천 값으로 다시 만들지 않는다. 접수 일정 확정은 공급정보 주인을 바꾸지 않는다. `공고문 확정`은 `원천 반영`으로 되돌아가지 않는다.
- 단지 목록은 이름과 검토 상태를 별도 열로 표시한다. 현재 페이지 번호도 다시 눌러 같은 조건으로 조회할 수 있다.
- 공고의 보정 도구 줄과 독립 JSON 갱신 화면은 제거했다. `출처·수정 이력`에서 `수집 원천과 비교`를 펼쳐 확인한다. 단지의 `데이터 검증`은 유지한다. 수집 자료 대조는 공고 전체의 정확성을 인증하는 기능이 아니다.
- 공고 원천 비교는 다른 값부터 표시하고 값 수정 폼 없이 확인 기록·원천 연결만 처리한다. 실제 값이 있는 자료를 먼저 표시한다. 자동 비교 미지원·원천값 없음·현재 원천 소실은 접힌 설명에서 구분한다. 금액 등 자동 비교할 수 없는 값은 `직접 대조`로 표시하며 다른 값이 0개여도 검토 완료는 아니다.
- 공고의 이전 `section=verification` 주소는 `section=history&comparison=source`로 이동해 비교 영역을 펼친다. 이전 `section=json` 주소는 기본정보로 이동한다. 다른 조회·복귀 조건은 유지한다.
- `출처·수정 이력`에서 처리자·시각·근거와 변경 전후를 확인한다. 충돌·미저장 입력 보호와 원천 확인 기준은 유지한다.
- 저장하지 않은 입력이 있을 때 다른 화면으로 이동하면 앱 확인 창이 뜬다. `계속 수정`은 머물고, `저장하지 않고 이동`은 누른 메뉴·링크로 이동한다.
- 단지 주택형은 표의 `삭제`로 바로 휴지통으로 옮기고 같은 줄의 `복구`로 되돌린다. 공급정보가 연결된 주택형은 공고 공급정보에서 연결을 바꾼 뒤 삭제한다.
- 실패·검토 항목 목록은 대상·원인·상태만 보여 준다. 상세 설명·현재 서비스 데이터·처리 기록은 `확인·처리`에서 본다.

### 공고문과 PDF 보정

공고의 `공고문·첨부파일`에서 기존 첨부파일을 미리보기·다운로드한다.
OCR·폴더 에이전트 연동은 제공하지 않는다. PDF 보정 작업 초안은 [PDF 보정 초안](correction-drafts.md)으로 서버에 임시저장한다.
`공고 추가`는 직접 입력을 사용한다. `마이홈에서 가져오기`를 고르면 입력 폼 없이 '마이홈 공고 단건 등록은 지원을 종료했습니다. 공고는 LH 공고 정제와 PDF 보정으로만 바뀝니다.'만 보여 준다. 독립된 JSON 입력은 제공하지 않는다.
기존 공고는 `기본정보 수정`, `PDF로 보정`, `공급정보·단지 연결`에서 작업에 맞게 수정한다.
`공급정보·단지 연결`은 공급정보 표부터 보여준다. `PDF로 채우기`와 `직접 추가`는 같은 편집표에서 수정하고 `공급정보 저장`으로 저장한다. 공급행이 없는 공고도 첫 행부터 추가할 수 있다. PDF에서 채우는 값은 서버 자동 추출 결과를 쓴다.
전체 예제·필드 형식·단위·미확인 값 처리와 복사 가능한 Codex 요청문을 제공하며 자동 전송·저장은 없다.

### 수집·정제

`공고 수집`(`/admin/ingest/announcements`)과 `단지 수집`(`/admin/ingest/complexes`)을 독립 메뉴로 제공한다.
기존 `/admin/ingest`와 `/admin/ingest-v2` 주소는 도메인에 맞는 화면으로 이동한다.
공고 수집은 LH·SH 카드에서 최근 실행과 결과를 확인한다. LH 공고 갱신은 LH 공고 목록·공급·상세 수집 뒤 LH 공고 정제까지 이어서 실행하며 마이홈 공고는 수집하지 않는다.
SH 수집은 제목·본문·첨부 원천을 저장한다. SH의 서비스 공고 등록·정제는 포함하지 않는다.

LH 공고 갱신은 버튼 한 번 → 실행 접수 확인 → 실행 중 단계 → 결과 순서다. 화면에서 API 키를 입력하지 않고 서버의 `DATA_GO_KR_SERVICE_KEY`를 사용한다.
서버에 키가 없으면 화면이 "서버 수집 키 미설정"을 알리고 공공데이터포털 수집 버튼(LH 공고 갱신·공고 수집·단지 원천 수집)을 막는다. 정제와 SH 수집은 실행할 수 있다.
접수 확인과 서버 실행 중 상태를 구분하며 화면을 나갔다 들어와도 서버의 실행 상태를 다시 조회한다.
LH 품질과 공급 감소 보류 정보는 공고 수집의 보조 영역에서 펼쳐 확인한다.
이 지표는 LH 대상이며 전체 기관의 품질이나 이번 실행의 성공률을 뜻하지 않는다.

마이홈 공고 단건 가져오기는 지원을 종료했다. `/admin/announcements/new?mode=myhome`은 지원 종료 안내만 보여 준다.
지난 단건 등록 실행 이력은 계속 보여 주며, 그 실행이 진행 중으로 남아 있으면 수집·정제 실행 잠금에 포함하되 이동 링크는 두지 않는다.

디자인은 기존 사용자용 화면의 토큰·Button을 사용한다. 관리자 스타일은 관리자 영역에만 적용한다.

#### 단지 수집

같은 화면의 가로 탭에서 필요한 단계만 선택해 실행한다. 제목 옆 정보 아이콘에서 단계 설명을 확인하며,
탭을 바꿔도 선택한 ZIP과 진행 상태·결과를 유지한다. 페이지를 다시 열면 서버의 마지막 수집·정제 상태를 조회한다.

| 단계 | 실행 범위와 결과 확인 |
|---|---|
| 단지 원천 수집 | 마이홈 단지와 LH 임대 카탈로그 원본을 저장한다. 화면에서 API 키를 입력하지 않고 서버의 `DATA_GO_KR_SERVICE_KEY`를 사용하며, 키가 없으면 실행 버튼을 막는다. |
| 주소에 맞는 좌표 적재 | 위치정보요약DB 월 전체분 ZIP을 업로드한다. 결과는 중복 제거한 대상·일치·미일치 주소 수이며, 정제를 자동 실행하지 않는다. |
| 단지 정제·저장 | 지원 종료. 실행 버튼은 비활성이고 지난 실행 결과만 보인다. 단지·주택형은 공고와 PDF 보정으로만 바뀐다. |

수집·정제 실행 버튼 옆의 `수집 중지`·`정제 중지`로 현재 실행의 중지를 요청한다.
이미 저장한 데이터는 유지하며 현재 처리 후 종료한다. 중단 지점에서 이어서 재개하는 기능은 없다.

`결과 오류 조회`는 수집·정제 단계에 항상 표시한다. 실행 전에는 기록 없음을, 접수·진행 중에는 조회 가능한 시점을 안내한다.
완료·실패·중지 후 펼치면 해당 실행의 오류 대상·원인·다음 행동을 검색·조회한다. 조회 실패와 오류 없음은 구분한다.
정제 결과의 `좌표 문제`에서 미일치 주소의 원인을 확인한다. ZIP 업로드 결과에는 미일치 주소 목록이 없으며,
이 화면에서는 값을 직접 보정하지 않는다.

제목 옆 `실행 이력`은 모달에서 저장된 시각·상태·단계별 수치를 조회하는 용도다. 실행·오류 조회 버튼은 제공하지 않는다.
오류 기록은 이후 실행에 따라 바뀔 수 있으므로 당시 오류의 스냅샷으로 해석하지 않는다. 실행 완료가 개별 오류의 해결을 뜻하지도 않는다.
오류 조회 범위와 좌표 문제 분류 방식은 [실행 계약](../ingest/executions.md#단지-화면의-결과와-오류-조회)을 따른다.

### PDF로 공고 보정

공고 상세 상단의 `PDF로 보정`은 전용 화면(`/admin/announcements/{id}/pdf-correction`)을 연다.
준비 단계도 검토 단계와 같은 크기의 PDF 영역을 왼쪽에 두고, 그 머리에서 PDF를 고른다.
등록된 PDF 중 종류가 공고문인 첨부, 이름에 `공고문`·`모집공고`가 든 첨부, 첫 PDF 순서로 자동 선택하며, 드롭다운에서 바꿀 수 있다.
등록된 PDF가 있어도 `내 PC에서 PDF 고르기`나 PDF 영역에 끌어다 놓기로 다른 PDF를 쓸 수 있다. 첨부 중 PDF가 없으면 `연결된 PDF가 없습니다`를 표시한다.
오른쪽 패널에서 PDF 첫 쪽의 제목이 이 공고와 같은지 확인한 뒤 추출한다. 호출마다 비용이 들므로 `PDF에서 값 추출`을 누를 때만 [PDF 자동 추출](data-management.md#pdf-자동-추출) 작업을 넣는다. AI 워커가 처리하는 동안 화면은 작업 상태를 몇 초마다 다시 확인하며 로딩바와 경과 시간을 표시한다. 서버가 작업을 받으면 `추출 취소`가 보이고, 누르면 서버에서 작업을 끝내고 기다림을 멈춘다. AI 워커가 작업을 가져가지 않을 때 다시 요청하려면 이것을 쓴다. 넣은 지 40분이 지난 작업은 서버가 끝낸다. 이 공고에 같은 PDF로 진행 중인 추출이 있으면 새로 넣지 않고 그 작업을 기다린다. 진행 중인 추출이 다른 PDF면 기다리지 않고, 그 파일 이름과 함께 끝난 뒤 다시 추출하라는 오류를 표시한다.
추출이 끝나면 공급행·대상·일정 수, 읽은 쪽, 토큰 사용량과 `확인할 점`(서버 경고)을 표시한다. 실패하면 이유와 `다시 추출`을 보여준다. 서버가 추출한 첨부가 화면에서 미리 본 PDF와 다른 파일(SHA-256 비교)이면 그사이 첨부가 바뀐 것이므로 결과를 쓰지 않고 다시 추출하라고 알린다. 같은 PDF로 검토에서 돌아오면 결과를 유지하고, PDF를 바꾸면 이전 결과를 버린다.
추출 결과는 서버에 남긴다. 이 공고에 저장한 결과가 있으면 `이전 결과`에 추출 시각과 파일 이름을 보여주고, `이전 결과 불러오기`는 모델을 부르지 않고 그 결과를 쓴다. 지금 고른 PDF와 같은 파일(내용의 SHA-256 비교)이면 불러오기를 먼저 권하고, 다른 파일이면 그렇다고 알린다.
추출을 마치면 하단의 `추출 결과 검토하기`로 비교·보정 단계로 넘어간다.
응답의 잘못된 이스케이프와 `&#x20;` 같은 HTML 공백 문자 코드는 자동 복구하며 복구 내역은 화면에 표시하지 않는다. 추출 결과는 검토를 거쳐 적용할 때만 공고에 반영한다.
PDF의 공고명·공고일을 현재 공고와 비교해 `일치`·`다름`·`확인 불가`로 표시한다. 수집 공고명의 공고일·`공고` 표기는 비교에서 제외하고, 괄호 위치·어순이나 단지명 뒤의 `단지`·`아파트` 표기만 다르면 같은 공고로 본다. 다르면 추출 요약과 검토 화면 위에 경고하지만 진행은 막지 않는다.

검토 중에는 관리자 메뉴를 숨기고 PDF와 검토표를 나란히 표시한다. 두 영역은 각자 스크롤하고, 위에는 공고·단계·검토 진행·임시저장 상태를, 아래에는 `임시저장`·`미해결 N개 ↓`·`보정 내용 적용`을 둔다. 좁은 화면은 `PDF 보기`와 `검토표 보기`로 전환한다.
공급정보는 위쪽 `공급행 목록`이 단지별로 행마다 주택형·전용·모집수·저장할 곳(`#ID 고침`·`새로 추가`·`#ID 나눔`·`LH 행에 붙임`)·상태(오류·확인 필요·경고·주택형 미연결·적용 제외·준비됨)를 요약하고, 고른 행 하나를 아래에서 편집한다. `단지 주택형 보기`는 그 단지 주택형마다 단지 정보(면적·건설호수·기본 임대조건)와 이번 공고 값(모집수·예비자 수·연결 공급행·PDF 추출 행)을 나눠 보이고, 기존 주택형 연결과 새 주택형 생성을 따로 고르게 한다. 값이 없으면 `없음`으로 둔다.
각 항목에서 `기존 값`·`PDF 추출값`·`직접 입력`을 고르며 입력칸은 직접 입력할 때만 열린다. `반영값`은 저장에 보내는 값이다.
임대조건 표의 `조건 N 대조·수정`에서 같은 방식으로 값을 고른다. 선택을 바꿔도 원래 추출값과 직접 입력값은 유지한다.
근거가 있는 추출값은 `목록 모집수 N과 다름` 같은 참고가 있어도 고를 수 있고 참고는 칸 옆에 둔다. 값이나 근거가 없거나 형식이 틀린 추출값은 고를 수 없는 이유와 `근거 p.N 열기`·`추출값으로 직접 입력`을 칸 옆에 둔다.
`p.N`은 해당 쪽으로 이동해 근거 값을 강조한다. 공급행 칸은 그 행의 공고 주택형 표기·전용면적이 같은 텍스트 줄에 있는 값만 강조하고, 없으면 강조하지 않고 `위치를 찾지 못했습니다 · p.N 원문과 인용문을 확인하세요`와 인용문을 보여 준다. 추출이 잘못 지정한 쪽이나 스캔 문서는 직접 확인해야 한다.
확인되지 않은 값과 선택 해제한 항목은 현재값을 유지하며 임대유형·모집유형·기관·공급구분은 이 화면에서 바꾸지 않는다.

사람이 판단해야 하는 행 대응·일정 대응과 근거가 약하거나 형식이 맞지 않는 값은 `확인 필요`로 센다. 값을 고르거나 `공급행 N 대응 확인`·`일정 N 적용`·`일정 N 적용 안 함`을 누르면 목록에서 빠진다.
섹션 탭에 영역별 확인 필요 수를, 하단에 `미해결 N개 ↓`을 표시한다. 하단 버튼은 화면 순서상 첫 항목의 행을 열고 그 칸으로 포커스를 옮긴다. 저장할 곳 오류(같은 기존 공급정보에 두 행 저장 등)도 미해결로 센다.
검토표 위의 `전체`·`확인 필요`·`변경`·`추가` 칩으로 항목을 거른다. 변경·추가는 추출 당시 상태로 거르므로 값을 골라도 목록에서 사라지지 않는다.
저장하면 적용하는 공급행을 PDF 공급 표 순서로 표시하고, PDF에 없는 기존 공급행은 그 뒤에 원래 순서대로 둔다. 순서가 바뀔 때는 공급정보 영역 위에 바뀔 순서를 알린다.
응답 문장에 한자·가나·키릴 문자가 섞이면(예: `生계`) 확인 필요로 표시하고 기본 반영에서 뺀다. 공고문이 쓰는 `無`·`有`·`外`·`內`는 예외다.
확인 필요 표시는 안내이며 저장을 막지 않는다. 별도의 PDF 대조 확인 체크 없이 값과 저장 위치를 수정하고 `보정 내용 적용`으로 저장한다.
하단에 영역별 변경 수(기본정보·접수처·공급정보·일정)를 항상 보여 주고, `반영할 변경 보기`를 펼치면 현재 → 저장 후 값을 확인할 수 있다.
서버 변경 검증과 확인 토큰 발급 후 같은 보정안을 바로 적용하며, 별도 미리보기 화면으로 이동하지 않는다.
연결이나 날짜 근거가 불명확한 일정은 기본 반영에서 제외한다.
저장은 공고 전체 검토 완료나 정제 오류 해결을 뜻하지 않는다. 공개 화면을 확인하고 필요한 범위의 검토 기록을 별도로 남긴다.
적용 결과에서 공개 공고·저장된 공급정보·출처·수정 이력으로 이동한다. 결과 화면에서 공고를 다시 정제하지 않는다. 이력에는 `PDF로 공고 보정` 한 건이 남고, 공급행 변경(이 공고의 주택형 표기 포함)과 기본정보·접수처·일정의 바뀐 값을 함께 보여준다. 공급행이 고른 주택형의 이름·공급면적·세대수(건설호수)는 이 공고 값으로 맞추고, 결과의 `공고로 갱신한 주택형`에 바뀐 값과 유지한 값을 보여준다. 이름은 검토에서 고른 공고 표기에서 끝의 공급대상 괄호(`39(창업인)`의 `(창업인)`)를 떼어 쓰고 면적만 적힌 표기는 쓰지 않는다. 관리자가 단지 상세에서 직접 바꾼 이름·세대수와 이미 반영한 더 최근 공고의 값은 유지하고, 같은 주택형을 고른 행들의 값이 서로 다르면 그 값은 유지한다. 바뀐 주택형은 단지 이력에 `PDF 공고로 주택형 갱신`으로 남는다. 단지에 같은 전용면적 주택형이 있거나 휴지통에 있으면 새 주택형을 만들지 않는다.
실패 검토의 주택형 대응 오류는 현재 페이지의 같은 공고끼리 묶어 진입하며, 저장 후 원래 목록 조건으로 돌아갈 수 있다. 진입하면 상단에 고칠 공급행과 오류 사유를 보여 준다.

## 검토 절차

변경·검토 이력에서 실제 처리한 관리자와 시각을 확인한다.

### 1. 검토할 대상을 찾기

처리할 일은 `실패·검토 항목`에서 찾고, 그 밖의 대상은 단지·공고 목록에서 검색한다.
단지·공고 목록에서 연 상세는 읽기 화면으로 시작하며 `수정`을 눌러 편집한다.
상세 탭은 URL의 `section`에 남는다.
0·미설치는 빠진 값으로 간주하지 않는다. 원천에 없는 값은 추정해 채우지 않는다.

### 2. DB 원천과 비교·수정

- 단지 기본정보: 기존 `데이터 검증`에서 바로 비교한다.
- 주택형: 같은 화면의 `주택형 원천 비교·수정`을 펼친다.
- 공고: `출처·수정 이력 → 수집 원천과 비교`에서 공고 기본정보·공급행·공급대상 임대조건을 선택한다. 다른 값부터 표시하고 원천 확인 기록·연결만 처리한다. 이전 `section=verification` 링크도 이 위치로 이동한다.
- 비교 가능한 자료를 먼저 보여주고, 자동 비교 미지원·원천값 없음·원천 소실은 접힌 설명에서 확인한다. `다른 값만`은 비교 가능한 값의 차이이며, 단위 확인이 필요한 금액이나 잘못된 날짜 등은 `직접 대조`로 별도 표시한다.
- 자동 연결된 원천을 확인하고 필요한 자료는 `원천 검색·연결`에서 근거를 적어 연결한다.
- 단지·주택형은 `이 원천값 사용` 또는 직접 입력 후 변경 전후·근거를 확인해 저장한다. 공고 기본정보는 `기본정보 수정` 또는 `PDF로 보정`에서 수정한다.
- 공고의 공급행·임대조건은 여기서 비교·원천 확인만 하고, 값 수정은 `공급정보·단지 연결`로 이동해 같은 편집표에서 수정하고 저장한다.
- 금액 문자열의 단위와 적용 범위는 직접 확인한다. 단지 전체 세대수를 주택형 세대수에 적용하지 않는다.
- 충돌하면 입력은 남고 저장은 잠긴다. 필요한 입력을 보관한 뒤 다시 조회해 대조한다.

### 3. 공고문 확인과 PDF 입력

공고 상세의 `공고문·첨부파일`에서 공식 원문 링크와 이미 연결된 첨부파일을 연다.
공개 상세와 같은 PDF·HWP 미리보기를 사용한다. 별도 업로드·텍스트 추출·OCR·폴더 에이전트 설정은 없다.
편집을 멈추고 1.5초 뒤나 `임시저장`으로 작업 상태를 관리자별 초안으로 저장한다. 열 때 초안이 있으면 복원·폐기를 고르게 하며, 초안 뒤 공고가 바뀌었으면 바뀐 공급행을, 다른 PDF였으면 그 사실을 먼저 보여 준다. 다른 탭이 더 최신 초안을 저장했으면 덮어쓰지 않고 알린다. 초안은 적용에 성공한 뒤에만 지운다. PDF 보정에 올린 PDF는 추출 작업이 처리되는 동안에만 서버에 두고, 끝나면 비운다. 자동 추출 결과는 다시 불러올 수 있게 남긴다.

`PDF로 보정`에서 고른 PDF를 서버가 AI 모델로 추출하고 원문과 나란히 대조한다.
독립된 JSON 입력·파일 가져오기·예제 화면은 제공하지 않는다.
새 공고는 `공고 추가`에서 직접 입력한다.

### 4. 다음 수집의 변경 확인

원천을 확인하고 수정할 값이 없으면 근거를 적어 `현재 원천 확인 기록`을 누른다.
다음 수집 이후 원천 값이 바뀌면 상세의 비교 화면이 새 원천을 보여 주고, 확인 전 화면으로 저장하면 최신값을 다시 보라고 거절한다.
현재값을 유지할지 수정할지 검토하고 새 원천 확인 기록을 남긴다. 값 수정·등록값 검토 기록은 별개다.

서버 계약은 [관리자 데이터 검토 흐름](review-api.md),
기존 흐름은 [DB 단지 비교](guide.md#단지-기본정보-비교)을 참고한다.

### 5. 공급정보를 공고 단위로 보정

공고 상세의 `공급정보·단지 연결`은 저장된 공급정보 표부터 보여준다. 각 행의 모집수·임대조건 개수·누락 상태를 확인하고 필요한 행만 펼친다.
표에서 행을 펼치지 않고 원천 공급행은 `제외`, 관리자가 추가해 저장한 행은 `삭제`로 표시한다. 저장 전 추가한 행은 `지우기`로 바로 없앤다. 제외도 다른 변경처럼 보정 이유·공식 근거와 함께 저장한다.
`직접 추가`로 빈 공고의 첫 행부터 만들 수 있다. `PDF로 채우기`는 현재 편집 중인 행을 기준으로 응답을 대조한 뒤 같은 편집표에 채운다. PDF는 추출 작업이 처리되는 동안에만 서버에 두고, 끝나면 비운다.
행 추가·제외·복원, 단지·주택형 연결, 공고별 주택형 표기·면적·모집수와 순서를 변경할 수 있다.
주택형 이름이 틀렸을 때 이 공고에서만 다르게 부르는 경우(예: `26형 고령자(주거약자용)`)는 `이 공고의 주택형 표기`를 고친다.
단지 주택형 이름 자체가 틀렸다면 `단지 주택형 이름 고치기 →`로 단지 상세에서 고친다. 이 변경은 그 단지를 쓰는 모든 공고에 반영된다.
수집 원문 단지명·주택형명은 정제가 매칭에 쓰는 값이라 이 화면에서 바꾸지 않는다.
공통 주택형이 없으면 `이 단지의 주택형 확인 → 누락된 주택형 만들기`로 생성과 연결을 함께 요청한다.
공고 모집수는 단지·주택형 전체 세대수에 반영하지 않는다. 빈 수량·금액은 미확인, 숫자 0은 확인된 0이다.
대상 모집수가 중복 없이 행 모집수와 같은 범위일 때만 수량 합계 확인을 선택한다.

공식 근거 URL·페이지·이유를 적고 `공급정보 저장`을 누른다. 서버 검증과 확인 토큰 발급 후 동일한 변경안을 저장한다. 별도 미리보기 단계나 5단계 진행표는 없다.
원천·연결 후보·등록값이 달라지면 적용을 거절한다. `입력을 유지하고 최신값 비교`에서 겹치는 항목을 선택한다.
응답 유실 시 같은 작업으로 결과를 확인한다. 이 탭의 새로고침 후에도 작업을 복원하며,
브라우저 저장 공간에 재확인 정보를 보관하지 못하면 적용을 시작하지 않는다.
일반 작성 중 입력을 자동 저장하는 기능은 아니므로 이동·새로고침 경고를 확인한다.

저장 후 사용자 공고 화면과 남은 문제를 확인한다. 적용으로 바뀐 행·조건은 표시 순서대로 검토한다.
수집 원천은 `출처·수정 이력`에서 확인한다. 대응 근거가 부족하면 임의로 연결하지 않는다.
`저장된 공급정보 검토·보류`에서
확인한 행·조건과 필드만 선택하고 판단·근거를 기록한다. 선택한 원천 필드는 실제 값 변경·소실을 추적하며,
선택하지 않은 원천이나 외부 원문 자체의 변경을 자동 판정하지 않는다.
기록은 누적하고 같은 대상의 최신 기록을 현재 판단으로 사용한다. 보정 저장은 전체 검토 완료가 아니다.

보정한 행의 원천이 사라지거나 비활성화되면 값을 유지하고 검토 목록과 작업실에서 재확인을 안내한다.
공통 주택형 수정은 별도 화면에서 영향을 받는 공고를 확인한다. 공급행이 연결된 주택형은 전용면적을 바꿀 수 없다.
면적이 틀렸으면 올바른 면적의 주택형을 새로 만들고 공급행을 옮긴 뒤 옛 주택형을 휴지통에 넣는다.
조건부 보정 되돌리기, 전체 보정 보호 해제·원천값 채택, 일반적인 행 합치기·조건 이동은 아직 제공하지 않는다.

### 6. 운영 홈·의견·알림 조사

로그인 후 운영 홈에서 수집·정제 실패, 데이터 검토, 접수 의견과 알림 발송 문제로 이동한다.
일부 집계가 실패하면 0건으로 표시하지 않고 해당 영역에서 다시 확인하도록 안내한다.
오류·검토 목록에서 상세로 들어갈 때 검색조건·페이지와 선택 대상을 유지한다.

사용자 의견은 상태·관련 단지/공고·처리 결과를 기록하고 실제 처리한 관리자와 시각을 자동으로 남긴다. 보류와 처리 완료에는 이유가 필요하다.
내부 처리 기록이며 사용자에게 메시지를 발송하지 않는다. 동시 변경은 입력을 유지하고 최신 기록과 비교한다.

알림 발송 내역은 회원·공고·상태로 조회한다. 공급자 수락, 사용자 읽음, 발송 내역 없음은 서로 다른 상태다.
실패 코드·시도 횟수·다음 재시도 시각을 확인하며 이 화면에서 알림을 재발송하지 않는다.

### 7. PDF 응답으로 기존 공고 보정

공고 상세 상단의 `PDF로 보정`에서 PDF를 고르면 AI 워커가 필요한 쪽을 골라 추출 프롬프트로 값을 뽑는다. 프롬프트는 워커 리소스(`ai-worker/src/ai_worker/prompts/announcement-pdf-extraction.txt`)에 두며 화면에서 편집하지 않는다. 신규 공고 등록, 공통 주택형 수정은 이 흐름에 포함하지 않는다.
마크다운 코드 블록, 잘못된 JSON 이스케이프와 HTML 공백 문자 코드(`&#x20;`·`&nbsp;` 등)는 자동 복구하며 내역을 화면에 표시하지 않는다. 문자 코드가 따옴표 옆이면 지우고, 그 밖에는 공백 한 칸으로 바꾼다. 금액은 최대 18자리 정수 문자열을 유지한다.
모델은 공고문 값을 옮기기만 하고 계산은 화면이 한다. "26A/B/C"처럼 묶인 주택형은 LH 한 행이라 `subtypes`로 받아 공급행 하나로 둔다. 모집수·대상·임대조건은 그 행에 두고, 전용면적마다 하나인 세부 타입 주택형을 모두 그 행에 연결한다(함께 모집하는 주택형). 공통 모집수는 만들지 않는다.
세부 타입은 전용면적으로 단지 주택형을 찾는다. 하나로 정해지면 읽기만 하고, 같은 면적 후보가 둘 이상이거나 면적이 없으면 고르게 하며 고르기 전에는 확인 필요로 남아 저장하지 않는다. 단지에 같은 면적 주택형이 없으면 그 세부 타입의 형명·면적으로 새 주택형을 만든다. 대표 주택형은 저장 위치의 지금 주택형을 고른 세부 타입, 없으면 첫 세부 타입이다. 주택형 이름·공급면적·건설호수는 세부 타입마다 반영하되, 이름은 관리자가 공급행의 주택형 표기를 받아들였을 때만 반영한다. 새 주택형 추가를 고른 세부 타입은 최신값 비교 뒤 단지에 같은 면적 주택형이 생기면 그 주택형으로 다시 고른다. 주택형 가격은 고른 대상 금액을 연결한 주택형 모두에 쓴다. 공급행 면적은 대표 주택형을 따른다.
공급면적은 전용 + 공용으로 계산하고, 여러 행에 같은 사실은 `[*]` 경로 하나로 받는다. 근거는 공급행과 대상별 임대조건마다 받는다. 임대조건 표가 공급 표와 다른 쪽에 있는 경우가 많아서다. 세부 타입은 공급행 근거로 확인한다.
`개별안내`처럼 날짜가 없는 일정은 `notApplicable`의 path `schedules`로 받는다. 받은 일정 값에는 적용하지 않고 일정 영역에 `날짜 없이 안내한 일정`으로 보여 준다.
건설호수 합계와 단지 전체 세대수, 대상별 모집수 합계와 행 모집수, 공고문 공급면적과 계산값이 다르면 공급정보 위 `검산 확인`에 표시한다. 저장은 막지 않는다.
PDF 공고명·공고일이 현재 공고와 다르면 다른 공고의 PDF일 수 있다고 경고한다.

- LH 공급 원본 행이 있는 단지는 단지 탭 위 `LH·PDF 대응`에 LH가 준 행과 PDF 행을 주택형 표기·전용면적·세대수와 합계로 나란히 보인다. LH 통합행 하나(예: 240세대, 면적 없음)를 PDF가 여러 행(200·25·15)으로 적었으면 `LH는 이 단지를 1행(…)으로, PDF는 3행(…)으로 적었습니다.`로 차이를 요약하고 `PDF대로 N행으로 나누기`와 `LH대로 1행 유지`를 단지 단위로 묻는다. AI 워커가 그 LH 행을 표시했거나(`lhSourceRow`) PDF 모집수 합이 LH 이번 공급 수와 같을 때만 나누기에 `(권장)`을 붙인다. 나누면 통합행이 ID를 유지한 첫 행이 되고 나머지 PDF 행은 새 공급정보가 되며, 그 결과를 `#747(240세대)이 051.9800A 200세대가 되고 059.9100A 25세대 · 059.9300B 15세대가 새로 생깁니다.`처럼 보인다. 1행 유지는 첫 PDF 행이 통합행을 고치고 나머지 행을 이번 보정에서 반영하지 않는다(행의 `적용`으로 다시 넣을 수 있다).
- 공급행이 없는 LH 행은 같은 영역에서 `LH 행 '59.19B 5세대'에 맞는 PDF 행이 없습니다.`로 하나씩 묻는다. `PDF 행 고르기`는 고른 PDF 행을 그 LH 행에 붙인 새 공급정보로 저장하고, `이번 보정에서 그대로 두기`는 질문만 접는다(임시저장본에 남는다). 어느 쪽이든 새 공급정보 추가를 막지 않는다.
- 공급행마다 저장될 곳을 한 문장으로 보인다(`기존 공급정보 #1033(051.9800A)을 고칩니다.`·`새 공급정보로 추가합니다.`·`#747(240세대)을 나눈 행입니다.`). `바꾸기`는 추천 행을 먼저 두고 이 공고의 제외하지 않은 공급행 전체를 단지·주택형·면적·모집수·#ID로 찾아 고칠 행을 고르거나 `새 공급정보로 추가`를 고르게 한다. 나누기와 LH 행에 붙이기는 `LH·PDF 대응`에서 정하고 행에서는 `LH·PDF 대응 보기`로 그리로 이동한다.
- 행 대응은 단지명, 면적, 선택적으로 건설호수, 주택형명을 바탕으로 제안한다. 표기·면적 근거 없이 남은 기존 행 하나는 모집수가 같을 때만 고르고, 아니면 고르지 않고 후보를 추천으로 보인다. 단지명 표기가 달라 찾지 못하면 이번 모집수가 유일하게 같은 기존 행을 확인 필요로 제안한다. 저장할 곳을 바꾸면 주택형 후보를 다시 계산하되 관리자가 고른 값은 유지한다. 자동 대응 근거(AI 표시·모집수 합 등)는 행의 `자동 대응 근거`에 접어 두고, 근거 없이 고르지 않았거나 전용면적이 다르거나 LH 이번 공급 수가 0세대이거나 AI가 표시한 LH 행과 저장할 곳이 다를 때만 `이 대응이 맞는지 확인하세요.`와 그 까닭을 보인다.
- 여러 공급행이 같은 기존 공급정보를 고치면 `공급행 2(059.9100A)도 같은 기존 공급정보 #747(공공임대)을 고칩니다.`로 저장을 막고, 그 행이 LH 통합행이면 `PDF 행마다 나누기`를, 아니면 `저장할 곳 다시 고르기`를 제공한다. 나누는 첫 행이 합친 모집수를 그대로 두면 두 번 센다고 알리고 그 행의 모집수 칸으로 이동하게 한다. 나눌 PDF 행이 하나뿐이면 저장을 막는다. 나눈 행의 모집수 합이 LH 이번 공급 수와 다르면 경고한다.
- 같은 이름·전용면적의 주택형 후보는 공급면적으로, 그래도 같으면 주택형 번호로 구분한다.
- 같은 LH 행을 가리키는 공고문 행 여럿(LH `26A/B(고령자)` ↔ 공고문 26A·26B)은 대상·금액이 같으면 세부 타입 묶음 행 하나로 접어 그 LH 행에 저장한다. 대상·금액이 행마다 다르면 접지 않고 저장할 위치를 확인하게 한다. LH 행이 공급대상 묶음(`고령자`)이면 공고문 행의 대상이 모두 그 묶음일 때만 접고, 같은 세부 타입을 가진 LH 행이 여럿인데 묶음으로 나눌 수 없으면 접지 않는다.
- 단지에 연결된 LH 행이 같은 주택형을 공급계층 묶음마다 따로 두면(`26A/B/C(고령자)`·`26A/B/C(주거급여수급자)`) 공급행은 주택형 × 공급계층 묶음이다. 공고문 행 하나의 대상이 두 묶음 이상에 들면 대상을 묶음별로 나눠 각 LH 행에 저장한다. 묶음은 행이 기록한 LH 공급 원천행의 표기로 읽는다. 모집수는 각 LH 행의 이번 공급 수이고 확인 필요로 둔다. 어느 묶음에도 들지 않는 대상(`기존거주자(철거민)`)은 첫 묶음 행에 넣고 안내를 붙인다. 세부 타입 주택형은 나눈 행마다 똑같이 연결한다. 단지에 연결되지 않은 LH 원천행에 맞출 때도 같은 규칙을 쓴다.
- 접거나 나눈 행의 공고 주택형 표기는 LH 행 표기가 아니라 공고문 표기다. 공고문 한 행이면 그 행의 표기(`26A/B/C`)를 그대로 쓰고, 공고문 행 여럿을 접었으면 형명을 잇는다(`26A/26B`). 이은 표기는 공고문 한 줄 인용에 없어 확인 필요로 두며, 관리자가 받아들일 때만 저장한다. 단지 주택형은 세부 타입마다 따로 연결한다(26A·26B·26C).
- 기존 행 표기로 세부 타입을 읽을 수 없어도(한스빌 `아파트` ↔ 공고문 26A·26B) 공고문이 행 모집수를 공통 모집수로 묶은 행들이 기존 공급행 하나와 새로 추가할 행뿐이고 대상·금액이 같으면, LH 한 행으로 보고 그 기존 행 하나의 세부 타입 묶음 행으로 접는다. 모집수는 공통 모집수이며 저장할 위치를 확인하게 한다.
- 공통 모집수는 그 밖에 공고문이 여러 행의 모집수 칸을 병합한 경우에만 기존 한 행과 서로 다른 기존 주택형에 연결한 새 행을 하나의 묶음으로 저장한다. 묶음 일부만 적용할 수 없다. 기존 묶음의 단지·합계는 관리자 화면에서 바꿀 수 없다. 세부 타입 묶음 행은 공통 모집 묶음에 넣을 수 없어, 그런 행이 든 공통 모집수는 저장하지 않는다. 이때 세부 타입 묶음 행의 모집수는 관리자가 직접 입력해야 저장할 수 있고, 나머지 행의 모집수는 비워 둔다.
- 각 항목에서 기존 값 유지·보정값 반영·직접 수정을 선택한다. 입력칸은 직접 수정에서만 열리며 잘못된 직접 입력은 적용을 막는다. 남은 `확인 필요` 수와 다음 항목 이동, 상태 필터를 제공하지만 저장을 막지 않는다. `보정 내용 적용`은 서버 검증 결과로 `적용 전 확인`을 열어 단지별 변경 전·후 공급행과 연결 주택형, 모집수 합계, 같은 주택형 중복, 통합행 처리와 분리 합계, 추가·변경 임대조건, 경고와 남는 LH 행을 보여 주고, `이대로 적용`을 눌러야 저장한다. 조건 하나를 제외해도 기존 조건은 삭제하지 않는다.
- 단지별 일정은 기존 ID를 보존해 같은 보정값을 복사한다. 선택한 기존 일정이 없으면 새 일정으로 추가된다. 연결이나 날짜 근거가 불명확한 일정은 기본 반영에서 제외하며 필요한 일정만 직접 선택한다.
- 근거가 없거나 현재 접수처 값이 더 자세하면 기본 선택하지 않는다. 자동 비교와 사람이 확인한 결과를 혼동하지 않는다.
- `409` 또는 저장 응답 유실 시 재적용을 막는다. `입력을 유지하고 최신값 비교`로 수동 값·제외·대응을 유지하면서 저장값을 갱신하고 행·일정 근거를 다시 확인한다. 이미 처리한 같은 요청이라는 409(`ADMIN_DATA_CONFLICT`)를 받거나 응답을 잃은 뒤 최신값을 비교하면 이 변경이 이미 반영됐는지 알린다.

LH 공급 원본 행을 공급행으로 만드는 일은 LH 공고 정제가 맡는다. LH 원천 소유 공고에 아직 공급행이 되지 않은 LH 원본 행이 있어도 PDF 보정의 새 공급정보 추가와 공급정보 편집표의 `직접 추가`를 막지 않는다. 저장하면 공고문 소유가 되어 정제가 그 행을 공급행으로 만들지 않으므로, PDF 보정의 `LH·PDF 대응`에서 맞는 PDF 행을 붙이도록 묻는다. LH 한 행을 주택형별로 나눈 분리 형제행은 중복으로 보지 않는다. LH 펼침 행이 있는 단지에 예전에 직접 추가한 행은 `LH 원본과 중복 가능`으로 표시한다. 공급정보 편집표에서 그 행을 펼치면 `펼친 행으로 합치기`가 같은 단지·같은 주택형에 연결된 펼침 행이 하나일 때 그 행을 제안하고, 없거나 여럿이면 같은 단지의 펼침 행 중에서 고르게 한다. 합치면 직접 추가 행의 공고 표기·모집수·입주예정월·공급구분·면적 중 비어 있지 않은 값과 제외하지 않은 임대조건을 펼침 행으로 옮기고, 직접 추가 행은 삭제 예정으로 둔다. 펼침 행에 제외하지 않은 임대조건이 이미 있으면 두 조건을 보여 주고 합치기를 막는다. 저장 전 `합치기 취소`로 되돌릴 수 있으며, 저장은 기존 공급정보 보정 한 건으로 남는다.

실패 검토에서 `AMBIGUOUS_HOUSING_TYPE`·`HOUSING_TYPE_NOT_FOUND`인 미해결 공고/LH 보강 오류에만 진입을 제공한다.
공고 미생성·휴지통·단지 미확정·수집 실패에는 제공하지 않는다. 묶음 건수는 현재 조회 페이지 기준이며 전체 미해결 수가 아니다.
보정을 저장하면 이 공고(같은 원천 공고 식별자)의 미해결 공고 정제·LH 보강 실패를 모두 해결로 바꾸고, 실패 검토 목록과 처리창에 `관리자 {이름}가 공고 보정으로 해결`로 표시한다.

## 단지 기본정보 비교

1. 관리자 단지 목록에서 대상을 연 뒤 `데이터 검증` 탭을 선택한다. 검토 목록의 비교 링크는 해당 탭으로 바로 진입할 수 있다.
2. 자동 정제에 연결된 마이홈 원천이 있으면 현재 등록값 옆에 바로 표시한다.
3. 추가 자료는 `원천 검색·연결`에서 마이홈 단지 또는 LH 임대 단지를 검색한다.
   `연결 전 원천 확인`으로 이름·주소·공급 범위를 살펴보고 근거를 적어 연결한다.
4. `값이 다른 항목`으로 좁히고 `이 원천값 사용` 또는 항목별 `수정`을 누른다.
   여러 원천이 다르면 각각 표시하며 대표값을 자동으로 선택하지 않는다.
5. 저장할 변경 전후와 수정 근거·메모를 확인하고 `수정사항 저장`을 누른다.
6. `출처·수정 이력`에서 바뀐 값과 당시 DB 원천을 확인한다.

조회·비교에는 파일이나 수기 값 입력이 필요하지 않다. 원천 연결·수정·검토 기록을
저장할 때에는 관리자가 확인한 근거를 남긴다. DB 원천은 수집 당시 자료이며 실시간 공식 정보는 아니다.

### 범위와 보호

- 비교: 단지명·기관·공급유형·준공일·세대수·주차대수·난방·건물·복도 유형·엘리베이터.
- 원천에 없는 최근 퇴거자 수·이미지·좌표 등은 미제공으로 표시하고 직접 수정할 수 있다.
- LH 단지 전체 세대수와 주택형 세대수를 구분한다. 단위·공급 범위는 사람이 확인한다.
- 주소·PNU·지역 코드·좌표는 접힌 주소 영역에서 함께 확인·수정한다.
- 직접 연결은 비교용이며 자동 정제의 단지 연결이나 통합을 바꾸지 않는다.
- 원천이 재수집으로 사라지면 연결을 유지한 채 현재 원천 없음으로 표시한다.
- 저장 충돌은 수정값을 유지한다. 필요한 값을 메모한 뒤 `비교 데이터 다시 조회`로 재검토한다.
- 수정과 확인 범위·검토 기록은 동시에 작성하지 않도록 잠근다. 저장 또는 취소하면 다른 작업이 열린다.
- 값 수정만으로 검토 완료가 되지 않는다. `확인 범위·검토 기록`에서 실제 확인한 항목만 기록한다.
- 공고문은 공고 상세의 `공고문·첨부파일`에서 확인하고 필요한 값을 편집 화면에 입력한다.

이 문서는 단지 기본정보 비교를 설명한다. 공고·주택형·임대조건 비교와 재수집 대비 원천 확인은
[관리자 데이터 검토 흐름](guide.md#검토-절차)을 참고한다.
서버 계약과 마이그레이션은 [단지 원천 비교](review-api.md#단지-기본정보-비교와-수정)를 참고한다.
