# 신청자격 화면과 API 연결

공고 상세와 목록은 최신 신청자격 API를 사용한다. 이전 기본 비교의 MATCHED와 요약 집계는
지원 가능 여부나 건수에 사용하지 않는다. 판정 규칙의 원본은 [판정과 표시](decisions.md)다.

## 화면별 연결

| 진입점·화면 | 요청·동작 | 표시 범위 |
|---|---|---|
| 상세의 내 조건 수정·항목 입력, 마이페이지 `/mypage/conditions` | GET/PUT `/api/v2/me/eligibility-profile`, 입력 계약 3·expectedVersion·CSRF | 공통 사용자 정보. 해당 공고에 필요한 항목만 부분 입력 가능 |
| 공고 상세 `/announcements/{id}` | GET `/api/v2/announcements/{id}/eligibility` | 공고 결과, 실제 모집 선택지, 경로, 공통·경로별 조건과 근거 |
| 정보 저장 이후 | GET `/api/v2/eligibility/processing`와 상세 재조회 | 저장 완료와 현재 정보의 재판정 완료를 구분 |
| 공고 목록·배너·지원 가능 스위치 | v1 공고 검색 후, 불러온 공고의 최신 판정 조회 | **현재 불러온 목록 안에서만** 개인 판정 필터·건수 제공 |
| 내 조건 관리의 새 지원 가능 안내 | GET `/api/v2/eligibility/discoveries` | 현재 정보로 새로 확인됐으며 아직 확인 처리하지 않은 공고와 선택지 |
| 안내의 확인했어요 | POST `/api/v2/eligibility/discoveries/{rootAnnouncementId}/ack?eventId={eventId}` | 명시적으로 확인한 발견 이벤트만 확인 처리 |

[eligibilityRepository](../../../frontend/src/user/conditions/eligibilityRepository.ts)는 API의 응답을
화면 모델로 변환한다. 사용자 정보의 조건식 계산과 경로·공고 집계는 서버가 맡는다.
입력 화면은 현재 계약의 항목·흐름을 명시적으로 구성하며, 카탈로그로 입력 UI를 자동 생성하지 않는다.

## 결과와 입력 상태

- 수치 조건은 항목, 기준값·비교 방향·단위, 입력값을 함께 보여준다. 나이는 공고 기준일의
  환산값도 표시한다. 소득표 근거의 연도·가구원 수·비율을 함께 읽을 수 있다.
- 확인된 미충족은 다른 항목이 미입력이어도 유지한다. 부족한 항목을 추가하면 해당 조건도
  확인한다는 문구를 사용한다. 복합 조건은 하위 조건별로 표시하고 수정할 수 있는 항목을 연결한다.
- 수집하는 정보의 누락에는 해당 항목 입력창을 연결한다. 수집하지 않는 필수 법정 자격은
  정확한 자격명·원문 조건과 직접 확인 안내를 제공한다. 가족 형태나 필터 선택으로 법정 자격을 확정하지 않는다.
- 신청 제한 이력 등 `APPLICATION_EXCLUSION`은 별도의 접기 영역에 표시한다.
- 빈 가족 수·자녀 수를 다른 항목 수정으로 자동 확정하지 않는다. 가족 형태가 미입력이어도
  독립 수집하는 소득·가족 수·선택 가족 정보를 보존한다. 거주지역을 바꾸면 이전 지역 거주기간을 비운다.
- 정정 전 ID로 상세를 조회해도 현재 공고 ID의 판정 응답을 받아들인다. CANCELLED,
  NOT_STRUCTURED, NOT_PUBLISHED는 개인 자격의 미충족으로 바꾸지 않는다.

## 최신성·실패 처리

저장 성공은 재판정 완료가 아니다. 저장 성공 시 이전 상세·목록 결과를 숨기고 현재 정보로 다시
확인 중이라고 안내한다. 처리 중 상태를 입력 부족이나 필수 자격 직접 확인으로 표시하지 않는다.

현재 사용자, 프로필 버전, 저장 후 갱신 번호, 공고 및 지역이 응답의 적용 범위다. 범위가 바뀌면
진행 중 조회를 취소하고 이전 응답을 표시하지 않는다. 계정 전환 시 입력창·충돌 안내도 초기화한다.
다른 창에서 프로필을 수정한 경우 처리 상태의 프로필 버전을 통해 재조회한다.

처리 중 상세는 짧은 간격으로, 완료 결과는 30초 간격으로 다시 확인한다. 목록 상세 조회는 동시에
최대 4건씩 실행한다. 이 동작은 현재 화면 연결 방식이며 100만 명 규모의 처리량을 검증한 결과가 아니다.
조회 실패는 재시도 화면으로 표시하고 0건이나 미충족으로 대체하지 않는다. 서버 재판정 복구는
[저장·작업 처리 계약](storage.md)에 따른다.

## 목록의 조회 범위

일반 목록의 전체 건수는 v1 공고 검색의 `totalCount`다. 개인 판정 배너와 필터 건수에는
“불러온 공고 중 지원 가능”을 표시한다. 일부 페이지의 판정을 전체 공고 집계로 확대하지 않는다.
추가 페이지가 있으면 다음 공고를 불러올 수 있다. 정보 저장만으로 개인 필터를 자동 선택하지 않는다.

지역을 선택하면 판정 요청에도 해당 지역을 보낸다. 지원 가능 스위치를 켰을 때는
`eligibleOptionIdsInRegion`이 있는 공고만 남긴다. 수지구의 선택지는 미충족이고 기흥구의 선택지는
충족인 D01은 수지구+지원 가능 목록에서 빠지지만 공고 전체의 판정은 지원 가능이다.
스위치를 끄면 수지구 공고 검색 결과에 다시 나타난다. 공고 필터는 API가 반환하는 용인시 수지구·기흥구
전체를 선택할 수 있으며, 기존 단지 필터의 도시 중심 선택 방식은 유지한다.

## 새 지원 가능 안내

내 조건 관리에서 재판정 완료 후 발견 API를 조회한다. 화면에 표시하기 전에 해당 공고의 현재
결과와 이벤트의 선택지 ID를 대조한다. 조회만으로 확인 처리하지 않고 확인했어요 버튼을 눌렀을 때
API 성공 후 제거한다. 오래된 이벤트의 409는 목록을 다시 조회해 처리한다. 빈 페이지에도 hasMore가
있으면 다음 안내를 조회한다. 계정·정보 변경 시 이전 안내를 숨기고 주기적으로 현재 목록을 다시 확인한다.

이 화면은 Q8에서 허용한 화면 안내를 연결한 것이다. 별도 알림 발송이나 사용자·공고별 평생 1회 발송
정책을 도입하지 않는다. Q7 관심 조건·수신 설정과 채널별 전달 방식은 그대로 후속 연결 대상이다.

## 남은 연결과 검증

전체 공고를 대상으로 한 개인 판정 검색·정확한 집계 API, 특수조건 분류 필터, Q7 관심 조건과
신청자격을 함께 적용한 구독·발송은 아직 이 화면과 연결되지 않았다. v1 검색·알림 기능의 존재만으로
이를 완료한 것으로 보지 않는다. 수집된 원문 전체의 구조화·공개 흐름도 별도다.

프런트 변경은 `frontend/`에서 `npm run check`로 검사한다. 대표 회귀 검증은 다음과 같다.

- `eligibilityRepository.test.ts`: 최신 API, 지역별 선택지, 실패와 입력 부족, 법정 자격·제한 분리.
- `ConditionsProvider.test.tsx`, `conditionDraft.test.ts`: 저장 버전, 계정 전환, 부분 입력 보존.
- `EligibilityDiscoveries.test.tsx`: 현재 결과 대조, 명시적 확인, 빈 페이지와 409 처리.
- `RegionFilterFields.test.tsx`: 공고의 하위 구 선택과 기존 단지 선택 방식 보존.

실제 브라우저에서는 D05 소득 미입력 상태에서 소득을 저장하고 재판정·새로고침 후 값을 확인한다.
자산 미충족과 소득 미입력을 함께 둔 경우에는 소득을 채워도 자산 미충족이 남아야 한다. D11은
법정 자격 직접 확인, D01은 위 지역 조합을 확인한다. 개인 로컬 검증 계정·실행 포트·커밋·증거는
해당 환경의 진행 기록에 남기며, 테스트 fixture를 원문 전체나 운영 공고로 취급하지 않는다.
